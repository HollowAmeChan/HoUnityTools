## 0. 一句话与分工

**控制器是一份作品：树形、坐标、姿势由作者定；代码只做装配与求值。**
Unity 侧把它搬到**影子台**上跑、只抄自己拥有的键（[`PIPELINE.md`](PIPELINE.md) §4）；
Warudo 侧把它打成 **AssetBundle**、在隐藏影子上跑真控制器再把结果采出来（[`PIPELINE.md`](PIPELINE.md) §7.1）。

**三件事分开，各归各的作者**：

| 谁 | 出什么 | 长什么样 |
| --- | --- | --- |
| **控制器**（生成器 / 混合树编辑器 / 拿现成的一份） | 树形、坐标、参数 | 一份完整 `.controller`；它引用的每个片段就是一个**槽位** |
| **动画文件夹**（动画工具的「形态键动画」栏 / 手 K） | 姿势数据 | 一堆 `.anim`，**文件名 = 槽位名** |
| **调试对象**（场景里的角色实例） | 写谁 | 它下面**所有** `SkinnedMeshRenderer` |

**改形状 / 核对的入口**（改设计时走这里，**别手改资产**）：

* 生成（两条路，见 §7「三处同步」）：菜单 `HoUnityTools/面捕/生成控制器骨架（VTS 原生语义）`
  （`Editor/FaceTracking/HoFaceControllerSkeletonBuilder.cs`）或文本生成器 `Tools~/FaceTracking/make-vts-controller.ps1`。
* 核对：`Tools~/FaceTracking/check-controller.ps1 -Path <那份>.controller` —— 参数名 / 类型 / 默认值 / 层状态与 WD /
  树形与轴 / Direct 子节点有没有挂参数，一次核完。**名字敲错一个字符 = 那条值被静默丢掉**，这一步别省。
* 包侧门：`.research/compile-check-pkg.ps1`（+ 改到 `.ps1` 时 `ensure-bom.ps1 -Fix`）。

### 1.1 眼睑：Direct 张量积表（最新形状）

**为什么是张量积**（§5.7.36 ①）：眼睛除了喜/悲还有**怒**。归一化 3 分量是两个自由度 ⇒ 在混合树里天生占**一张面**，
再乘闭合 1 维 = **3 维**；而 **Unity 的 BlendTree 只有 1D / 2D / Direct 三档，没有 3D 表**
⇒ 三维只能用**张量积门**表达：`gate = w情绪 × w闭合`，因为两边各自归一化 ⇒ **Σ门 = 1×1 = 1**。
而归一化是除法（非线性），**混合树只会做凸组合** ⇒ **归一化必须留在中间层，树只负责插值**。

**两条结构规则**（用户定）：

- **不拆键**（不要"开合键 + 形状键"分层）：那样状态不可控 ⇒ 仍是**一组眼形键**，全部靠状态点组合；
- **可达性交给状态点数量**：不可达的组合（如 `睁大×喜`）**不建状态点**，而且**门里不许写合并特判**
  ⇒ 前提是那个乘积**恒为 0** ⇒ 所以把"不许睁大"写成**判据里的一道门**。

**落地**：`LidL`/`LidR` 从 2D 9 格换成 **Direct 11 门表**（4 情绪 × 3 闭合 = 12 个状态点，减去不可达的 `睁大×喜`
⇒ **11 格/眼**），11 个门 = `Ho/Drive/Lid/<侧>/Gate/<情绪><闭合>`（共 22 行，表达式 = `out(Weight/<情绪>) × out(Closure/<闭合>)`，
两边各自归一化 ⇒ **11 个门相加恒 = 1**）⇒ 输出就是 11 张姿势的**凸组合**，`default` 不参与。
槽位名变得**一眼可读**：`LidL__Gate__NeutralOpen` / `…__HappyOpen` / `…__AngerWide` / `…__SadClosed` …。
⚠️ **一格动画同时写眼睑键 + 眉键**（眉眼合一）；`Ho/Drive/Brow/*` 四根轴照旧**发布当出口**（和注视/颊同理：发布但无树消费）。

⚠️ **删掉的是「按键表情整表分叉」**（§5.7.37）：原来眼/眉各有一套 `*Expr` 副本表 + `*Switch` 开关，
由 `Ho/Drive/Gate/Expr/{Smile,Angry}` 分叉。新方案里喜/怒/悲/中性是**中间层的归一化权重**
⇒ 权重混进同一组状态点，**不需要另一套表** ⇒ 删。

### 1.2 每格叶子是什么语义

| 树 | X 轴 | Y 轴 | 一格代表什么 | 分工（该写哪些键） |
| --- | --- | --- | --- | --- |
| `MouthCore` | `Mouth/Form`（读作**净笑量**）与 `Mouth/Open` **都是手工拉的自由点集** | 同左 | 外嘴基础：**唇的轮廓与口孔**，只回答「笑到什么程度 × 张多大」；⚠️ **顶行中间那一格不要**（嘴张到最大时半笑与全笑分辨不出来） | 只写唇/口孔，**不写下颌与下巴**；负侧三族全在别的表 |
| `MouthJaw` | `Mouth/Jaw`（**咬合/闭 ↔ 张开**） | —（1D） | **下巴只留上下**：咬合/闭（咀嚼也走这一档）↔ 张开。用户判定「**左右两个点完全没必要**」（实测下巴左右只在"微张 / 解放咬颌"时才到 **0.52**，咬紧时只有 **0.02~0.04**） | 下颌 / 下巴 / 口内 |
| `MouthCoreRoll` | 同 `MouthCore` | 同 `MouthCore` | **猫嘴版整嘴表**（嘴唇内翻压在牙上） | 与 `MouthCore` 同分工 —— 因为它是**替换**不是叠加 |
| `MouthShift` | `Mouth/X` **−0.95 往右 · 0 静息 · +0.95 往左**（有符号，曲线 ±0.20 死区） | `Mouth/Y` **0 静息 · +1 上**（只有两档：负侧钳到 0） | **整嘴平移残差**：嘴整体左右/上下挪、**唇形不变**；中间那格 = **零位移** | 只写**整嘴位移**那几根键，**不重画唇形** |
| `MouthWidth` | `Mouth/Pucker`（= `2×(dimpleL + dimpleR) − pucker`，⚠️ **2×和**）**−0.93 窄 · −0.09 中 · +2.0 宽** | —（1D） | **嘴宽**：嘴整体变窄 ↔ 变宽 | 只写**嘴宽**那几根键 |
| `MouthTongue` | `Mouth/TongueL`（**伸出量**）⚠️ **占位**（`tongueOut` 还没实测过） | —（1D） | **默认（不出舌）+ 沿对角线 3 步**：舌出来多少、嘴就张多少 ⇒ 不穿模。⚠️ 别做成 2D 表：那几个点在 2D 里**共线**（退化点集不可预测） | 舌相关键 + **每段自己把该有的张嘴量烘进去** |
| `LidL` / `LidR` | （Direct 表：权重门 = `w情绪 × w闭合`） | — | 该侧眼睑完整姿势（含眉的形状） | 该侧眼睑 + 眉相关键 |
| `NoseUp` | `Nose/Up` 0 不顶 / 1 上顶 | —（1D） | **鼻子上顶**。它连带的内眼睑上抬 / 眯眼 / 眉毛内下移**由物理共动带出**，不单独做检测 | 鼻相关键 |

**三条要记住的纪律**：

- **没摆的格不用补洞**：基础表没摆 = 复用同一份低维基础姿势；修正表没摆 = **零残差**。
- ⚠️ **Direct 是加法、不归一化**：兄弟表**写同一个键就会相加**。所以叶子姿势的键分工必须守住上表的「分工」列 ——
  最容易撞的是 `MouthCore`（唇）与 `MouthJaw`（下颌/下巴）。**加法确定的前提就是键不重叠**。
- ⚠️ **刻度是按索引命名的**（`A<n>X<i>Y<j>`）：往某个轴**中间或底部插一格，上面所有格子的编号都会顺移**
  ⇒ 已经烘好姿势之后改刻度 = 片段与语义错位。**先把刻度定死再烘**；真要改，就手动改名/搬移已烘的片段（生成器只建缺的、**不会替你搬**）。
- ⚠️ **`MouthCore` 的坐标是用户在 Animator 窗口里手工拉的**（11 个点：8 个手拉的 + 补的苦列 3 个）。
  **先读资产、再改生成器**，顺序反了就把他的手改冲掉（§7）。

## 2. 区域门与"现在没有门控"

### 2.1 我们**不再**做的事

| 删掉的东西 | 现在怎么做 |
| --- | --- |
| **区域门控 / 区域闸**（我们注入的开关） | **不注入开关**：哪些键算数由使用者自己的混合树/参数决定。会话里明写"没有区域门控"（`HoFaceAnimationSession.cs:205-206`） |
| ↳ 后果 | 编译出来的绑定数**就是控制器里有的那些键**（不再按区域排除） |
| ↳ Direct 树的每个子节点**必须**挂一个参数 | 那是**使用者那一侧**的事；我们那份实测控制器里恒 1 的那一格挂 `Ho/Drive/W/One` |
| **双眼同步（`HoFaceEyeSync`）** | 这类左右整形属于**参数生产**，写在中间层的输入行/输出行里（表达式 + 曲线 + 修饰符），不该在会话里做 |
| **"驱动对象列表"（手工维护的网格表）** | 要驱动的网格 = 调试对象下**所有** `SkinnedMeshRenderer`，每次现取新表 |
| **旧面板 UI** | 旧按钮名（"按 Animator 填充 / 装配控制器 / 检查绑定"）没有了；现在是「原地装配 / 只填动画 / 只重绑网格」+ 「详情」折叠栏 |

> 区域门控不是"做不到"（Direct 子节点挂参数就是门控，嵌套还是**相乘**的 —— §8），而是**我们不再替使用者决定**。
> 想门控就在自己的控制器里画。

**⚠️ 一条边界要读准**：`HoFaceNaming.cs` 里只剩 `Ho/Drive` 根、两根轴语义 `BlinkWide` / `Squint`、以及 `LidAxis()`
—— 也就是 `Ho/Drive/Lid/<Left|Right>/<BlinkWide|Squint>` 这 4 个名字由**代码**认。
**格子名、树名、坐标代码完全不认** —— 它们活在控制器里，是给**编控制器与姿势的人**看的。

### 2.2 门控归树、覆盖归输出阶段

§2.1 说的是"我们**不注入**门控"。那**用户想关掉某一块**怎么办？答案分两半：

| 谁 | 干什么 | 为什么 |
| --- | --- | --- |
| **树侧（控制器）** | **门控只门控"动作"**：恒 1 的门控参数画在**使用者自己的树 / 子节点**上，默认值住在**控制器参数**上（我们那份实测控制器里就是 `m_DefaultFloat: 1`） | 门控本质是**空间混合**，混合树就是干这个的；中间层不该知道树里有哪几个门 |
| **中间层输出阶段** | 用户想"用一个值把某个门控关掉"时，**不去改控制器的默认值**，而是在**参数写进控制器之前**把那个键覆盖进字典 | 覆盖发生在**同一次写入**里，不会多出"第二个写者"在旁边抢 |

**要认的三条后果**：

1. **门控不门控"参数"，只门控"动作"。** 中间层照旧不求值 gate —— Animator 参数与动态参数 Hub 里读到的仍然是**未门控**的值。
2. **覆盖必须每帧给值。** Animator 参数会**保持上次写的值**，"这一帧字典里没有这个键" ≠ 回到默认值；要 1 就写 1。
3. **名字必须在控制器参数表里**，否则**静默忽略**（写入那一步是按控制器声明的口逐个查字典的）。

#### ⚠️ 边界：**树里的门控只做一层**（2026-09-26 用户定）

这条边界要**说准**（2026-09-26 用户纠正过一次）：**Hub 本身不限制写者** —— 它是一片**"脚本写的工作台"**：
我们的中间层、作者自己挂在角色上的组件、别的 mod 的脚本，都能按名字写。真正的限制只有两条：
① **动画 clip 写不了它**（曲线写 `values.<i>` 那条路删了）；② **我们不提供"跑在控制器里"的写者**（那个状态机行为也删了）。
于是"**树内部算出来的量**"在**不往控制器里放代码**的前提下就没有出口了 —— 而其中唯一实际会被要的，就是**有效门控**：

| 树的形状 | "有效门控"是什么 | 传得出来吗 |
| --- | --- | --- |
| **一层**（那版控制器就是）：根 Direct 的子节点各自挂一个 gate 参数 | **就是那个参数** | ✅ 想让它在 Hub 上就加一行输出行；一层时它就是真值，**下游不用重算** |
| **嵌套**：门控下面再挂门控（子区域开关 / 用乘法把两个开关合成"有效门控"） | 各层相乘，只活在树里 | ❌ **我们那两条入口都交不出来**（clip 不行、我们也不往控制器里放代码）；真要就得**自己写一个组件**读 Animator 参数、算完再按名字写 Hub |

**规矩**：**树 gate 只做基础 gate，只做一层，不做乘法分叉、不做嵌套的区域开关。**
想要"两个开关的与"（例如 `眼开 && 某条件`），正确做法是**在中间层乘好**，把 `gate = a * b` 作为**一行输出**喂进树。

⚠️ **别把"区域子树本身是 Direct"误判成违规。** 那是对的形状：区域子树里挂的是**每键的参数**（`browInnerUp` / `jawOpen`…），
**不是第二个开关**。树上"gate × 每键参数"的乘积是**普通混合权重**，不是门控 —— 下游要"某个键实际被应用了多少"，
把两个值（都在 Hub 里）乘一下就行，那不需要重算门控规则。
（引擎能力本身没变：嵌套 Direct 门控确实相乘，实测 `0.6 × 0.8 → 48` —— §8。这条规矩说的是**不要那样用**，不是"做不到"。）

> **"行侧 gate"现在可以做了**（补完"每行的默认值"之后）：在配置文件里写一行**常量行** ——
> `parameter = Ho/Drive/Gate/Lip`、`expression` **留空**、`defaultValue = 1` —— 中间层每帧就把 1 写进去，
> 控制器那边连 `m_DefaultFloat` 都不用管（"控制器只是混合器"这条终于闭环）。语义见 [`PIPELINE.md`](PIPELINE.md) §3.6。

## 3. 二维表（FreeformCartesian2D）：命名形状与摆法

**名字是唯一能把「混合树里的格子」和「去 DCC 做形态键时的那张清单」对上的东西**，
所以它定在**一处**（本文 + `HoFaceNaming.cs` 里那几个参数名），不许各自拼字符串（散着写迟早会漂）。

### 3.1 名字的形状

```text
二维： <树名>__<X语义>__<Y语义>__A<n>X<i>Y<j>        例：LidL__BlinkWide__Squint__A3X2Y0
一维： <树名>__<轴语义>__A<n>X<i>                 例：MouthShrugBase__Shrug__A3X1
副本： 把 <树名> 换成 <树名>Expr                   例：LidLExpr__BlinkWide__Squint__A3X0Y0
```

**每个字段都用 `__`（双下划线）分隔，名字里不出现单下划线**（ASCII、CamelCase）—— 于是"按 `__` 切"就是完整的解析规则：

| 字段 | 规则 |
| --- | --- |
| `<树名>` | `LidL` / `MouthCore` / …。**必须有**：左右两棵树除了名字完全一样，不带侧就会重名 |
| `<X语义>` / `<Y语义>` | 轴的语义，**正端在前**：眼睑开合「闭 / 睁大」→ `BlinkWide`；单端轴只写正端 → `Squint`。**这两段合起来就是"这棵树在混什么"** |
| `A<n>` | ⚠️ **`n` = X 轴刻度数**（⚠️ **允许非方阵**：嘴上有 4×3 的 `MouthCore` 与 3×2 的 `MouthShift`，分别写 `A4` / `A3`） |
| `X<i>Y<j>` | 坐标：**从 0 开始、左下为原点、永不出现负号**；可以取小数（`X0.5`） |

⚠️ **2026-09-28 更正：不再是"方阵"** —— 形状由 `A<n>`（X 档数）与规则表里的 `ys`（Y 档数）一起决定；
照"方阵 + 留空"去读会把 3×2 表的 `Y1` 当成"3 行里的中间行"（实际是 2 行的顶行）。

**原始那条"为什么用方阵"的论证**（原文如此，保留作参考）：奇数刻度的中间刻度就是中线，两轴刻度数一致，
于是"中轴在哪"不再需要一条规则，也不会被误读成"关于 0 对称的 0.5 坐标" —— 而后者恰恰是默认误读
（Unity 的 2D 混合树心智模型就是"motion 围绕中心 `(0,0)` 组成多边形"）。
**刻度线性铺满该轴的值域**，顺序即从负端到正端：

| 轴 | 值域 | `A3` 的刻度 → 轴值 |
| --- | --- | --- |
| X 眼睑开合（双边） | −1 睁大 … +1 闭 | `X0`→−1、`X1`→0（**中线**）、`X2`→+1 |
| Y 眼睑眯眼（单边） | 0 不眯 … +1 眯满 | `Y0`→0、`Y1`→0.5（半眯）、`Y2`→+1 |

**方阵不必铺满。** 那版眼睑 X 走满三档，Y 只用 `Y0` 与 `Y2` 两行，中间 `Y1`（半眯）空着，空行交给树插值。
**下面按 Unity 2D 混合树图的朝向打印**（坐标随轴值增加 → `Y2` 在图的上方、`Y0` 在下方）：

```
LidL__BlinkWide__Squint__A3X0Y2 睁大+眯   …X1Y2 眯   …X2Y2 闭+眯     ← Y2（眯满）= 图的上方
LidL__BlinkWide__Squint__A3X0Y1 （空）    …X1Y1 （空） …X2Y1 （空）   ← Y1（半眯，没摆）
LidL__BlinkWide__Squint__A3X0Y0 睁大      …X1Y0 中性  …X2Y0 闭        ← Y0（不眯）= 图的下方
```

> **原点为什么在左下、为什么不是 DX 的左上。** DX 的左上原点是**光栅/渲染目标/屏幕**的约定（行主序 + V 轴向下），
> 它管纹理与帧缓冲，不管参数网格；而且 Unity 自己就两套并用（屏幕/GUI 左上，纹理 UV 左下，`Texture2D` 第 0 行在底）。
> 我们的网格**只被 Unity 的 2D 混合树图与本文档画出来**，那是一张普通笛卡尔图（`+Y` 朝上），所以取左下 0。
> **将来如果要把这张网格当查找纹理/矩阵索引**（2D LUT、跟别的模块交换矩阵），这里必须改成**左上 0、行主序**，
> 否则在纹理边界上一定出一次上下翻。那时记得本文档与用例一起改。

### 3.2 对照表（那版眼睑 2D 表）

**眼睑对照表**（左眼；右眼同构，`LidL`→`LidR`、键名 `Left`→`Right`）；表按图朝向排（上排 `Y2` 在前）：

| 片段名 | 坐标 | 树里 `Pos`（轴值） | 这一格写的键与值 |
| --- | --- | --- | --- |
| `LidL__BlinkWide__Squint__A3X0Y2` | X0 Y2 | (−1, +1) | `eyeWideLeft 100` + `eyeSquintLeft 100` |
| `LidL__BlinkWide__Squint__A3X1Y2` | X1 Y2 | (0, +1) | `eyeBlinkLeft 90` + `eyeSquintLeft 100` |
| `LidL__BlinkWide__Squint__A3X2Y2` | X2 Y2 | (+1, +1) | `eyeBlinkLeft 100` |
| `LidL__BlinkWide__Squint__A3X0Y0` | X0 Y0 | (−1, 0) | `eyeWideLeft 100` |
| `LidL__BlinkWide__Squint__A3X1Y0` | X1 Y0 | (0, 0) | 全 0 |
| `LidL__BlinkWide__Squint__A3X2Y0` | X2 Y0 | (+1, 0) | `eyeBlinkLeft 100` |

**眯那一行（`Y2`）的 `blink 90` 是这张表最有价值的一条**：眯眼自带眨眼量，所以"又眨又眯"永远不会加和成 200。
名字里已经有轴语义（知道在混什么）与坐标（知道哪一格），**但回答不了"这一格写多少"** —— 那必须查这张表。
`A3X2Y2`（闭+眯）那格的**艺术决定**同理："眨满时眯眼还剩多少"。

### 3.3 轴段词（槽位名里那两段从哪来）

完整轴段词表在 [`PARAMETERS.md`](PARAMETERS.md) 与 `FACE_TRACKING_NAMING.md` §6；下表是**当年那几根轴**的速查：

| 轴 | +1 / −1 | 参数里的轴名 | 方阵与占用 | 摆了的格子 |
| --- | --- | --- | --- | --- |
| 眼睑开合 | 闭 / 睁大 | `BlinkWide` | `A3` 的 X 轴 | `X0` `X1` `X2` 三档全走 |
| 眼睑眯眼 | 眯 / 无 | `Squint` | `A3` 的 Y 轴 | 只用 `Y0`（不眯）与 `Y2`（眯满），`Y1` 半眯空着 |
| 凝视内外 | 内 / 外 | `InOut` | 未来 | —— |
| 凝视上下 | 上 / 下 | `UpDown` | 未来 | —— |
| 唇角 | 欣 / 悲 | `SmileFrown` | 未来 1D（单轴） | —— |
| 横向偏嘴 | **+1 偏左** / −1 偏右 | `LeftRight` | 未来 1D | —— （旧版这里写 `RightLeft`，是没核公式的猜法：`mouthLeft − mouthRight + smileL − smileR` ⇒ 正端是**左**） |

**⚠️ 轴名"正端在前"这条老规矩继续用**：`BlinkWide` = +1 闭 / −1 睁大、`UpDown` = +1 上 / −1 下。
轴名只表达**观测语义**；模型镜像/方向是**校准映射**的事（写在各行的曲线里），不靠改名解决。

**⚠️ 中性约定**（作者摆采样点全照它）：

* **双向轴**（`Form` `Press` `Pucker` `LeftRight` `BlinkWide` `InOut` `UpDown` `Height`）：**0 = 静息**，两端约 ±1；
* **单端轴**（`Open` `Funnel` `Jaw` `Forward` `Squint` `InnerUp` `CheekL/R` `PuffL/R` `TongueL/R` `SneerL/R`）：**0 = 静息**、+1 = 满；
* VB 那些**静息 0.5** 的量（`MouthSmile`、`BrowLeftY`/`BrowRightY`）**进控制器前必须重映射**（`2x − 1`）——
  否则"中性在哪"会一棵树一个说法，而 0..1 的默认曲线还会把负半边**静默夹掉**。

**名字为什么还叫 `Form`**（2026-09-27 用户定：**不改**）：Cubism 标准参数就叫 `ParamMouthForm`，
VTS 官方把 `MouthSmile` 推荐接进它 ⇒ 不是自造词；改叫 `Smile` 会撞控制器里已有的 `Ho/Drive/Gate/Expr/Smile`（0/1 表情门）；
改叫 `SmileSad`/`SmileFrown` 会过度承诺（那是 VRCFT 给**双向**轴的名字）。
⚠️ 唯一要记住的是**读法**：**`Form` = 净笑量**（`[(smileL+smileR) + dimple/2 − (frownL+frownR) − pucker] / 2`），**仍会出负值**
（苦/噘压过笑时），负值照旧是"正值的抑制量"、照旧发布到 Hub，只是树把它钳到 X0 = 静息。

### 3.4 参数、门、切片

```text
轴参数    Ho/Drive/<部位>[/<Left|Right>]/<轴>     例：Ho/Drive/Mouth/Form、Ho/Drive/Lid/Left/BlinkWide
区域门    Ho/Drive/Gate/<Mouth|Eye|Brow|Nose>      默认 1，中间层写常量行
表情门    Ho/Drive/Gate/Expr/<表情名>               默认 0，中间层不写
恒 1 权重 Ho/Drive/W/One                            默认 1，没人写；**Direct 的每个子节点都要挂参数**
切片权重  Ho/Drive/Slice/<树名>/<切片名>            例：Ho/Drive/Slice/MouthCore/Funnel0Press0
```

- **区域门** = 中间层**常量行**（写 `1`）；调小 = 让这块回到启动姿势。**常量行不过曲线**，写 1 就是 1；但**修饰符照走**。
- **切片权重**（Funnel × Press 4 条）= 双线性切片，**四条和恒为 1**；profile 里算了，**树里还没接**。
- ⚠️ **Direct 的每个子节点都必须挂一个参数**（不挂就不参与混合）—— 所以"这一格永远全量生效"也要一个参数：**`Ho/Drive/W/One`**。
- **参数名一律 ASCII**（它是给后端吃的），只有片段名与树名是给人看的。

### 3.5 `m_DefaultFloat` 与常量行

**"行侧 gate"现在可以做了**：配置文件里一行**常量行**（`expression` 留空 + `defaultValue = 1`）就能每帧写一个门，
控制器那边连 `m_DefaultFloat` 都不用管。用户想临时关掉某一块，走**合并字典的 `覆盖` 口**（同一次写入里改值，不产生第二个写者）。

## 4. 变体与副本：两类"1D + 两张整表"

### 4.1 平行副本（按键表情）

重要树可以带一份**平行副本**：与主版**同轴、同键集合，只有姿势不同**，由一个门交叉淡入（1D 树，阈值 0/1）。

| 东西 | 名字 |
| --- | --- |
| 副本树 | `<树名>Expr`（例：`LidLExpr`） |
| 1D 开关容器 | `<树名>Switch`，`blendParameter` = 表情门 |
| 表情门 | `Ho/Drive/Gate/Expr/<表情名>`（`Smile` / `Angry` / `Wink`…）；**默认 0，中间层不写它** |

一个门可以同时驱动多张表的副本（`Smile` 同时改眼睑、眉 ⇒ 两棵 1D 树共用一个参数）。

⚠️ **2026-09-28 深夜：这一套（眼/眉的 `*Expr` + `*Switch` + `Gate/Expr/*`）用户判"这个方案应该删了"** ⇒
喜/怒/悲/中性改成**中间层的归一化权重**，权重混进同一组状态点，**不再需要另一套表**（§1.1）。
⚠️ **嘴没有副本**（2026-09-27 用户定，已删 `MouthCoreExpr` + `MouthCoreSwitch`）：
「按键表情版本身对于嘴张嘴笑没有意义」—— 夸张的笑嘴 = `Form` 更大，轴上本来就够得到；
**只有轴上到不了的"性质"才值得开副本**（笑眼、怒眉）。

### 4.2 轴驱动的变体（**另一类**：不是按键表情）

同一种"两个孩子都是整表"的 1D 树，但**由某根轴的值选**、阈值 = 那根轴上的**实测档位**（不是 0/1）。
语义上是**分叉**：那个时刻的姿势一定是**作者画过的两张表之一（或两者的加权）**，而不是几条残差相加。

| 东西 | 名字 | 例 |
| --- | --- | --- |
| 变体树 | `<树名><驱动它的轴段词>` | `MouthCoreRoll`（由**风格轴** `Ho/Drive/Style/CatMouth` 选中的 `MouthCore` 变体 = 猫嘴版整嘴）。⚠️ 树名里的 `Roll` 是**旧轴名**留下的；改它要连带动 8 个槽位名与槽位 GUID，所以当时只改了轴名 |
| 1D 开关容器 | `<变体树名>Switch`，`blendParameter` = 那根轴 | `MouthCoreRollSwitch`（blend = `Ho/Drive/Style/CatMouth`，阈值 0.15 / 0.30） |

⚠️ **变体 vs 副本**：机制一样（1D + 两张整表），区别在**谁选** —— 副本由**按键表情门**选（0/1），变体由**某根轴**选（实测档位）。
名字上用 `Expr` / `<轴段词>` 区分，一眼能看出是哪一类。
⚠️ **变体表被选中时必须是完整姿势**（WD 开着，没烘的格会让那几根键回默认）⇒ 作者要为用到的格画整张。
⚠️ **阈值必须显式写死**（`m_UseAutomaticThresholds: 0`），否则 Unity 会在 `[0,1]` 上平摊两档、静默错位。
⚠️ **变体表与主版逐点坐标必须一致**（主版是用户手拉的，变体那份不会跟着动）⇒ 检查器有一条硬检查。
⚠️ **2026-09-28 试砍过 3 格、当场撤回**：那三格看着"轴上到不了"，但**常开**（直接写 `Mouth/Roll ≥ 0.30`）会把它们采到 ⇒ **一格不少**。

### 4.3 变体/风格轴的开关：三个风格轴一个机制

| 形态 | 判定 | 常开注入线 | 自动开关 |
| --- | --- | --- | --- |
| 倒V | `Ho/Style/InvertedV = (mouthPucker * HoAutoInvertedV) + HoExternalInvertedV` | `HoExternalInvertedV` | `HoAutoInvertedV` |
| 鼓嘴 | `Ho/Style/Cheek` | `HoExternalCheek` | `HoAutoCheek` |
| 猫嘴 | `Ho/Style/CatMouth = 判定 × HoAutoCatMouth + HoExternalCatMouth` | `HoExternalCatMouth` | `HoAutoCatMouth` |

- ⭐ **键盘/按键要"强制某个形态"怎么办 —— 走增量开关，别去写轴**（2026-09-28 用户更正）：
  写 `HoExternalXxx` = 1 就是常开（判据那一半照样在跑，它加在判定**前面**）；`HoAutoXxx` = 0 则只留常开、关掉自动触发。
  ⚠️ 直接写轴（`Ho/Drive/Style/CatMouth` ≥ 0.30）也满档，但那是**绕过中间层**的旁路。
- ⚠️ **`Ho/Style/*` 是中间层内部行**（只被别的输出行读，**不写控制器参数**）；`Ho/Drive/*` 才是**契约**。
  控制器看不见内部行 ⇒ 由**契约行**转发：`Ho/Drive/Gate/MouthStyle = out("Ho/Style/MouthGate")`、
  `Ho/Drive/Style/InvertedV = out("Ho/Style/InvertedV")`（猫嘴那条即 `Ho/Drive/Style/CatMouth`）。
- ⭐ **形态门压在哪些孩子上**：两个风格化形态（倒V / 鼓嘴）要顶掉的是 **"张嘴 × 笑"整块**
  （`MouthCoreRollSwitch` / `MouthShift` / `MouthWidth`）；下巴（`MouthJaw`）与舌头（`MouthTongue`）跟风格化不冲突 ⇒ 恒 1；
  两条形态子树本身就是"被门放行的东西" ⇒ 恒 1（再挂门就套娃了）。
- ⚠️ **猫嘴不关其他**：它不关整块"张嘴 × 笑"，它是变体开关在**块内部**换整张嘴 ⇒ 只发一条契约行。
- ⭐ **猫嘴判据现状**（2026-09-28 换）：`Roll = clamp(下唇卷 × clamp((嘴角方向 − 0.12)/0.10, 0, 1) × (1 + 3·jawOpen²), 0, 1)`，
  其中 `嘴角方向 = (酒窝左 + 酒窝右)/2 − (苦左 + 苦右)/2` —— **两个条件都得成立**。
  修饰符：**维持**（trigger **0.28** / threshold 0.26 / hold 0.2 ⇒ 释放 0.02）+ **平滑 0.08 s**。
  ⚠️ **旧口径已被推翻**（旧 = `√(上×下) × 死区 × (1+4·jawOpen²) × 噘嘴门`，实测缝 **−0.24** ⇒ 说话就已经是目标 3 倍）。
  ⚠️ **已知的理论缺口**：**笑 + 下唇卷 ≥0.15** 会开始淡入（实测余量 2 倍）。

### 4.4 副本 / 变体的开关树：`Simple1D` 的两个参数

- **阈值必须显式写死**（`m_UseAutomaticThresholds: 0` / 生成器与检查器钉 `0` 与 `1` 两档）。
- **`m_NormalizedBlendValues` 必须全是 0**（检查器有一条断言）—— 见 §8.4。

## 5. 装配：就地改你工程里那一份

**装配 = 把「你自己复制到工程里的那一份控制器」就地改成能跑的样子。** 面板上就是这几步：

```
预置控制器目录（Editor/FaceTracking/Controllers/，现在只有一份 README）
  ↓ 菜单「HoUnityTools/面捕/控制器编辑」→「打开目录」（你自己把要的那份复制进工程，之后归你管）
  ↓ 把它拖进「控制器」栏 —— 这一栏选中的那份就是会话真正跑的那一份
  ↓ 点「原地装配」＝
      ① 按槽位名把「动画文件夹」里的同名 .anim 填进树与状态（没找到就保留控制器自带的那份）
      ② 把每条形态键曲线重绑到「调试对象」的网格上
      ③ 清掉填完之后已经没人引用的临时片段
  ↓ 就地改这一份：不新建资产、不改名、不移动、不动 GUID、不碰层与参数
```

装配的入口是 `HoFaceAnimationAssets.Adopt(controller, 同一个路径, …)`：`sourcePath == targetPath` 时整段复制被跳过
（`HoFaceAnimationAssets.cs:122-131`）；面板就是这么调的。

> **旧流程已经不存在**：「混合树模板 → 复制出一份新控制器 → 输出到某路径」这条（以及设置里的 `assemblyOutputPath` 字段）删了。
> `Adopt` 的 `template != target` 复制分支还在，但只给脚本与用例用；面板只走"模板 = 自己"的原地分支。
> 设置里还留着 `treeTemplateGuid` / `treeTemplatePath`，注释也写明"工具页已经不需要它了，保留给脚本与验收用例"。

| 项 | 现状 |
| --- | --- |
| 图层 / 状态 / 参数 | **作者的事**，装配不增不减 |
| 槽位填充 | 文件夹里同名 `.anim` **顶替**控制器自带的那份；「详情」栏实时列出每个槽位是"文件夹 / 模板自带 / 缺" |
| 驱动对象 | 调试对象下所有 `SkinnedMeshRenderer`；一个键可以落在多个网格上 |
| 模型上没有的键 | 那条曲线**原样留着不动**（作者的格子数据不丢），「详情」栏报出"这些格子落不到任何网格上" |
| 外部片段（别人的 `.anim`） | 先复制成本文件的子资产再改，树里的引用一起换掉；**共享资产一个字节不动** |
| GUID | 就地装配根本不换文件，GUID 自然不变。`Adopt` 的复制分支也会把 GUID 塞回去 |
| 幂等 | 反复装配结果一致 |

**为什么动画要放在文件夹里**：树是"结构"，动画是"数据"。分开之后，改姿势不用碰树、换模型不用重做动画
（装配时按**形态键名**重绑，这份文件夹跟模型无关），而且"缺哪些动画"变成一个能显示出来的事实。
"缺"有三种：文件夹里没有、控制器自带的片段也没写任何键 —— 「详情」栏逐槽位说清楚是哪一种。

**代价是诚实的**：我们不再能保证控制器的形状，所以「详情」栏改成**从资产读实况**
（几层几个状态、会写哪些键、哪些键这台模型没有），而不是从配置推断。

**归属不靠名字判断**：装配时按"调试对象里谁有这个键"重绑，不靠树名/片段名认领 —— 所以改名字不会漏掉任何东西。

### 5.1 装配之后，谁负责什么

| 东西 | 谁管 |
| --- | --- |
| 树形、格子坐标、参数名 | **控制器作者**（生成器 / 混合树编辑器） |
| 每格写哪个键、写多少 | **动画文件夹里的片段**（控制器自带的片段只是兜底） |
| 动画驱动哪些网格 | 调试对象（装配时作用于曲线绑定；没有"驱动对象列表"这种东西了） |
| 参数的值怎么算出来 | 中间层（[`PIPELINE.md`](PIPELINE.md) §3）；控制器只等着被喂 |
| 哪些键算我们拥有的、要不要抄回真模型 | 会话：通道模式 + 输出所有权（[`PIPELINE.md`](PIPELINE.md) §4.4） |

**边界仍在**：运行期只允许形态键曲线；无 Behaviour、无同步图层、无事件/对象曲线/Humanoid、**Direct 树必须 WD 开**。
装配**不拦**这些（`Adopt` 不调 `Compile`），**开始驱动时才拒**，面板会说是哪一条（`HoFaceAnimationAssets.cs` 的 `Compile` 检查表见 [`PIPELINE.md`](PIPELINE.md) §4.2）。

## 8. 混合树的**实测边界**（数字全部保留）

> 这一节的数字来自 **Unity 6000.3.15f1 · batchmode** 的矩阵探针（2026-09-27 补测）与判别性实验。
> 探针脚本是 `.research` 里的草稿（`.research/UnityFaceValidation2/Assets/Editor/HoBlendTreeProbe.cs`，**未入库**）——
> 数字与做法都记在下面，要复跑照这几棵树搭一遍即可。

### 8.0 精确模型

> **一句话**：混合树不是"参数进、任意函数出"的表达式求值器。它是**姿势插值机** ——
> 输出永远是"作者摆过的那些姿势的加权组合"；以下静态代数讨论限定于**叶子为常量姿势**的树。
> 完整 Animator 还包含时间、状态、属性曲线，**也能由叶子里的 Animator float 曲线产生参数**；不能把纯姿势树的限制推广到整个控制器。

Direct 树对**每一个属性**的结果是：

```
输出 = Σᵢ (Πⱼ 门控ᵢⱼ) · 值ᵢ   +   (1 − Σw) · 默认值        引擎不自动保证形态键范围
```

- `值ᵢ` 是**作者摆的常量**（片段里写的形态键值 / 位移 / 材质参数）。**树自己不产生数。**
- `门控ᵢⱼ` 是参数值。**嵌套一层 Direct，门控就多乘一次**（实测：**0.6 × 0.8 → 48**）。
- **`Σw > 1` 时不做归一化**（实测：同一属性 **0.6 + 0.8 → 140**，不是 70、也不是 80）。
  也就是"两个子节点各给一份"就是**相加**，Unity 不会替你平均 —— **裸的直通树为什么会过眨眼，根因就在这里**。
- **引擎不会自动钳制。** 上面那个 140 是 `GetBlendShapeWeight` 读回来的原值 —— Animator 把超过 100 的值原样交给 Renderer。
  **"姿势不超过 100"是设计纪律，不是引擎保证**（实测：参考实现 Shinano 的 **510 个片段里，一个 >100 的都没有**；
  它靠"权重和 ≤ 1"维持，`EyeSyncMix = 0.5` 正是为此而设）。
- 余项 `(1 − Σw)` 与**默认值**混合；WD 开时那个"默认值"是**Animator 启动时捕获的值**（实测）。
  判别性实验：同一条键在启动时被别的动画写成 33，之后 `0.6 × 100` 得的是 **73.2**（33 + 0.6 × (100 − 33)）；
  **WD 关**时同一棵树把余项混向硬 0，于是"基础动画也在写同一个键"时**发散**。

**推论：它是一台"以参数为变量的多项式机器"，没有钳制。** 这条推论决定了下面所有"能 / 不能"。

**WD 判别性实验（Direct 树会不会削弱）**：

| 条件 | jawOpen（参数 0.6） | mouthSmileLeft（参数 0.8） | 结论 |
| --- | --- | --- | --- |
| **Direct + Write Defaults 开** | **60.0** | **80.0** | 精确 = `参数 × 100`：不归一化、不互相削弱 |
| Direct + Write Defaults 关（没有别的写入者） | 0 | 0 | 归零 |
| Direct + Write Defaults 关（基础动画也在写同一个键） | 98.98 → 246.28 → 1059.33 | 131.97 → 531.97 | **发散** |

机制：`98.976` 精确等于递推 `out ← 0.6×100 + 0.4×out` 的第五项。结论两条：

- **Direct 树本身没问题** —— Unity 官方文档也明说 Direct 就是"把参数映射到子权重"，并点名可用于混合表情的形态键。
- **不可用的组合是「Direct 树 + 写默认值关闭」**。这个组合**代码直接拒**（`Compile` 里检查"状态关 WD 且动作里有 Direct 树"就抛）。

### 8.1 混合树以「动画」为处理对象，不是以「轨道」为对象

**① 一句话：混合树的处理对象是「动画」，不是「轨道」。** Direct 树里每个孩子有一个权重（它自己的混合参数）；
1D/2D 表里权重由孩子的**坐标**算出。两种情况下**同一个孩子的所有曲线共用这一个权重**
⇒ 等价于"**以动画为单位先预乘**" ⇒ **不存在**"这根键按这个权重、那根键按另一个权重"。

**② 表内（1D/2D）的权重和恒为 1**（实测；缺角时靠负权重也必须凑成 1）⇒ 代进 §8.0 的式子，余项 `(1 − Σw) = 0`
⇒ **默认值根本不参与**。于是：

* **"给不写这根键的格子补一条 0 轨道"与"不补"数学上完全等价** ⇒ **0 轨道一根都不用铺** ✓；
* 某一根键只有一格写了 1 时，这根键在整个表里的曲线**就是那一格的权重曲线**（`Σ w·v` 里只有一项非零）；
* 代价：**那条曲线的形状你控制不了** —— 1D 是线性；2D 是 Unity 没公开的**距离权重**（实测偏差可达 ~6%，手算对不上）。

**③ ⚠️ 表内真正的风险不是"没写 0"，而是"表形状有洞 / 点共线重合"** ⇒ 权重被迫为负（`Σw` 必须凑成 1）
⇒ 只被一格写的键会冲到 **>1 或 <0**，而**引擎不夹取**。⇒ 两条实测结论：
**每个能到达的角都要摆上姿势**；**别让点落在别的点构成的边上或重合**。

**④ 跨区域（Direct 层）不归一**（最坏 `Σw = 5`）⇒ 默认值会漏，而且 `(1−Σw)·默认值 = −4×默认值`（甚至反号）
⇒ **默认值必须为 0**；同一根键两个**活跃**写者会**加权平均**（混合树没有"后写覆盖"）⇒ 要互斥只能用**门**，
**写 0 压不住**（只按权重摊）。

**⑤ 作者契约（每格只写三样）**：

1. **这一格要让哪些键起** —— 姿势本体；
2. **这一格里必须压到 0、而那根键默认值又 ≠ 0 的键** —— 只在这时写 0；
3. **不写别的区域拥有的键**（例：嘴表里不写下颌 / 舌头 / 颊的键）—— 跨区域抢键靠门解决。

**推论：静息 / 零位移那些格子留空就是对的**（残差 = 默认 = 0）⇒ 不必逐格铺满。

### 8.2 能表达什么（附配方）

| 想要的 | 怎么做 | 状态 |
| --- | --- | --- |
| 加权和 `Σ wᵢ·Cᵢ` | 多个子节点写同一个属性 | 实测 |
| **乘积 `a · b`** | 嵌套 Direct：外层门控 `a`，里层门控 `b` | **实测：0.6 × 0.8 → 48** |
| **加权平均 `(a+b)/2`** | 两个子节点写同一属性，**值摆成一半**（50），门控给出 a、b | **实测**（相加不归一化 ⇒ 系数就是那个 50） |
| 反向 `1 − a` | 同一属性上两个子节点分别写 1 与 0，权重取 `a` | 由上面的加法推得 |
| 幂 `a²` | 同一个门控套两层 | 由"嵌套相乘"推得 |
| 上下限 / 饱和 | **没人替你钳**：要么设计时让权重和 ≤ 1，要么由**写出去的那一方**钳。现在钳在三个明确的地方：① 中间层输出行那条响应曲线的关键点范围（超出按端点算）；② 约束组件里独立的那套写入器（只服务 LookAt / 眨眼 / 弹簧）；③ 会话抄回真模型时的输出集合 —— **树自己不会钳** | 实测（引擎不钳） |
| 区域/模式开关 | 子树挂在父树上，权重 = 门控参数 —— **树本身支持**，但那参数现在是**使用者自己树里的事** | 引擎行为（0.6 × 0.8 → 48 那批实测） |
| 两版映射交叉淡入 | 一棵 1D 树，两个子节点分别是"OFF 版"和"ON 版"的子树 | 参考实现的做法（我们现在的变体/副本就是这个形状） |
| **把会重叠的语义并进同一棵树** | 2D 树 + 作者摆好的组合姿势 | 实测 |
| 分段（近似） | 多阈值子节点，段内是线性插值 | 实测（1D 树语义） |
| **输出 Animator float 参数** | 叶子绑定 `type=Animator`、属性名 = 参数名；曲线值随树混合，求值后可 `GetFloat` | **两版本实测**；现有 `Compile` 白名单尚未开放 |

> ⚠️ **"乘积 / 嵌套门控"是引擎能力，但不是我们推荐的形状**：**树里的门控只做一层。**
> 原因是动态参数那条链 —— Hub 里传的是**中间层算出来的参数值**，嵌套门控的"有效值"只活在树里、**传不出来**（§2.2）。
> 要"两个开关的与"，就在**中间层**乘好再喂一棵树。
>
> 参考实现那个 `EyeSyncMix = 0.5` 现在看懂了：它把"两只眼的值"当**加法**用，而 0.5 不是为了"平均"，
> 是为了**把加法除回一半**（两边都写一半 ⇒ 得到一只眼的量）。它就是在没有归一化的前提下手工补上归一化系数。

### 8.3 不能表达什么

| 做不到 | 为什么 |
| --- | --- |
| `min(a,b)` / `max(a,b)` | 不是参数的多项式组合 |
| 除法 `a / b` | 同上 |
| 任意非线性（`sin`、`smoothstep`、软饱和曲线） | 同上；只能靠多个阈值**线性近似** |
| **纯静态姿势树自己积分弹簧/惯性** | 静态插值没有速度/位移历史；但整个 Animator 的状态机和动画片段有时间，不能说整个控制器没有状态 |
| **把同一 Controller 的 Layer 当作确定的同轮计算流水线** | 曲线可以写参数，但本轮测试中下一 Layer 到第二次求值才消费新值；复杂反馈需明确调度 |
| 精确的分段（"小于 X 就是 0"） | 只能线性近似，除非用 `Step` 那种离散档 |

**一条实用的判断法**：**把你要的映射写成一个表达式，看它是不是"参数的多项式组合 + 钳制"。**
是 → 树能做（可能要多层门控）；出现 `min`/`max`/除法/时间 → 树做不到。

### 8.4 四条"逃生口"与 2D 的实测边界

**树做不到的事，只有这四个去处**：

| 逃生口 | 能做什么 | 代价 |
| --- | --- | --- |
| **在控制器外面算**（我们的做法：中间层表达式 + 曲线，再由会话写进影子参数） | 任意 | 需要宿主能跑 C#：Unity / Warudo 可以，**VRChat 不行** |
| **Unity 原生 Animator 参数曲线** | 混合叶子曲线，产生可读的 float 参数 | 不保证同一次求值里后续 Layer 立即读取新值；不要把它当任意无延迟闭环 |
| **曲线 + 纯数据组件 + C# 读回** | 写组件字段，在求值后导出语义/属性；可再送另一个阶段 | **不必等待下一帧**：本轮已验证 A 求值→读回→B 求值可同帧完成；需要明确阶段/时钟 |
| **StateMachineBehaviour** | 在控制器内跑任意 C# | 一个状态一个行为；**我们现在的 `Compile` 明确拒绝 Behaviour** |

**2D（FreeformCartesian）的边界行为 —— 2026-09-27 已量过**（这是**处方必须遵守**的一条）：

做法：一次性工程里四棵树挂在同一个 Direct 根下（每个子节点权重 = 一个恒 1 的参数，互不干扰），
**绑 `m_LocalPosition` / `m_LocalScale` 读原始混合值**（形态键读回来可能被 Renderer 钳，不能用）：

| 树 | 形状 |
| --- | --- |
| `Cartesian4` | 矩形四角 `(0,0)=0` `(1,0)=100` `(0,1)=200` `(1,1)=300` |
| `Triangle3` | **缺一角**：`(0,0)=0` `(1,0)=100` `(0,1)=200`（`(1,1)` 故意不摆） |
| `Grid9` | 3×3 网格，坐标 `−1/0/+1`，槽值 `= 100·i + j`（**形状与正式表一致**） |
| `Switch1D` | Simple1D（阈值 0/1），**两个孩子都是子树**（分别写 0 / 100） |

| 情形 | 实测 | 结论 |
| --- | --- | --- |
| 矩形内部，**网格线上/对称中点**（`Grid9` 的 (0.5,0.5)、(0.5,0.2)、(0.5,0.75)） | 151.5 / 151.29 / 151.67 = `100×i + j` | **看起来像分段线性**（第一版据此误判成"精确双线性"） |
| 矩形内部，**离格点的非对称点** | **与手算不符**：(0.2,0.3) 实测 **129.93**（手算 121.3）、(0.4,0.5) **145.94**（141.5）、(0.75,0.5) **168.17**（176.5）、(−0.2,0.5) **72.93**（81.5）⇒ 最大偏差 ≈ **8.6**（约 6%） | **不是双线性/分段线性**：是**引擎的距离权重**（Unity 手册只说"离该点越远影响越弱"，**不给公式**）。五种候选公式（积距离 / 积倒数距离 / IDW k=1,2,4,8）**没有一个对得上** ⇒ 位置与姿势的对应关系**不能手算** |
| 矩形外低侧（x = −1.5 / −2 / −3） | **全是 1.5** = x=−1 那一列的值 | **钳到边界** |

| y 两侧、`Cartesian4` 外部 | 同样钳到边界（低侧 150 / 高侧 152；四角表 x≤0 → 100、x≥1 → 200、y≤0 → 50、y≥1 → 250） | **钳到边界** |
| **把整列往里挪**（0 / 0.4 / **0.75**） | (0.75,0.5) → 201.5、(0.8/1/1.5/3, 0.5) → **全是 201.5**；低侧 (−1/−0.5) → 1.5 | **挪点之后照样钳到位移后的那一列** ✓ |
| **挪点之后轴值 0.9 / 1.0 / 1.2** | 与 **0.75 逐位相同**：x=0.5 时 y=0.75/0.8/0.9/1.0/1.2 **全是 152**；边界也干净：y=0.70 → 1.857、y=0.75 → 2.0、再往上恒 2.0 | **钳制是逐轴的**：y 饱和后 x 照常插值 —— 顶行上 x=−1/0/0.4/0.5/0.75/0.9/1/1.5 → 2/102/142/152/177/192/202/202；**两轴都挪**时 (0.9,0.9)/(1,1)/(1.5,1.5) 全部 → **202** |

| **把一个角往里挪**到三角形**内部**（第四点 (0.75,0.75)） | (1,1) → **300**、(1.25,1.25) → 300、(2,2) → 300（钳到那个被挪的点）；(1,0.5)=220、(0.5,1)=260 | ✓ 挪单角也安全 |
| **把一个角挪到退化位置**（第四点 (0.5,0.5) 正好落在另三点构成的边上） | **非单调**：(0,0.5)=166.67 而 (−0.5,0.5)=**100**；(1.5,0.5)=100、(3,0.5)=100 | ⚠️ **别让点落在退化位置**（共线/压在别的点构成的边上） |
| **缺一格**（三点表，无中心无边中点） | (0.5,0.5)=100、(1,0.5)=**125**、(1.25,0.5)=112.5、(1.5,0.5)=100、(1,1)=150、(0.5,−0.5)=**50** | **不可预测、非单调** |
| **3×3 缺一角**（**我们的形状**：有中心、有边中点） | 见 §8.5 | **内部平滑单调、不压回原点**；但**超范围行为不再干净** |
| 权重和 | 上面每一种**和都为 1** | 权重和恒为 1（缺角时靠负权重维持） |
| 1D 树的孩子是子树 | g = 0 / .25 / .5 / .75 / 1 → `sx` = 0 / 25 / 50 / 75 / 100 | **线性交叉淡入**，与"孩子是 clip"无差别 |
| 四层嵌套（Direct → Direct → 1D → 2D） | 端点仍精确（0 与 100），无报错 | 嵌套层数不是问题 |
| **Normalize Blend Values**（Inspector 上那个复选框，手册没写） | 1D/2D：**开与关读数逐位相同**（129.9286 / 151.5 / 72.92857、超范围也是同样的 201.5）⇒ **对 1D/2D 是空操作**。Direct：**开了会真的归一化**（见下） | 我们生成的树都写 `m_NormalizedBlendValues: 0`，**别动它** |

**`Normalize Blend Values` 那个复选框**：

| 混合类型 | 复选框**关**（我们生成的树都是这个） | 复选框**开** |
| --- | --- | --- |
| 1D / 2D | —— | **空操作**：同一棵树开/关，内部点、非对称点、超范围点读数**逐位相同** |
| **Direct**（两个孩子写同一个属性，权重 0.6 / 0.8） | **加法**：`100×0.6 + 200×0.8 = 220`；两个都写 100 时 `= 140` | **归一化**：权重被除以它们的和 ⇒ `0.4286×100 + 0.5714×200 = **157.14**` |

⚠️ **这一条对我们是个陷阱**：我们的区域 Direct **权重和本来就是 N**（`MouthRegion` 下 7 个孩子 = `MouthCoreRollSwitch` /
`MouthJaw` / `MouthShift` / `MouthWidth` / `MouthTongue` / `InvertedV` / `Cheek`；其中 3 个（"张嘴 × 笑" / 整嘴平移 / 嘴宽）
挂**形态门** `Ho/Drive/Gate/MouthStyle`、其余恒 `W/One` ⇒ 权重和 = 4 + 3×门）。
**一旦有人在 Inspector 里把这个复选框勾上，孩子们会被按权重和除小 ⇒ 整个区域变淡/姿势被摊薄**（4 个恒 1 的孩子时就是各 `0.25`）。
所以：**别勾它**（生成器写 `m_NormalizedBlendValues: 0`，那就是我们要的）。
（Unity 的 IssueTracker 有一条标题是「Direct blend tree "Normalize Blend Values" does not normalize」，
但在 **6000.3.15f1 上实测它是生效的**（157.14 就是归一化的结果）—— **以实测为准**。）

### 8.5 奇数阵缺一角（3×3 少一个角）：会不会"压回原点"？

这是**我们的形状**（每张表都是奇数阵，中心点有状态），值得单独测。做法：3×3 网格（坐标 `−1/0/+1`、槽值 `100i+j`）
把 **(1,1) 那个角去掉**（8 个孩子），再把**中心那个孩子的值打成 999** —— 于是"压回原点"会直接读成 999。

| 采样点 | 满 9 格 | 缺一角（8 格） | 缺一角 + 中心打 999 | 中心权重（反推） |
| --- | ---: | ---: | ---: | ---: |
| (0,0) 中心 | 101 | 101 | **999** | 1 |
| (0.3,0.3) | 138.88 | 124.31 | 607.85 | 0.55 |
| (0.5,0.5) | 151.5 | 134.67 | 434 | 0.34 |
| (0.7,0.7) | 164.13 | 139.85 | 347.08 | 0.24 |
| (0.9,0.9) | 185.17 | 146.91 | 228.55 | 0.09 |
| **(1,1) 缺的那个角** | 202 | **151.5** | **151.5** | **0** |
| (1.1,1.1) / (1.5,1.5) | 202 | 151.5 | 151.5 | 0 |
| (1,0.5) | 201.5 | 176.25 | 176.25 | 0 |
| (0.5,1) | 152 | 126.75 | 126.75 | 0 |
| (0.5,1.5) | 152（= y 钳到 1） | **102**（≠ (0.5,1) 的 126.75） | 102 | 0 |
| (1.5,0.5) | 201.5 | 201 | 201 | 0 |
| (−1,−1) / (1,−1) / (−1,1) | 0 / 200 / 2 | 同左 | 同左 | 0 |

**结论（三条）**：

1. **不会压回原点。** 中心孩子的权重从 0.55 沿对角线**平滑衰减到 0**，在缺角那一块**正好是 0**。
   缺角处的值 = **相邻两个边孩子各半**（(1,0)=201 与 (0,1)=102 → 151.5）—— 也就是说缺的那块不是"回中性"，
   而是**塌到那条缺失边上**（= 圈被切掉一角后的**新边**）。
2. **内部平滑、单调、不越界**（124.31 → 151.5 一路递增，全部落在子节点值域内）—— 比"三点表"那种退化摆法好得多。
   **所以奇数阵少一个角，内部是可以接受的。**
3. ⚠️ **但缺角会让"圈"变小**：满 9 格时 `(0.5,1.5)` 钳到 `(0.5,1)`=126.75，缺角后是 **102** ——
   因为它被投影到**新边**的端点 `(0,1)` 上，而不是原来的矩形边界。
   ⇒ 要"圈外停在矩形边界那一格"，就得**摆满**；缺角时圈外会停在"缺口那条边"上（安全，但位置不同）。

### 8.6 统一规律 + 四条可执行的结论

> **只要"最外围孩子围成的圈"是完好的，任何参数点得到的姿势都在这个圈里面** ——
> 圈内按距离权重混合，圈外**把参数点投影到圈边上**再用那条边的两个端点线性混合。**永远不外推。**

| 点在哪 | 引擎的行为 | 实测（复盘验算） |
| --- | --- | --- |
| **圈内**（含边界） | 距离权重混合圈里所有孩子（值在圈内，但**不是分段线性**） | (0.2,0.3)=129.93、(0.5,0.5)=151.5… |
| **圈外** | ① 把点**投影到圈的边界**（最近点）② 用**那条边的两个端点**线性混合 | 三点表：(1,0.5)=**125** = 投影到 (0.75,0.25) 后 `100×0.75+200×0.25`；(1.5,0.5)=**100** = 投影正好落在 (1,0)；(0.5,−0.5)=**50** = 投影到 (0.5,0) 即 `(0,0)`/`(1,0)` 各半；(0.5,1)=**175** = 投影 (0.25,0.75)。8 格缺角：(1,0.5)=**176.25** = `201×0.75+102×0.25`、(1,1.2)=**141.6**、(0.5,1.5)=**102**（投影落在端点 (0,1)）。矩形：x=−3 与 x=−1 同值、x=3 与 x=1 同值 |
| **圈退化**（某个孩子正好落在别的孩子构成的边/线上） | 那个孩子在**圈外算不到**（圈外只用边的两个端点）⇒ **圈内外跳变** | (0,0.5)=**166.67**（圈内，算上了那个点）而 (−0.5,0.5)=**100**（圈外，只用边端点） |

**四条可执行的结论**：

1. **圈 = 语义边界，轴怎么超都只在圈里走。** 这正是"安全钳回"的机制：**你要"张满"的样子摆在圈上，超出就停在圈上**。
   把点往里挪（0/.4/.75）之后同样成立（0.9 / 1.0 / 1.2 与 0.75 逐位相同）。
   ⚠️ 上面这些数字都是**平顶矩形/规则网格探针**测的；现在那棵树**右上角单独挪过**
   （`MouthCore__Form__Open__A3X2Y2` 从 (1,0.75) 挪到 (1,0.6)）⇒ 顶边是 **0.6 ↔ 0.75 的斜线**。
   落点照样"投影到圈边 + 两端点混合"（圈仍凸、`X2Y2` 仍是顶点），但**这条斜边本身没有重新上机测过** ——
   要精确数字就得再跑一次矩阵探针。
2. **圈内**别指望手算：非对称点与分段线性差最多 ~6%（引擎的距离权重公式没文档、五种候选都拟合不上）。
   要**精确**的死区 / 半格 / 量程，只有中间层的曲线能给你（那是自己算的）。
3. **两种圈会坏**：① 孩子落在别的孩子构成的边/线上 ⇒ 圈内外**跳变**（别这么摆）；
   ② **缺角** ⇒ 圈被切掉一块，圈外那一侧的落点变成"缺口那条边的两个邻居各半"—— **安全，但形状不再是你摆的那个角**。
4. 2D 权重和**量过了：和恒为 1**（全程都是凸组合）。

> **更正（两版结论）**
> * 第一版只采网格线与对称中点，写成"内部**精确双线性**" —— 补采非对称点后**推翻**（是距离权重）。
> * 第二版说"缺角会出现**负权重**、不可预测" —— 那是从"只有 3 个孩子 + 权重和为 1"**硬解出来的一个解**
>   （`(1.5,−0.5,0)`），**不是引擎的机制**。按"投影 + 边端点"复盘，所有数字都是凸组合、**没有负权重**。

### 8.7 混合树上一共有哪些设置（别乱点的按钮）

序列化出来的树级字段只有 9 个（`BlendTree`，读自参考控制器与咱们那份资产）：

| 字段 | Inspector 上的位置 | 我们要的值 | 说明 |
| --- | --- | --- | --- |
| `m_BlendType` | **Blend Type** | `FreeformCartesian2D`（13 张表）/ `Simple1D`（5 个副本开关）/ `Direct`（根与 5 个区域） | 换类型等于换整棵树的语义，别在 Inspector 里随手改 |
| `m_BlendParameter` / `m_BlendParameterY` | **Blend Parameter**（X / Y） | 我们的轴参数 | 2D 才有 Y；写错名字 = 树永远停在一个点 |
| `m_UseAutomaticThresholds` + `m_MinThreshold` / `m_MaxThreshold` | **Automate Thresholds** + 图下方那两个数字（1D） | 现在是 `1` + 范围 `0…1` | ⚠️ **开着时 Unity 会忽略你填的阈值，在 `[min,max]` 上平均分配**。我们的开关树只有两个孩子 ⇒ 平均分就是 `0 / 1`，与我们要的一致；**要三个阈值就得先关掉它** |
| `m_NormalizedBlendValues` | **Normalize Blend Values** | **`0`，别动** | 1D/2D 空操作；**Direct 开了会把权重归一化**（我们的区域权重和是 4，会被除成 0.25） |
| `m_Childs[].m_Threshold` | 每行的 **Threshold**（1D） | 副本开关 = `0 / 1` | |
| `m_Childs[].m_Position` | 每行的 **Pos X / Pos Y**（2D） | 我们的采样坐标 | 见 §8.4–§8.6 的三条结论 |
| `m_Childs[].m_TimeScale` / `m_CycleOffset` | 每行的时钟图标 / 偏移 | `1 / 0` | 姿势片段是静态的，改这两个只会让姿势**动起来**（我们不要） |
| `m_Childs[].m_DirectBlendParameter` | 每行的 **Direct Blend Parameter**（Direct 才有） | `Ho/Drive/W/One` 或区域门 | ⚠️ **Direct 的每个子节点都必须挂一个参数**，不挂就不参与混合 |
| `m_Childs[].m_Mirror` | 每行的 **Mirror** | `0` | 只对人形 locomotion 有意义；我们是形态键/骨骼姿势，勾了等于把姿势镜像，脸会歪 |

**Inspector 上的四个动作按钮**（不是字段，点了立刻改数据）：

| 按钮 | 干什么 | 我们能用吗 |
| --- | --- | --- |
| **Compute Positions**（2D） | 从每个孩子的**根运动**里取数据来算 Pos（`Velocity XZ` / `Speed And Angular Speed` / 单轴版…） | ❌ **绝对不要点**：我们的姿势片段**没有位移**（根运动速度 = 0）⇒ 一点下去**所有孩子的位置都会被算成 0**，整棵树塌成一格 |
| **Compute Thresholds**（1D） | 同上，但改的是 1D 的阈值 | ❌ 同上（我们的阈值是语义开关 0/1） |
| **Automate Thresholds**（1D 复选框） | 在参数范围上平均分配阈值 | 🟡 现在是开的、结果正确（两孩子 ⇒ 0/1）；加第三个阈值前要关掉 |
| **Adjust Time Scale ▸ Homogeneous Speed** | 把每个孩子的 Time Scale 重新缩放成同一速度 | ❌ 与"静态姿势"无关 |

> [2D 混合](https://docs.unity3d.com/cn/6000.0/Manual/BlendTree-2DBlending.html)、
> [常用混合树选项](https://docs.unity3d.com/cn/6000.0/Manual/BlendTree-AdditionalOptions.html)。

### 8.8 判别性实验与"设计前的三个自问"

**Direct 树会不会削弱**（早先我们以为"多个通道同时给会互相削弱"，于是给每个形态键开一个独立 Override 图层 —— **这条理由是错的**）：
同一个 Direct 树只改一个变量的实测见 §8.0 的表。**结论：Direct 树本身没问题；不可用的组合是「Direct 树 + 写默认值关闭」。**
"必须 WD Off"来自早期**接管角色 Animator**的设计（那时 WD On 会把身体动画每帧复位）。
改影子求值之后这条约束过期了：影子台是隔离的、没有别的写入者，**WD On 完全无害**。

**设计前的三个自问**：

1. **我要的是"姿势"还是"值"？** 姿势 → 直接进树（含重叠语义的合并）。值要给别人用 → 看 §8.4 的逃生口。
2. **写成表达式，它是不是"参数的多项式组合 + 钳制"？** 是 → 树能做；否（`min`/`max`/除法/时间）→ 外面算。
3. **需要同帧串联或反馈吗？** 不需要时可以直接使用原生参数曲线/属性输出；需要时定义阶段、时钟与反馈缓冲，
   不用"多 Update 几次"作为通用语义。

## 9. 两个正面例子

### 9.1 会重叠的语义要并进同一棵树

ARKit 的 `eyeBlink` 与 `eyeSquint` 在模型上闭的是同一块，裸输入里两者同时非 0 → 同一个形变被写两遍 → 过眨眼。
参考实现的解法**不是**在参数上做抑制，而是：**把这三个键写进同一批姿势，用一棵 2D 树插值**（实测五个片段的内容）：

| 姿势 | blink | squint | wide |
| --- | --- | --- | --- |
| 睁大 | 0 | 0 | **100** |
| 中性 | 0 | 0 | 0 |
| 闭 | **100** | 0 | 0 |
| **眯** | **90** | **100** | 0 |
| 睁大+眯 | 0 | 0 | **100** |

关键在**「眯」那格自带 blink 90**：两个轴走到哪就是哪个姿势，**权重和恒为 1，不可能相加**。
这也解释了"为什么眼睑是 2D 而嘴是 1D"——不是好看，是必须。
（实测有效：眼睑改成 2D 子树后，`blink` 与 `squint` 的加和最多 **~110**（原来是 **200**）—— 因为**权重和恒为 1**。）

### 9.2 一张 3D 需求 → 张量积门

见 §1.1：**Unity 只有 1D / 2D / Direct，没有 3D 表** ⇒ 三维用 `gate = w情绪 × w闭合` 表达，
两边各自归一化 ⇒ **Σ门 = 1×1 = 1**。**归一化是除法（非线性）⇒ 必须留在中间层，树只负责插值。**

**降维有损**（一条硬边界）：压成两根轴是有损的 —— `开合 = blink − wide` 让 `wide=0.5` 与 `blink=0.5` 落在同一个点。
而且**压轴是参数算术，必须在树外面做**。

**三条硬边界**（把重叠语义并进一棵树这件处方的适用范围）：

| | 边界 | 说明 |
| --- | --- | --- |
| **① 维数** | **只有 2 维能用** | Unity 的混合树只有 1D / **2D**，没有 3D。两个会重叠的通道 → 2D 树 ✓；三个以上 → 树上表达不了 |
| **② 降维有损** | 压成两根轴是有损的 | 见上；而且压轴必须在树外做 |
| **③ 没摆的角没有定义** | 圈外的点**投影到圈边、再用那条边的两个端点混合**（凸组合，**不外推**） | ⇒ **缺角是安全的**，只是"圈"被切掉一块。真正会**跳变**的是"孩子落在别的孩子构成的边/线上" |

**准确的表述**：通用的是**处方**（会重叠的语义并进同一棵树 + 为每个能到达的组合摆姿势）；
不通用的是**维数**（超过两根轴就得先降维，而降维有损、且必须在树外做）。

**找反例（拿别人的控制器复核）**：有没有非多项式的运算（`min`/`max`/除法）→ **没有**（`Limit` 链全是"按参数交叉淡入到空动画"，仍是分段线性）；
是否依赖引擎钳制 → **不依赖**（510 个 `.anim` 里一个 >100 的都没有）；怎么产生参数 → 参考资产使用 Animator 参数曲线，
**不能据此归因为 VRChat 独有能力**（原生 Unity 同类绑定已实测成立）。
