## 1. 为什么要有它

`AnimatorController` 只是**动画资产控制器**：它吃参数、吐**动画姿态**。它天生**没有"参数输出"**，
所以"控制器 A 的输出喂给控制器 B"在 Unity 里没有现成机制。

解法不是把控制器改成万能角色控制器，而是给它加一条**很薄的第二输出**：

```
Face Capture → Animator Controller ─┬─→ 动画姿态（形态键 / 骨骼）
                                    └─→ 语义参数（Dynamic Parameter Hub）
```

于是：

* **控制器只干动画**（形状、骨骼，将来也许材质）；
* **语义值走 Hub**，任何脚本 / 材质 / 蓝图读 Hub 就够；
* 换面捕方案（ARKit → 手机 → 手动 → 另一个控制器）时，**消费方一行都不用改**。

## 2. 四个角色，各管一件事

| 角色 | 是什么 | 负责 |
|---|---|---|
| `HoFaceSemanticHub`（**值 + 名字**） | MonoBehaviour，挂在角色 mod 的一个空物体上 | **这一帧是多少**：`float[] values` + `string[] names`。**槽是写的人运行期开的**（`ClaimSlot(name)`）⇒ 没有长度政策、没有下标约定 |
| `HoFaceSemanticConnector`（**给人看的表**） | MonoBehaviour，挂同一个物体（或任何方便编排的地方），并**直接引用**那个 Hub | **这些名字是什么意思**：槽表（`key` / `note`）+ **顺序即下标**。它也是消费方的入口 |
| `HoFaceSemanticWriterBehaviour`（**写手**） | **状态机行为**，挂在控制器的状态上 | **控制器里的中间值怎么出来**：按表达式从 Animator 参数算出来，按**名字**开槽写进 Hub（§5） |
| 消费方 | 作者的脚本 / 材质控制 / 蓝图 | 填 **Connector**，按名字读（`connector.GetFloat("MouthOpen")`） |

**为什么值和表要分在两个组件上**：
① **bundle 里的那份 Hub 不能带表** —— 控制器在 bundle 里跑，bundle 里放不了我们自己写的组件类型，
给控制器用的是一份**代理 Hub**；表要是长在 Hub 上，代理那份就得带一张"假表"，两边迟早对不上；
② 表和值分开之后，**值可以随便清零、表可以慢慢改**（改名字不动值，清值不动名字）；
③ 消费方**只需要一个引用**（Connector 自己指向 Hub）。

**为什么值是 `float[]` 而不是一堆 `public float MouthX`**：三个理由缺一不可 ——
① 运行期读**不能反射**（UMod 禁 `System.Reflection`），字段名读不出来、下标可以；
② 语义表是**每个角色自己定义的**、不是编译期固定的集合 ⇒ 字段名没法在编译期写出来；
③ 加一个语义 = 控制器里多声明一个名字，**两边代码一行不动**。

### 2.1 为什么**不再有**那个 ScriptableObject 资产（2026-09-26 用户定）

原来还有第三个类型 `HoFaceSemanticAsset`（词表放资产、值放 Hub）。删掉它的理由**是实测的**：

* 资产那半边**从来没有过消费者**：`IndexOf / KeyAt / NeutralAt / BuildKeySnapshot / FillNeutral`
  的外部调用点 **0 个**；`HoFaceSemanticHub.GetFloat(string) / SetFloat(string) / ResetToNeutral()`
  的外部调用点也是 **0 个**；`AlignToAsset()` 只有写动态参数节点那一处。
* 资产存在的**公开理由也不成立**："bundle 里放不了组件类型 ⇒ 名字必须放在双方都能引用的东西上"
  —— 可 bundle 里那份 Hub **本来就没有资产**，控制器从头到尾**按下标**读。
* 用户定：**不做跨角色共享词表**（N 个角色 = N 份表拷贝，这是有意的，不是缺陷）。

⇒ 词表变成**组件上的槽表**：少一个文件、少一步"预制件挂资产引用"。
⚠️ **中性值不在表里**：中性 = `0`，是**静态规则**（`Connector.ApplyNeutral()` 就是 `hub.Zero()`）。
`0.5` 那种"中立位"是 VBridger 私有的约定，我们**不采用**（[HO 参数规范](PARAMETER_HO.md) §2）。

## 3. 命名前缀：只给"生成预制动画"那一步用

控制器生成器（把参数定义编译成混合树 + 叶子 Clip）需要知道**每个槽该写哪里**。用名字前缀表达：

```
SK/xxx   → SkinnedMeshRenderer 的 BlendShape
BT/xxx   → Bone / Transform 动画
P/xxx    → 动态参数（写进 Hub）
```

例：`SK/MouthSmile`、`BT/Jaw`、`P/MouthX`。

**⚠️ 前缀只存在于生成 IR / 参数定义里，生成完的控制器不需要知道它。**
这条很重要，而且它跟我们既有的另一条规矩是同一条：

> **解释控制器结果时绝不看名字。**

我们的驱动路径（喂参数 → 跑影子 → 采结果）**本来就是按结构走的**：骨骼按 `HumanBodyBones` 枚举、
形状按网格上的 `GetBlendShapeName(i)` 枚举。名字只在**生成**那一步参与。

⚠️ **一处例外要说清**：形状采集是"按名字"取权重的（下标来自 `mesh.GetBlendShapeName(i)`）。
但那是**网格上的形状名**，与"控制器参数名的前缀"完全是两回事 —— 前者是 Unity 的绑定机制，后者只是生成期的协议。

## 4. 落点约定

* **Hub 与 Connector 都挂在同一个空物体上**（不是塞进角色模型层级里），例如 `Character/SemanticHub`。
* **写手挂在控制器的状态上**（`Add Behaviour`），不是挂在物体上。
* **两边不需要约定顺序**：写手按**名字**开槽（`ClaimSlot`），采样时按名字报键，节点再拿角色的
  **槽表**按名字解释 ⇒ 表重排**不会**让任何东西静默错位（对不上名字会在节点 `状态` 里被点名）。
* 消费方填 **Connector**，运行时按名字解析一次下标、之后按下标读 `GetFloat(int)`。
* **表长在预制件上**：N 个角色 = N 份拷贝（有意的）。改一处不影响别的角色。

### 4.1 "槽位预留多少"这个问题**不存在了**（2026-09-26）

以前 Hub 预留固定 128 个槽，是因为**动画曲线**要写 `values.<i>`：绑定是静态字符串，
**越界写不报错、值就是不动**，而且运行期枚举不了控制器的曲线绑定（`AnimationUtility` 是编辑器专属）
⇒ 长度必须在打包前猜对。当时在三个候选政策（硬编码常量 / 可见字段 / 编辑期从曲线推真值）之间悬着。

改成**状态机行为**（代码）之后：槽数 = 控制器实际声明过的名字数，写手自己 `ClaimSlot`。
⇒ **没有魔法数字、没有长度政策、也没有"作者必须预先知道下标"**。
Hub 的 `values` / `names` 出厂就是**空数组**（`Reserve(count)` 只增不减，给"按下标写"的节点用）。

## 5. 控制器怎么把值写进 Hub：**语义写手**（状态机行为）

作者在控制器的一个状态上 `Add Behaviour` → `HoFace Semantic Writer Behaviour`，填一张小表：

| 字段 | 意思 |
|---|---|
| `slot` | 语义名（写进 Hub 的名字表；要和角色的 Connector 槽表对得上） |
| `expression` | 值怎么算：变量就是**这个控制器的 Animator 参数名**（float / int / bool；别的类型当 0） |

例：`slot = MouthX`、`expression = jawOpen * 0.5 + smile * 0.5`。
表达式语言就是中间层那一套（[面捕中间层处理](FACE_TRACKING_MIDDLE_LAYER.md) §5.1，
`HoFaceExpression`：函数表 / 惰性 `if` / 非有限折 0）；波浪类函数按帧推进（它内部读 `HoFaceExpression.Frame`）。

**为什么是代码不是曲线**（这才是这一节的重点，四条一起消失）：

| 曲线写数组元素 | 语义写手 |
|---|---|
| 绑定是静态字符串 ⇒ **作者必须先知道下标** | 按名字，**不用知道下标** |
| Animation 窗口里数组元素是 `Element 0..N`（**没有名字**） | 在状态的 Inspector 里填 `名字 + 表达式` |
| 表重排 ⇒ 旧曲线**静默写错槽** | 表重排无所谓（按名字走） |
| 长度要在打包前猜对（越界写静默无效） | 槽由写手当场开，**没有长度** |

生态里也是这么做的：ChilloutVR 的 [`Animator Driver` 状态机行为](https://docs.chilloutvr.net/cck/state-behaviours/animator-driver/)
就是"在状态机里驱动 Animator 参数"的同一思路。

**时机**：`OnStateEnter` + `OnStateUpdate`（状态激活期间每帧）。
**状态退出时不清零** —— 和 Unity 动画的语义一致（没人再写就保持最后的值）；"丢脸清中性"由下游那条链负责。

### 5.1 曲线那条路：**不再是主线**，但留了实测记录

`values.<i>` 那条路（动画曲线直接写 Hub 的数组元素）现在**不用了**，理由见上表。
它当年是**推断**而不是实测：能力表里测过的是脚本 `float`/`bool`/`int`、`Vector`/`Color` 分量、
开关、材质、对象引用，**没有"数组元素"这一行**；而数组元素的 SerializedProperty 路径通常是
`values.Array.data[i]`，与注释里写的 `values.<i>` 是两个不同的字符串。

`Tests~/FaceTrackingValidation.cs` 的 `stage 17-20` 仍然把这三种情况跑一遍并**只报告不断言**
（`HO_HUB_PATH` / `HO_HUB_PROBE` / `HO_HUB_VERDICT`）：万一以后想拿曲线当备选，答案就在日志里。

### 5.2 ⚠️ 运行期**还没验**的两条（SMB 方案的地基）

1. **`OnStateUpdate` 在手动 `Animator.Update()` 求值时会不会被调用** —— 我们两边（Unity 影子台、
   Warudo 的 `HoFaceController`）都是手动推 Animator 的，所以这条不成立的话整个方案不成立。
   批处理用例 `stage 20-21` 就是测它：状态上挂写手、`P/A = 0.6` ⇒ 断言 Hub 里出现
   `MouthX = 0.6` / `MouthY = 1.2`（外加一条标记物曲线当对照组）。**还没跑过**（本机 Unity 编辑器占着）。
2. **bundle 里的控制器能不能解析到写手这个类型** —— 和"bundle 里的 Hub"是同一类依赖
   （我们程序集里要有这个类型，mod 侧靠同步的那 11 份），但这套东西**从来没在 Warudo 里跑过**。

### 5.3 写手现在**读不到姿态**（明确记着）

写手的变量只有 **Animator 参数**。所以"中间值"要么本来就是参数、要么**用表达式从参数算出来**。
想读**姿态**（某个形态键的权重 / 某根骨头的旋转）现在**没做** —— 那要给每个条目再加一个"源"描述
（渲染器引用 + 形态键名，或者骨骼 + 轴），等真有需求再加。
⚠️ 但注意：**姿态本来就能被采出来**（我们的求解节点已经在采形态键与骨骼了），
所以"读姿态"这件事不一定需要经过 Hub。

### 5.4 但 Hub 不是全部：完整输出还有别的类

[控制器完整输出](ANIMATOR_OUTPUT_PIPELINE_DESIGN.md) §6 定了更完整的一份"求值帧"，Hub 只是其中
**`signals`（导出语义）**那一格。其余（`properties`：显隐 / 组件 float / 材质 MPB / 对象引用）
按那份文档的**批量应用节点**走，**不要**都塞进 Hub —— 那会把 Hub 变成一个万能写入口，
正是那份文档 §7 结尾警告的事（"物理调度不能隐含在一个名字叫「写组件值」的 node 里"）。

**所以本文件只负责 `P/` 这一类（语义信号）；显隐/材质/引用那些看那份文档。**

## 6. 我们**不做**的事

* ❌ **不写组件值 / 材质值**（原先规划里那一条）。理由：它们的**能力上限取决于我们能不能读回来**，
  而读回来要么反射（禁）、要么需要一个能被动画的已知类型 —— 成本远高于收益。
  语义值走 Hub 已经覆盖了"下游要读"这件事。
* ❌ **不让控制器的语义依赖名字**（"解释结果时不看名字"）—— 名字只进生成器与写手这张小表。
* ❌ **不提前扩展前缀**（`M/` 材质、`C/` 组件这些），三个够用。
* ❌ **不做跨角色共享词表**（2026-09-26 定）：表跟着预制件走，一个角色一份。
* ❌ **不用动画曲线写 Hub**（2026-09-26 定）：原因是"作者必须先知道下标"那一串问题，见 §5。
* ❌ **不让 Connector 去改 Hub 的数组长度**（组件之间不耦合；长度是写手按名字开的）。

## 7. 与既有设计的关系

* 这三个类型是**新挂在角色 / 控制器上的** ⇒ 与"角色预制件零组件"那条老规矩**冲突**：
  那是**调试状态**的规矩（调试状态在 `Assets/HoFaceDebugSettings.json`，不进预制件），
  而 Hub / Connector / 写手是**产品内容**、本来就必须在角色或控制器上。用户 2026-09-25 确认
  "可以接受角色 mod 制作时挂新脚本"（而且**带自定义脚本的角色 mod 打包这条路早就跑通了**），
  所以老规矩按"只约束调试状态"重新表述，不是被推翻。
* 求解节点目前的出口不变（官方同形的 5 个 + `状态`），**`P/` 语义值先作为新的一个出口**，
  不替换既有四个 —— 等作者的控制器做出来之后再评估要不要并。
  这与 [控制器完整输出](ANIMATOR_OUTPUT_PIPELINE_DESIGN.md) §6 的"保留现有五个 + 新增一份完整求值帧"**是同一个决定**：
  旧出口是同一帧结果的投影，**不各自重复求值**。
