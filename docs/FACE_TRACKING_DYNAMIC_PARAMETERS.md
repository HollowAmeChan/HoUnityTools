## 1. 为什么要有它

`AnimatorController` 只是**动画资产控制器**：它吃参数、吐**动画姿态**。它天生**没有"参数输出"**，
所以"控制器 A 的输出喂给控制器 B"在 Unity 里没有现成机制。

解法不是把控制器改成万能角色控制器，而是给它加一条**很薄的第二输出**：

```
Face Capture → 中间层（*.hoface.json：输入行 / 曲线 / 输出行）
                 ├─→ 控制器参数 → Animator Controller → 动画姿态（形态键 / 骨骼）
                 └─→ 动态参数（**同一份字典**）→ Dynamic Parameter Hub
```

于是：

* **控制器只干动画**（形状、骨骼，将来也许材质）；
* **动态参数由中间层算完顺手写进 Hub**，任何脚本 / 材质 / 蓝图读 Hub 就够；
* 换面捕方案（ARKit → 手机 → 手动 → 另一个控制器）时，**消费方一行都不用改**。

⚠️ 注意上图那条"中间层"的分叉：**Hub 里的东西不是控制器吐出来的，是中间层算出来的那份参数**
（Unity 侧会话算完写，Warudo 侧「HoFace写动态参数」节点算完写）。这是 2026-09-26 清理
「语义写手」之后的形状，理由见 §5。

## 2. 三个角色，各管一件事

| 角色 | 是什么 | 负责 |
|---|---|---|
| `HoFaceSemanticHub`（**值 + 名字**） | MonoBehaviour，挂在角色 mod 的一个空物体上 | **这一帧是多少**：`float[] values` + `string[] names`。**槽是写的人运行期开的**（`ClaimSlot(name)`）⇒ 没有长度政策、没有下标约定、**名字也只活在运行期** |
| `HoFaceSemanticConnector`（**挂出去的那个把手**） | MonoBehaviour，挂同一个物体（或任何方便编排的地方），并**直接引用**那个 Hub | **消费方的唯一入口**：`GetFloat(名字)` / `SetFloat(名字, 值)`。**它没有表、没有配置**（2026-09-26 删） |
| **写的人 = 中间层** | Unity 侧：调试会话（`HoFaceAnimationSession.PublishSemantics`）；Warudo 侧：「HoFace写动态参数」节点（`HoFaceHubWriteNode`） | **把算出来的参数按名字写进 Hub**。名字就是配置文件里输出行的 `parameter`（§5） |
| 消费方 | 作者的脚本 / 材质控制 / 蓝图 | 填 **Connector**，按名字读（`connector.GetFloat("MouthOpen")`）—— **先跑一遍看 Hub 里有什么名字，或者两边事先约定** |

⚠️ **Hub 不限制写者 —— 它是一片"脚本写的工作台"。**（2026-09-26 用户纠正过一次：
别把它说成"只有中间层能写"）我们的中间层是**我们的**写者（上面那一行那两条入口）；
作者自己挂在角色上的组件、别的 mod 的脚本，同样可以 `ClaimSlot` + `SetFloat` 按名字写进来 ——
`HoFaceSemanticConnector.SetFloat` 就是给这个用的。
**唯一写不进去的是动画 clip**：曲线写 `values.<i>` 那条路 2026-09-26 删了（§5.1）。
换句话说，"Hub 里能有什么"是**产品边界**（我们提供中间层这一条），不是**机制边界**。

**为什么"值"和"接口"要分成两个组件**：
① 值可以随便清零、接口可以随时换；
② 消费方**只需要一个引用**（Connector 自己指向 Hub），换面捕方案时它一行都不用改；
③ 名字的**定义权**留在写的人手上（谁写谁声明），Connector 因此只是个把手 —— 而不是一张需要维护的表。

**为什么值是 `float[]` 而不是一堆 `public float MouthX`**：三个理由缺一不可 ——
① 运行期读**不能反射**（UMod 禁 `System.Reflection`），字段名读不出来、下标可以；
② 参数集合是**每份配置自己定义的**、不是编译期固定的 ⇒ 字段名没法在编译期写出来；
③ 加一个参数 = 中间层多一行输出，**两边代码一行不动**。

### 2.1 为什么**不再有**那个 ScriptableObject 资产，也不再有一张"槽表"（2026-09-26 用户定）

原来还有第三个类型 `HoFaceSemanticAsset`（词表放资产、值放 Hub）。删掉它的理由**是实测的**：

* 资产那半边**从来没有过消费者**：`IndexOf / KeyAt / NeutralAt / BuildKeySnapshot / FillNeutral`
  的外部调用点 **0 个**；`HoFaceSemanticHub.GetFloat(string) / SetFloat(string) / ResetToNeutral()`
  的外部调用点也是 **0 个**；`AlignToAsset()` 只有写动态参数节点那一处。
* 资产存在的**公开理由也不成立**："bundle 里放不了组件类型 ⇒ 名字必须放在双方都能引用的东西上"
  —— 可 bundle 里那份 Hub **本来就没有资产**，控制器从头到尾**按下标**读。
* 用户定：**不做跨角色共享词表**（N 个角色 = N 份拷贝，这是有意的，不是缺陷）。

那之后我把词表放到了 Connector 上（一张 `key`/`note` 的表），**2026-09-26 又删了**，理由：

* 名字**本来就由写的人在运行期声明**（`ClaimSlot`），长在 Hub 的 `names` 上 —— 表里再写一遍就是**第二份真相**；
* 有了表，节点就要拿它**寻址**（名字 → 下标），于是 Connector 变成"注册表"，**不再像个接口**（用户原话：
  "connector 现在变得不像一个连接器了，他本来的职责应该是把动态参数挂出去用的"）；
* 用户定的用法是：**"名字都不用列，先跑一遍运行看里面有啥，或者约定好名字用"**。

⚠️ **代价要认**：表同时还兼着"**名字对不上**"的校验点。删掉之后，配置里把 `MouthX` 敲成 `Mouthx` 时，
那条值会**安静地**落到另一个槽（`Mouthx`），而读 `MouthX` 的人只会拿到 0。
现在发现它的办法只有两条：**跑一遍看 Hub 里的名字**（或面板的「参数输出」栏），
或者看节点/会话状态里那行 **新声明**（新开出来的名字会点名）。
⚠️ **中性值从来不在表里**：中性 = `0`，是**静态规则**（想清就 `hub.Zero()`）。
`0.5` 那种"中立位"是 VBridger 私有的约定，我们**不采用**（[HO 参数规范](PARAMETER_HO.md) §2）。

## 3. 命名前缀：只给"生成预制动画"那一步用

控制器生成器（把参数定义编译成混合树 + 叶子 Clip）需要知道**每个槽该写哪里**。用名字前缀表达：

```
SK/xxx   → SkinnedMeshRenderer 的 BlendShape
BT/xxx   → Bone / Transform 动画
P/xxx    → 动态参数（写进 Hub）
```

例：`SK/MouthSmile`、`BT/Jaw`、`P/MouthX`。

**⚠️ 前缀只存在于生成 IR / 参数定义里，生成完的控制器不需要知道它。**
这条很重要，而且它跟我们既有的另一条规矩是同一条：

> **解释控制器结果时绝不看名字。**

我们的驱动路径（喂参数 → 跑影子 → 采结果）**本来就是按结构走的**：骨骼按 `HumanBodyBones` 枚举、
形状按网格上的 `GetBlendShapeName(i)` 枚举。名字只在**生成**与**中间层**那两步参与。

⚠️ **一处例外要说清**：形状采集是"按名字"取权重的（下标来自 `mesh.GetBlendShapeName(i)`）。
但那是**网格上的形状名**，与"控制器参数名的前缀"完全是两回事 —— 前者是 Unity 的绑定机制，后者只是生成期的协议。

## 4. 落点约定

* **Hub 与 Connector 都挂在同一个空物体上**（不是塞进角色模型层级里），例如 `Character/SemanticHub`。
* **写的人是中间层，不是控制器**：Unity 侧不需要任何人在控制器上 `Add Behaviour`；
  Warudo 侧不需要把求解节点接到角色上（那是「HoFace写动态参数」节点的事）。
* **两边不需要约定顺序，也不需要一张表**：写的人按**名字**开槽（`ClaimSlot`）并写下名字
  ⇒ 顺序完全由"谁先声明"决定，没有任何东西会因为重排而错位。
* 消费方填 **Connector**：`GetFloat("名字")`（每帧都要读同一个名字的话，自己缓存一次下标更省）。
  **想知道有哪些名字：跑一遍看 Hub（面板/Inspector），或者两边事先约定。**
* **没有跨角色共享的词表**：名字由**每份配置的输出行**决定，一个角色一份。改一处不影响别的角色。

### 4.1 "槽位预留多少"这个问题**不存在了**（2026-09-26）

以前 Hub 预留固定 128 个槽，是因为**动画曲线**要写 `values.<i>`：绑定是静态字符串，
**越界写不报错、值就是不动**，而且运行期枚举不了控制器的曲线绑定（`AnimationUtility` 是编辑器专属）
⇒ 长度必须在打包前猜对。当时在三个候选政策（硬编码常量 / 可见字段 / 编辑期从曲线推真值）之间悬着。

后来改成**状态机行为**（代码）时，长度问题就已经消失了（槽数 = 控制器实际声明过的名字数）；
**再后来连状态机行为也删了**：槽数 = **中间层输出行的行数**，写的人自己 `ClaimSlot`。
⇒ **没有魔法数字、没有长度政策、也没有"作者必须预先知道下标"**。
Hub 的 `values` / `names` 出厂就是**空数组**；`Reserve(count)`（给老式 `#下标` 那条路用的）
2026-09-26 跟着一起删了。

## 5. 中间层怎么把值写进 Hub（2026-09-26 定的形状）

**两条写入口，写的是同一份东西**：

| 谁 | 怎么写 | 名字从哪来 |
|---|---|---|
| **Unity 侧**：调试会话 | **可选开关**（调试设置里的 `writeParameterHub`，**默认关**）：打开后每帧算完输出行就 `hub.ClaimSlot(parameter)` + `hub.SetFloat(index, value)` | 配置文件里**输出行的 `parameter`** |
| **Warudo 侧**：「HoFace写动态参数」节点 | 每帧把 `参数处理.参数`（或「Ho合并字典」的 `字典`）按名字写进角色 Hub | 同一份字典的**键** |

⚠️ **Unity 侧默认关**（2026-09-26 用户定）：Hub 是"把值挂出去给**别的**脚本 / 材质 / 蓝图读"的出口，
**调试台自己不需要它** —— 面板的「参数输出」栏看的就是同一份值；Warudo 侧也不靠它。
所以默认不往外写东西，需要时在面板「对象」段把「写动态参数 Hub」打开（下一帧生效）。

写的是**全部输出行**（不按"控制器里有没有这个参数"过滤）—— 面板的「参数输出」栏摊开的就是这一份，
所以"面板里看到什么 = Warudo 里是什么"这条规矩在动态参数上也成立。
（Unity 侧调试滑条 `SetPreview` 盖掉同名行时，Hub 里也跟着是那个值 —— 它驱的是影子那棵树。）

### 5.1 走错的两条路（留档，别再走回去）

**① 动画曲线直接写 `values.<i>`（2026-09-26 上午废弃）。** 绑定是静态字符串：

| 曲线写数组元素 | 现在（中间层写） |
|---|---|
| 绑定是静态字符串 ⇒ **作者必须先知道下标** | 按名字，**不用知道下标** |
| Animation 窗口里数组元素是 `Element 0..N`（**没有名字**） | 名字就是输出行的 `parameter` |
| 顺序一变 ⇒ 旧曲线**静默写错槽** | 顺序无所谓（谁先写谁在前） |
| 长度要在打包前猜对（越界写静默无效） | 槽由写的人当场开，**没有长度** |

它当年还只是**推断**而不是实测：能力表里测过的是脚本 `float`/`bool`/`int`、`Vector`/`Color` 分量、
开关、材质、对象引用，**没有"数组元素"这一行**；而数组元素的 SerializedProperty 路径通常是
`values.Array.data[i]`，与注释里写的 `values.<i>` 是两个不同的字符串。那条路**已经不在代码里**了
（`Tests~` 里原来那两组探针也一起删了），所以"到底哪个字符串能写"这个问题不再有人回答 ——
要走回去就得重新测。

**② 控制器状态上的「语义写手」（`StateMachineBehaviour`，同一天下午废弃）。**
它解决的是曲线那条路的下标问题：`Add Behaviour` → 填 `{slot, expression}`，变量是这个控制器的
Animator 参数，`OnStateEnter` / `OnStateUpdate` 按名字写进**影子** Hub，再由会话/节点中转到角色 Hub。
**为什么连它也删了**：

* 那些值**中间层本来就算得出来**（它就是写参数的那个人）—— 让控制器再算一遍 = **两份真相**；
* 它是一个**只在 bundle 里跑、编辑器里看不见**的写者：出问题时"面板里对、Warudo 里不对"这类
  最难查的现象就多一个来源；
* 它带来的每一件麻烦（影子 Hub、中继、`ValidateMachine` 的"只放过某一个"例外、
  "bundle 能不能解析到这个类型"这条没验的依赖、`P/A` 探针）都只为它服务；
* 想读姿态（它唯一有理由做的事）**现在也没做**，见 §5.4。

**结论**：**我们**的写者只有一个（中间层），而且它**不在控制器里**；出口只有一个（Hub）——
但 Hub 自己是谁都能写的（§2 那条"脚本写的工作台"），只是 **clip 写不了它**。

### 5.2 现场实测记录（2026-09-26）+ ⚠️ 现在的形状**要重跑一遍**

**✅ 当时实测通的**是"写手"那条链（现已删除）：土豆角色 + `PTP_CTR_Face_ARKit` + `ho-iPhoneVTS`，
控制器基座层默认状态上挂写手（10 条语义），会话每帧 `shadow.Update(0f)` ⇒ 影子 Hub 按名字开槽
⇒ 中继写到**角色那片 Hub**。证据有两条：

* 面板「参数输出」栏逐行显示中间层的求值结果（`N 行 · 非零 M · 不在控制器里 K`）；
* 角色 `面捕动态参数` 的 Hub 里 10 个槽**都带着名字与实时值**
  （`jawOpen=0.032 · mouthRound=0.559 · LidLeft=0.242 …`）。

⚠️ **那次跑通的是"写手 → 影子 Hub → 中继"三段；现在只剩"中间层 → 角色 Hub"一段**，
所以**要重新跑一遍现场**（Hub 里有名字与实时值 = 通过）。机器化的回归门是批处理用例
`Tests~/FaceTrackingValidation.cs` 的 `stage 18`：会话算完一帧后断言角色 Hub 上
**槽数 = 输出行数**、且 `ARKit/jawOpen` ≈ 0.6（`HO_HUB_PUBLISH` 那一行是它的读数）。

⚠️ 当时顺手暴露的两个**我们自己挖的坑**（都已修，记着别再犯）：

1. `HoFaceAnimationAssets.ValidateMachine` 原来"控制器里**任何** StateMachineBehaviour 都一票否决"
   ⇒ 挂上写手的控制器会让会话**起不来**，表现是"脸不动、Hub 空"，而报错只是一条容易被略过的红框。
   **现在又回到"任何 Behaviour 都拒绝"**（写手删了，不再需要例外）；改代码后**一定要让 Unity 重编译**
   —— 现场第一次报"毫无变化"，就是因为修复还没进编译。
2. 面板原来**看不到中间层的输出值**（只有"参数输入"那一栏的裸线名）⇒ 分不清"配置没算出值"和
   "算出来了但写不进去"。现在「参数输出」栏逐行摊开，并把**参数不在控制器里**的行单独标出。

**⚠️ 还剩没验的**：**Warudo 侧的连线与面板**（节点 → 角色 Hub 真的写进去了没有）。
Unity 侧的现场与批处理用例都测不到 Warudo 的节点行为 —— 那是跨仓验证项
（[仓库与提交](pitfalls/REPO_AND_GIT.md) §7）。

### 5.3 Hub 不是"控制器的中间值"了，那"控制器内部才有的量"怎么办

写手当年存在的理由是"控制器内部才有的量（读姿态 / 取决于当前状态的值）中间层看不到"。
现在这条需求**没有被实现**，也**没有借口用 Hub 兜** —— 但要把话说准：**不是"Hub 写不了"**，
而是"**我们不再提供跑在控制器里的写者，clip 也写不了 Hub**"。想要的人可以自己写一个组件
（读 Animator 参数 / 姿态，算完按名字写 Hub）—— 那正是"脚本工作台"允许的事，只是不在我们的产品范围内：

* **姿态**（形态键权重 / 骨骼旋转）**本来就能采**：求解节点一直在采（`HoFaceController.BlendShapes` /
  `BoneRotations`），只是它采的是"控制器算出来的姿态"，而不是"喂回去的参数"。
  真要"按姿态再产出一个参数"，正确的位置是**中间层再来一遍**（它已经能读输入行与通道），
  而不是往控制器里塞写者。
* **作者根本不用我们的中间层**（自己画树、自己管参数）时，我们这条链**不适用** ——
  这正是"我们的写者只有中间层"的代价，认了（用户 2026-09-26 的选择：**中间层全部算完，顺手输出到 Hub**）。
  那种场景下作者自己的脚本照样能写 Hub，我们只是不替他算。
* **取决于当前状态 / 层权重的值**：Warudo 侧另有官方的 `Get Animator …` / `Get Character …` 节点族，
  Unity 侧有脚本 —— 不该由这条链承担。

#### ⚠️ 唯一真会撞上的那条：**树里的"有效门控"**

"控制器内部才有的量"里，实际只有一件事会撞上来：**混合树里乘出来的有效门控**。
一层门控（一个区域一个参数）时"有效门控 = 那个参数"，Hub 里传的就是真值、下游不用重算；
**嵌套 / 乘法分叉**时有效值只活在树里 —— 我们的两条入口（中间层 / clip）都交不出来，
要就得自己写个组件去读参数、算完写 Hub。
所以定了一条边界：**树 gate 只做一层**；要"两个开关的与"就在**中间层**乘好，作为一行输出喂进树。
完整论述与现在这份控制器的形状见
[控制器结构](FACE_TRACKING_CONTROLLER_STRUCTURE.md) §3.3；引擎能力本身见
[混合树能力边界](BLEND_TREE_LIMITS.md) §2 与 [踩过的坑 · 混合树](pitfalls/BLEND_TREE_TRAPS.md) §3。

### 5.4 但 Hub 不是全部：完整输出还有别的类

[控制器完整输出](ANIMATOR_OUTPUT_PIPELINE_DESIGN.md) §6 定了更完整的一份"求值帧"，Hub 只是其中
**`signals`（导出语义）**那一格。其余（`properties`：显隐 / 组件 float / 材质 MPB / 对象引用）
按那份文档的**批量应用节点**走，**不要**都塞进 Hub —— 那会把 Hub 变成一个万能写入口，
正是那份文档 §7 结尾警告的事（"物理调度不能隐含在一个名字叫「写组件值」的 node 里"）。

**所以本文件只负责 `P/` 这一类（语义信号）；显隐/材质/引用那些看那份文档。**

## 6. 我们**不做**的事

* ❌ **不写组件值 / 材质值**（原先规划里那一条）。理由：它们的**能力上限取决于我们能不能读回来**，
  而读回来要么反射（禁）、要么需要一个能被动画的已知类型 —— 成本远高于收益。
  语义值走 Hub 已经覆盖了"下游要读"这件事。
* ❌ **不让控制器碰动态参数**（2026-09-26 定）：控制器里不放任何 `StateMachineBehaviour`，
  也不绑任何写 Hub 的曲线。"解释控制器结果时不看名字"这条老规矩因此还是干净的。
* ❌ **不提前扩展前缀**（`M/` 材质、`C/` 组件这些），三个够用。
* ❌ **不做跨角色共享词表**（2026-09-26 定）：名字跟着配置/预制件走，一个角色一份。
* ❌ **不用动画曲线写 Hub**（2026-09-26 定）：原因是"作者必须先知道下标"那一串问题，见 §5.1。
* ❌ **不让 Connector 去改 Hub 的数组长度**（组件之间不耦合；槽是写的人按名字开的）。

## 7. 与既有设计的关系

* 这两个类型是**新挂在角色上的** ⇒ 与"角色预制件零组件"那条老规矩**冲突**：
  那是**调试状态**的规矩（调试状态在 `Assets/HoFaceDebugSettings.json`，不进预制件），
  而 Hub / Connector 是**产品内容**、本来就必须在角色上。用户 2026-09-25 确认
  "可以接受角色 mod 制作时挂新脚本"（而且**带自定义脚本的角色 mod 打包这条路早就跑通了**），
  所以老规矩按"只约束调试状态"重新表述，不是被推翻。
  （⚠️ 因为写手删了，**控制器资产上现在一个我们自己的组件都没有** —— 只有角色上那两个。）
* 求解节点现在的出口是**官方同形的 5 个 + `状态`**（`动态参数` 那个口 2026-09-26 删了）；
  语义值现在是**参数处理那条链的一个分支**（`参数处理.参数 → ┬→ 控制求解`、`└→ 写动态参数`），
  **不替换**既有的形状/骨骼出口。
  这与 [控制器完整输出](ANIMATOR_OUTPUT_PIPELINE_DESIGN.md) §6 的"保留现有五个 + 新增一份完整求值帧"**是同一个决定**：
  旧出口是同一帧结果的投影，**不各自重复求值**。
