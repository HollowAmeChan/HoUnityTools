# 混合树的能力边界

起因：在中间层分工上反复踩到"这件事到底该放树里还是放外面"。这份文档把**能算什么、不能算什么、
以及怎么判断**一次写清，以后不必靠印象争。实测过程与踩过的坑见 [踩过的坑](pitfalls/BLEND_TREE_TRAPS.md)。

> **一句话**：混合树不是"参数进、任意函数出"的表达式求值器。
> 它是**姿势插值机** —— 输出永远是"作者摆过的那些姿势的加权组合"，
> 以下静态代数讨论限定于**叶子为常量姿势**的树。完整Animator还包含时间、状态、属性曲线，
> **也能由叶子里的Animator float曲线产生参数**；不能把纯姿势树的限制推广到整个控制器。
>
> **2026-09-25更正**：旧版“曲线不能写Animator参数、仅VRChat能做”的结论错误。
> Unity 2021.3.45f2与6000.3.15f1均已实测原生支持；同一Controller的下游Layer在测试中晚一轮求值消费新值。
> 完整证据、组件/材质输出与分阶段方案见[控制器完整输出设计](ANIMATOR_OUTPUT_PIPELINE_DESIGN.md)。
>
> **现状（2026-09-25）**：树跑在**影子台**上 —— 会话把参数写进一个隐藏的镜像 Animator，
> Unity 真实求值那棵树，再把影子上算出的键**只抄自己拥有的那些**回真模型（§1.1）。
> **当前包的编译器只允许形态键曲线**，所以当前路径的参数由会话写；这是实现范围，不是Unity引擎限制。
> **哪些键算数不再由我们注入门控决定，交给使用者自己的树与参数**。

## 1. 它到底算什么（精确模型）

Direct 树对**每一个属性**的结果是：

```
输出 = Σᵢ (Πⱼ 门控ᵢⱼ) · 值ᵢ   +   (1 − Σw) · 默认值        引擎不自动保证形态键范围
```

- `值ᵢ` 是**作者摆的常量**（片段里写的形态键值 / 位移 / 材质参数）。树自己不产生数。
- `门控ᵢⱼ` 是参数值。**嵌套一层 Direct，门控就多乘一次**（实测：0.6 × 0.8 → 48）。
- **`Σw > 1` 时不做归一化**（实测：同一属性 0.6 + 0.8 → **140**，不是 70、也不是 80）。
  也就是"两个子节点各给一份"就是**相加**，Unity 不会替你平均 ——
  **裸的直通树为什么会过眨眼，根因就在这里**。
- **引擎不会自动钳制。** 上面那个 140 是 `GetBlendShapeWeight` 读回来的原值 ——
  Animator 把超过 100 的值原样交给 Renderer。**"姿势不超过 100"是设计纪律，不是引擎保证**
  （实测：参考实现 Shinano 的 510 个片段里，**一个 >100 的都没有**；
  它靠"权重和 ≤ 1"维持，`EyeSyncMix = 0.5` 正是为此而设）。
- 余项 `(1 − Σw)` 与**默认值**混合；WD 开时那个"默认值"是**Animator 启动时捕获的值**（实测）。
  判别性实验：同一条键在启动时被别的动画写成 33，之后 `0.6 × 100` 得的是 **73.2**（33 + 0.6 × (100 − 33)）；
  **WD 关**时同一棵树把余项混向硬 0，于是"基础动画也在写同一个键"时**发散**。实测数字与用例见
  [控制器结构](FACE_TRACKING_CONTROLLER_STRUCTURE.md) §Direct × WD，坑见 [踩过的坑 · 混合树](pitfalls/BLEND_TREE_TRAPS.md)。

**推论：它是一台"以参数为变量的多项式机器"，没有钳制。**
这条推论决定了下面所有"能 / 不能"。

### 1.1 它跑在影子台上（现状）

- 会话**不接管**角色的 Animator：它建一个隐藏的镜像层级 + 独立 Animator（`HideAndDontSave`，
  `AlwaysAnimate`），把这份面部 `.controller` 挂上去求值
  （`Editor/FaceTracking/HoFaceAnimationSession.cs:119` 的 `BuildShadow`）。
  影子上没有别的写入者，所以 **Direct 树 + Write Defaults 开**是安全组合，不必要求 WD 关
  （见 [控制器结构](FACE_TRACKING_CONTROLLER_STRUCTURE.md) §Direct × WD 判别性实验）。
- **参数由会话写**（`shadow.SetFloat`，且**只写控制器里真有的名字**，`HoFaceAnimationSession.cs:242`）。
  参数来自中间层配置的输出行（面板把配置文件当必填总闸；**留空 / 没指定 ⇒ 空表，这一层不做事**、
  **没有内置默认兜底** —— 指定之后输入行只认它的，`Editor/FaceTracking/HoFaceDebugSettings.cs` 的
  `Inputs()` / `Outputs()`。⚠️ **Unity 侧与 Warudo 侧口径一致**：参数处理节点上「配置文件」留空
  同样 = **这一层不做事**、**没有内置默认**）。
- **只写自己拥有的键**：抄回时按 `HoFaceOutputOwnership` 的占用表过一遍
  （`Runtime/FaceTracking/HoFaceOutputOwnership.cs:10`）—— 别的写入者（LookAt / 眨眼约束）占着的键不会被覆盖。
  **桌面 Unity 侧这一条是本仓库可读的实测**（`Tests~/FaceTrackingValidation.cs` 的占用/交还断言）；
  **Warudo 侧同样"只写自己的键"** 出自同源设计（`Editor/FaceTracking/HoFaceAnimationSession.cs:22`），
  但 Warudo 的那份运行时代码不在本仓库 → **标 `UNVERIFIED`**。

## 2. 能表达什么（附配方）

| 想要的 | 怎么做 | 状态 |
| --- | --- | --- |
| 加权和 `Σ wᵢ·Cᵢ` | 多个子节点写同一个属性 | 实测 |
| **乘积 `a · b`** | 嵌套 Direct：外层门控 `a`，里层门控 `b` | **实测：0.6 × 0.8 → 48** |
| **加权平均 `(a+b)/2`** | 两个子节点写同一属性，**值摆成一半**（50），门控给出 a、b | **实测**（相加不归一化 ⇒ 系数就是那个 50） |
| 反向 `1 − a` | 同一属性上两个子节点分别写 1 与 0，权重取 `a` | 由上面的加法推得 |
| 幂 `a²` | 同一个门控套两层 | 由"嵌套相乘"推得 |
| 上下限 / 饱和 | **没人替你钳**：要么设计时让权重和 ≤ 1，要么由**写出去的那一方**钳。现在钳在三个明确的地方：① 中间层输出行那条响应曲线的关键点范围（超出按端点算，`HoFaceCurve.Transfer`）；② 约束组件里独立的那套写入器（`HoShapeKeyWriter`，`outputMax` / `clampToRange`，只服务 LookAt / 眨眼 / 弹簧）；③ 会话抄回真模型时的输出集合 —— **树自己不会钳** | 实测（引擎不钳，见 §1） |
| 区域/模式开关 | 子树挂在父树上，权重 = 门控参数 —— **树本身支持**，但那参数现在是**使用者自己树里的事**，不再由我们注入（区域门控已删，见 §2 后的说明） | 引擎行为（0.6 × 0.8 → 48 那批实测）；"我们生成门控"已作废 |
| 两版映射交叉淡入 | 一棵 1D 树，两个子节点分别是"OFF 版"和"ON 版"的子树 | 参考实现的 `EyeSync`（**只作参考，我们没有它**） |
| **把会重叠的语义并进同一棵树** | 2D 树 + 作者摆好的组合姿势（见 §6） | 实测（参考实现的眼睑五姿势） |
| 分段（近似） | 多阈值子节点，段内是线性插值 | 实测（1D 树语义） |
| **输出Animator float参数** | 叶子绑定`type=Animator`、属性名=参数名；曲线值随树混合，求值后可GetFloat | **两版本实测**；现有Compile白名单尚未开放 |

> 参考实现那个 `EyeSyncMix = 0.5` 现在看懂了：它把"两只眼的值"当**加法**用，
> 而 0.5 不是为了"平均"，是为了**把加法除回一半**（两边都写一半 ⇒ 得到一只眼的量）。
> 它就是在没有归一化的前提下手工补上归一化系数。
> （这段是对**参考实现**的解读，不是我们的实现 —— 我们的 `HoFaceEyeSync` 已经删了；
> 要左右合并就画在使用者自己的树里。）

## 3. 不能表达什么

| 做不到 | 为什么 |
| --- | --- |
| `min(a,b)` / `max(a,b)` | 不是参数的多项式组合 |
| 除法 `a / b` | 同上 |
| 任意非线性（`sin`、`smoothstep`、软饱和曲线） | 同上；只能靠多个阈值**线性近似** |
| **纯静态姿势树自己积分弹簧/惯性** | 静态插值没有速度/位移历史；但整个Animator的状态机和动画片段有时间，不能说整个控制器没有状态 |
| **把同一Controller的Layer当作确定的同轮计算流水线** | 曲线可以写参数，但本轮测试中下一Layer到第二次求值才消费新值；复杂反馈需明确调度，见 §4 |
| 精确的分段（"小于 X 就是 0"） | 只能线性近似，除非用 `Step` 那种离散档 |

一条实用的判断法：**把你要的映射写成一个表达式，看它是不是"参数的多项式组合 + 钳制"。**
是 → 树能做（可能要多层门控）；出现 `min`/`max`/除法/时间 → 树做不到。

## 4. 四条"逃生口"，以及各自的代价

树做不到的事，只有这四个去处：

| 逃生口 | 能做什么 | 代价 |
| --- | --- | --- |
| **在控制器外面算**（我们的做法：中间层表达式 + 曲线，再由会话写进影子参数） | 任意 | 需要宿主能跑 C#：Unity / Warudo 可以，**VRChat 不行** |
| **Unity原生Animator参数曲线** | 混合叶子曲线，产生可读的float参数；VRC模板也使用这类绑定 | 不保证同一次求值里后续Layer立即读取新值；不要把它当任意无延迟闭环 |
| **曲线 + 纯数据组件 + C#读回** | 写组件字段，在求值后导出语义/属性；可再送另一个阶段 | **不必等待下一帧**：本轮已验证A求值→读回→B求值可同帧完成；需要明确阶段/时钟 |
| **StateMachineBehaviour**（挂状态上，`OnStateUpdate` 里 `SetFloat`） | 在控制器内跑任意 C# | 依赖我们的代码进构建；一个状态一个行为；**我们现在的 `Compile` 明确拒绝 Behaviour** |

参数曲线与组件字段都能成为输出。需要区分**求值后读取**和**同一次Animator求值内部的依赖顺序**：
前者已验证可同步读到，后者不能仅凭Layer顺序假定。涉及物理积分时更应按语义→物理→姿势明确分阶段。

## 5. 设计前的三个自问

1. **我要的是"姿势"还是"值"？**
   姿势 → 直接进树（含重叠语义的合并）。值要给别人用 → 看第 4 节。
2. **写成表达式，它是不是"参数的多项式组合 + 钳制"？**
   是 → 树能做；否（`min`/`max`/除法/时间）→ 外面算。
3. **需要同帧串联或反馈吗？**
   不需要时可以直接使用原生参数曲线/属性输出；需要时定义阶段、时钟与反馈缓冲，不用“多Update几次”作为通用语义。

## 6. 一个正面例子：会重叠的语义要并进同一棵树

> §6–§9 讲的是**处方与证据**（参考实现的片段、当年的实测数字）。
> **我们的代码里现在不生成任何树** —— 控制器由使用者在 Unity 的混合树编辑器里装配，
> 这些格子名、轴名、树形都是作者的事。下面说的是"若要重叠语义，该怎么摆"。

ARKit 的 `eyeBlink` 与 `eyeSquint` 在模型上闭的是同一块，裸输入里两者同时非 0 →
同一个形变被写两遍 → 过眨眼。参考实现的解法**不是**在参数上做抑制，而是：

**把这三个键写进同一批姿势，用一棵 2D 树插值**（实测五个片段的内容）：

| 姿势 | blink | squint | wide |
| --- | --- | --- | --- |
| 睁大 | 0 | 0 | **100** |
| 中性 | 0 | 0 | 0 |
| 闭 | **100** | 0 | 0 |
| **眯** | **90** | **100** | 0 |
| 睁大+眯 | 0 | 0 | **100** |

关键在**「眯」那格自带 blink 90**：两个轴走到哪就是哪个姿势，**权重和恒为 1，不可能相加**。
这也解释了"为什么眼睑是 2D 而嘴是 1D"——不是好看，是必须。

## 7. 证据与不确定性

合成规则的**实测过程与数字**收在 [踩过的坑 · 混合树](pitfalls/BLEND_TREE_TRAPS.md)（同一套 `HO_*` 用例）。
本节只留"还没量过"的部分。

其余推断与验证边界：

- `1 − a`：靠"同一属性写 1 和 0、权重取 a"。若 Unity 对**同属性多子节点**的处理在 WD 关 / 归一化设置变化时改行为，
  这条要重验 —— **目前 `WD 开 + Direct` 是唯一被验证过的组合**。
- `a²`：同一个门控套两层，由"嵌套相乘"直接推出，没单独跑过。
- **2D（FreeformCartesian）树里的权重和是否恒为 1**：**没直接量过**，而 §6 / §9 的"姿势不可能相加"依赖它。
  参考实现（与当年的眼睑 2D 子树）就吃这条，值得补一个用例 —— **当前代码里没有这棵树**，
  所以这是"将来谁照处方摆 2D 眼睑树时要先验的前提"，不是现有实现的前提。
- **StateMachineBehaviour桥仍未验证**：当前Compile明确拒绝它。参数曲线、组件字段和两个Controller的显式同帧串联已由本轮实验验证，不能再列作全部未验证；Warudo中的扩展采集/应用还未实现。

## 8. 找反例：拿 Shinano 的控制器复核这份表

复核的收获不在"通读一遍"，而在挑**"模型依赖、但没直接量过"**的假设去打：

| 检查 | 结果 |
| --- | --- |
| 有没有非多项式的运算（`min` / `max` / 除法） | **没有** —— `Limit` 链全是"按参数交叉淡入到 `_EmptyAnimation`"，仍是分段线性 |
| 是否依赖引擎钳制 | **不依赖**：510 个 `.anim` 里一个 >100 的都没有（"属性范围自动钳制"那句因此从 §1 删掉） |
| 怎么产生参数 | 参考资产使用Animator参数曲线；**不能据此归因为VRChat独有能力**。原生Unity同类绑定已实测成立 |
| ±1 的双向轴怎么做 | 写的是**另一个键**（`CheekPuff_Left -1` 写 `CheekSuckLeft`）→ 印证"双向轴 = 两个方向的键" |

## 9. "把重叠语义并进一棵树"通用到什么程度

实测有效（**当年那版眼睑 2D 子树；现在这棵树由控制器的作者摆**）：眼睑改成 2D 子树后，
`blink` 与 `squint` 的加和最多 ~110（原来是 200）—— 因为**权重和恒为 1**。
但通用性有**三条硬边界**：

| | 边界 | 说明 |
| --- | --- | --- |
| **① 维数** | **只有 2 维能用** | Unity 的混合树只有 1D / **2D**，没有 3D。两个会重叠的通道 → 2D 树 ✓；三个以上 → 树上表达不了 |
| **② 降维有损** | 压成两根轴是有损的 | `开合 = blink − wide` 让 `wide=0.5` 与 `blink=0.5` 落在同一个点。而且**压轴是参数算术，必须在树外面做** |
| **③ 没摆的角没有定义** | 靠"恰好夹住" | 姿势表里没有 (闭, 眯) 那个角时，行为是引擎的边界行为 —— 实测恰好是"权衡"，但**恰好可用不是设计保证** |

不受边界②③影响的做法：**每个能到达的角都摆上姿势**。控制器的作者要做的，就是补一格 `闭+眯`
（格点 `A3X2Y2`）—— 那格的数值是一次**艺术决定**（"眨满时眯眼还剩多少"），摆进去就不再依赖任何未定义行为。

推广到 N 个重叠通道（真正的通用处方）：树上做不到，两条出路 ——
(a) 在外面算成一个组合参数再传进来（但那本身要先降维，见边界②）；
(b) 串联多棵 2D 树、中间**产生新参数** → 那就回到"树写不了参数"那座反馈桥（§4）。

**准确的表述**：通用的是**处方**（会重叠的语义并进同一棵树 + 为每个能到达的组合摆姿势）；
不通用的是**维数**（超过两根轴就得先降维，而降维有损、且必须在树外做）。
