# 混合树的能力边界

起因：在中间层分工上反复踩到"这件事到底该放树里还是放外面"。这份文档把**能算什么、不能算什么、
以及怎么判断**一次写清，以后不必靠印象争。实测过程与踩过的坑见 [踩过的坑](pitfalls/BLEND_TREE_TRAPS.md)。

> **一句话**：混合树不是"参数进、任意函数出"的表达式求值器。
> 它是**姿势插值机** —— 输出永远是"作者摆过的那些姿势的加权组合"，
> 以下静态代数讨论限定于**叶子为常量姿势**的树。完整Animator还包含时间、状态、属性曲线，
> **也能由叶子里的Animator float曲线产生参数**；不能把纯姿势树的限制推广到整个控制器。
>
> **2026-09-25更正**：旧版“曲线不能写Animator参数、仅VRChat能做”的结论错误。
> Unity 2021.3.45f2与6000.3.15f1均已实测原生支持；同一Controller的下游Layer在测试中晚一轮求值消费新值。
> 完整证据、组件/材质能动画到哪一步（以及**为什么我们只写姿态与 Hub**）见[控制器输出范围与实测能力](ANIMATOR_OUTPUT_PIPELINE_DESIGN.md)。
>
> **现状（2026-09-25）**：树跑在**影子台**上 —— 会话把参数写进一个隐藏的镜像 Animator，
> Unity 真实求值那棵树，再把影子上算出的键**只抄自己拥有的那些**回真模型（§1.1）。
> **当前包的编译器只允许形态键曲线**，所以当前路径的参数由会话写；这是实现范围，不是Unity引擎限制。
> **哪些键算数不再由我们注入门控决定，交给使用者自己的树与参数**。

## 1. 它到底算什么（精确模型）

Direct 树对**每一个属性**的结果是：

```
输出 = Σᵢ (Πⱼ 门控ᵢⱼ) · 值ᵢ   +   (1 − Σw) · 默认值        引擎不自动保证形态键范围
```

- `值ᵢ` 是**作者摆的常量**（片段里写的形态键值 / 位移 / 材质参数）。树自己不产生数。
- `门控ᵢⱼ` 是参数值。**嵌套一层 Direct，门控就多乘一次**（实测：0.6 × 0.8 → 48）。
- **`Σw > 1` 时不做归一化**（实测：同一属性 0.6 + 0.8 → **140**，不是 70、也不是 80）。
  也就是"两个子节点各给一份"就是**相加**，Unity 不会替你平均 ——
  **裸的直通树为什么会过眨眼，根因就在这里**。
- **引擎不会自动钳制。** 上面那个 140 是 `GetBlendShapeWeight` 读回来的原值 ——
  Animator 把超过 100 的值原样交给 Renderer。**"姿势不超过 100"是设计纪律，不是引擎保证**
  （实测：参考实现 Shinano 的 510 个片段里，**一个 >100 的都没有**；
  它靠"权重和 ≤ 1"维持，`EyeSyncMix = 0.5` 正是为此而设）。
- 余项 `(1 − Σw)` 与**默认值**混合；WD 开时那个"默认值"是**Animator 启动时捕获的值**（实测）。
  判别性实验：同一条键在启动时被别的动画写成 33，之后 `0.6 × 100` 得的是 **73.2**（33 + 0.6 × (100 − 33)）；
  **WD 关**时同一棵树把余项混向硬 0，于是"基础动画也在写同一个键"时**发散**。实测数字与用例见
  [控制器结构](FACE_TRACKING_CONTROLLER_STRUCTURE.md) §Direct × WD，坑见 [踩过的坑 · 混合树](pitfalls/BLEND_TREE_TRAPS.md)。

**推论：它是一台"以参数为变量的多项式机器"，没有钳制。**
这条推论决定了下面所有"能 / 不能"。

### 1.1 它跑在影子台上（现状）

- 会话**不接管**角色的 Animator：它建一个隐藏的镜像层级 + 独立 Animator（`HideAndDontSave`，
  `AlwaysAnimate`），把这份面部 `.controller` 挂上去求值
  （`Editor/FaceTracking/HoFaceAnimationSession.cs:119` 的 `BuildShadow`）。
  影子上没有别的写入者，所以 **Direct 树 + Write Defaults 开**是安全组合，不必要求 WD 关
  （见 [控制器结构](FACE_TRACKING_CONTROLLER_STRUCTURE.md) §Direct × WD 判别性实验）。
- **参数由会话写**（`shadow.SetFloat`，且**只写控制器里真有的名字**，`HoFaceAnimationSession.cs:242`）。
  参数来自中间层配置的输出行（面板把配置文件当必填总闸；**留空 / 没指定 ⇒ 空表，这一层不做事**、
  **没有内置默认兜底** —— 指定之后输入行只认它的，`Editor/FaceTracking/HoFaceDebugSettings.cs` 的
  `Inputs()` / `Outputs()`。⚠️ **Unity 侧与 Warudo 侧口径一致**：参数处理节点上「配置文件」留空
  同样 = **这一层不做事**、**没有内置默认**）。
- **只写自己拥有的键**：抄回时按 `HoFaceOutputOwnership` 的占用表过一遍
  （`Runtime/FaceTracking/HoFaceOutputOwnership.cs:10`）—— 别的写入者（LookAt / 眨眼约束）占着的键不会被覆盖。
  **桌面 Unity 侧这一条是本仓库可读的实测**（`Tests~/FaceTrackingValidation.cs` 的占用/交还断言）；
  **Warudo 侧同样"只写自己的键"** 出自同源设计（`Editor/FaceTracking/HoFaceAnimationSession.cs:22`），
  但 Warudo 的那份运行时代码不在本仓库 → **标 `UNVERIFIED`**。

## 2. 能表达什么（附配方）

| 想要的 | 怎么做 | 状态 |
| --- | --- | --- |
| 加权和 `Σ wᵢ·Cᵢ` | 多个子节点写同一个属性 | 实测 |
| **乘积 `a · b`** | 嵌套 Direct：外层门控 `a`，里层门控 `b` | **实测：0.6 × 0.8 → 48** |
| **加权平均 `(a+b)/2`** | 两个子节点写同一属性，**值摆成一半**（50），门控给出 a、b | **实测**（相加不归一化 ⇒ 系数就是那个 50） |
| 反向 `1 − a` | 同一属性上两个子节点分别写 1 与 0，权重取 `a` | 由上面的加法推得 |
| 幂 `a²` | 同一个门控套两层 | 由"嵌套相乘"推得 |
| 上下限 / 饱和 | **没人替你钳**：要么设计时让权重和 ≤ 1，要么由**写出去的那一方**钳。现在钳在三个明确的地方：① 中间层输出行那条响应曲线的关键点范围（超出按端点算，`HoFaceCurve.Transfer`）；② 约束组件里独立的那套写入器（`HoShapeKeyWriter`，`outputMax` / `clampToRange`，只服务 LookAt / 眨眼 / 弹簧）；③ 会话抄回真模型时的输出集合 —— **树自己不会钳** | 实测（引擎不钳，见 §1） |
| 区域/模式开关 | 子树挂在父树上，权重 = 门控参数 —— **树本身支持**，但那参数现在是**使用者自己树里的事**，不再由我们注入（区域门控已删，见 §2 后的说明） | 引擎行为（0.6 × 0.8 → 48 那批实测）；"我们生成门控"已作废 |
| 两版映射交叉淡入 | 一棵 1D 树，两个子节点分别是"OFF 版"和"ON 版"的子树 | 参考实现的 `EyeSync`（**只作参考，我们没有它**） |
| **把会重叠的语义并进同一棵树** | 2D 树 + 作者摆好的组合姿势（见 §6） | 实测（参考实现的眼睑五姿势） |
| 分段（近似） | 多阈值子节点，段内是线性插值 | 实测（1D 树语义） |
| **输出Animator float参数** | 叶子绑定`type=Animator`、属性名=参数名；曲线值随树混合，求值后可GetFloat | **两版本实测**；现有Compile白名单尚未开放 |

> ⚠️ **"乘积 / 嵌套门控"是引擎能力，但不是我们推荐的形状**（2026-09-26 用户定）：**树里的门控只做一层。**
> 原因是动态参数那条链 —— Hub 里传的是**中间层算出来的参数值**，嵌套门控的"有效值"只活在树里、**传不出来**
> （详见 [控制器结构](FACE_TRACKING_CONTROLLER_STRUCTURE.md) §3.3）。要"两个开关的与"，就在**中间层**乘好再喂一棵树。
>
> 参考实现那个 `EyeSyncMix = 0.5` 现在看懂了：它把"两只眼的值"当**加法**用，
> 而 0.5 不是为了"平均"，是为了**把加法除回一半**（两边都写一半 ⇒ 得到一只眼的量）。
> 它就是在没有归一化的前提下手工补上归一化系数。
> （这段是对**参考实现**的解读，不是我们的实现 —— 我们的 `HoFaceEyeSync` 已经删了；
> 要左右合并就画在使用者自己的树里。）

## 3. 不能表达什么

| 做不到 | 为什么 |
| --- | --- |
| `min(a,b)` / `max(a,b)` | 不是参数的多项式组合 |
| 除法 `a / b` | 同上 |
| 任意非线性（`sin`、`smoothstep`、软饱和曲线） | 同上；只能靠多个阈值**线性近似** |
| **纯静态姿势树自己积分弹簧/惯性** | 静态插值没有速度/位移历史；但整个Animator的状态机和动画片段有时间，不能说整个控制器没有状态 |
| **把同一Controller的Layer当作确定的同轮计算流水线** | 曲线可以写参数，但本轮测试中下一Layer到第二次求值才消费新值；复杂反馈需明确调度，见 §4 |
| 精确的分段（"小于 X 就是 0"） | 只能线性近似，除非用 `Step` 那种离散档 |

一条实用的判断法：**把你要的映射写成一个表达式，看它是不是"参数的多项式组合 + 钳制"。**
是 → 树能做（可能要多层门控）；出现 `min`/`max`/除法/时间 → 树做不到。

## 4. 四条"逃生口"，以及各自的代价

树做不到的事，只有这四个去处：

| 逃生口 | 能做什么 | 代价 |
| --- | --- | --- |
| **在控制器外面算**（我们的做法：中间层表达式 + 曲线，再由会话写进影子参数） | 任意 | 需要宿主能跑 C#：Unity / Warudo 可以，**VRChat 不行** |
| **Unity原生Animator参数曲线** | 混合叶子曲线，产生可读的float参数；VRC模板也使用这类绑定 | 不保证同一次求值里后续Layer立即读取新值；不要把它当任意无延迟闭环 |
| **曲线 + 纯数据组件 + C#读回** | 写组件字段，在求值后导出语义/属性；可再送另一个阶段 | **不必等待下一帧**：本轮已验证A求值→读回→B求值可同帧完成；需要明确阶段/时钟 |
| **StateMachineBehaviour**（挂状态上，`OnStateUpdate` 里 `SetFloat`） | 在控制器内跑任意 C# | 依赖我们的代码进构建；一个状态一个行为；**我们现在的 `Compile` 明确拒绝 Behaviour** |

参数曲线与组件字段都能成为输出。需要区分**求值后读取**和**同一次Animator求值内部的依赖顺序**：
前者已验证可同步读到，后者不能仅凭Layer顺序假定。涉及物理积分时更应按语义→物理→姿势明确分阶段。

## 5. 设计前的三个自问

1. **我要的是"姿势"还是"值"？**
   姿势 → 直接进树（含重叠语义的合并）。值要给别人用 → 看第 4 节。
2. **写成表达式，它是不是"参数的多项式组合 + 钳制"？**
   是 → 树能做；否（`min`/`max`/除法/时间）→ 外面算。
3. **需要同帧串联或反馈吗？**
   不需要时可以直接使用原生参数曲线/属性输出；需要时定义阶段、时钟与反馈缓冲，不用“多Update几次”作为通用语义。

## 6. 一个正面例子：会重叠的语义要并进同一棵树

> §6–§9 讲的是**处方与证据**（参考实现的片段、当年的实测数字）。
> **我们的代码里现在不生成任何树** —— 控制器由使用者在 Unity 的混合树编辑器里装配，
> 这些格子名、轴名、树形都是作者的事。下面说的是"若要重叠语义，该怎么摆"。

ARKit 的 `eyeBlink` 与 `eyeSquint` 在模型上闭的是同一块，裸输入里两者同时非 0 →
同一个形变被写两遍 → 过眨眼。参考实现的解法**不是**在参数上做抑制，而是：

**把这三个键写进同一批姿势，用一棵 2D 树插值**（实测五个片段的内容）：

| 姿势 | blink | squint | wide |
| --- | --- | --- | --- |
| 睁大 | 0 | 0 | **100** |
| 中性 | 0 | 0 | 0 |
| 闭 | **100** | 0 | 0 |
| **眯** | **90** | **100** | 0 |
| 睁大+眯 | 0 | 0 | **100** |

关键在**「眯」那格自带 blink 90**：两个轴走到哪就是哪个姿势，**权重和恒为 1，不可能相加**。
这也解释了"为什么眼睑是 2D 而嘴是 1D"——不是好看，是必须。

## 7. 证据与不确定性

合成规则的**实测过程与数字**收在 [踩过的坑 · 混合树](pitfalls/BLEND_TREE_TRAPS.md)（同一套 `HO_*` 用例）。
本节只留"还没量过"的部分。

其余推断与验证边界：

- `1 − a`：靠"同一属性写 1 和 0、权重取 a"。若 Unity 对**同属性多子节点**的处理在 WD 关 / 归一化设置变化时改行为，
  这条要重验 —— **目前 `WD 开 + Direct` 是唯一被验证过的组合**。
- `a²`：同一个门控套两层，由"嵌套相乘"直接推出，没单独跑过。
- **2D（FreeformCartesian）树的边界行为**：**2026-09-27 已量过** —— 摆满的矩形网格"内部双线性、外部钳到边界"，
  缺一角则完全不可预测（实测到负权重）。数字与做法见 §10。参考实现（与当年的眼睑 2D 子树）吃这条，
  所以这条从"没量过"升级为**处方必须遵守**：每个能到达的角都要摆上姿势。
- **StateMachineBehaviour桥仍未验证**：当前Compile明确拒绝它。参数曲线、组件字段和两个Controller的显式同帧串联已由本轮实验验证，不能再列作全部未验证；Warudo中的扩展采集/应用还未实现。

## 8. 找反例：拿 Shinano 的控制器复核这份表

复核的收获不在"通读一遍"，而在挑**"模型依赖、但没直接量过"**的假设去打：

| 检查 | 结果 |
| --- | --- |
| 有没有非多项式的运算（`min` / `max` / 除法） | **没有** —— `Limit` 链全是"按参数交叉淡入到 `_EmptyAnimation`"，仍是分段线性 |
| 是否依赖引擎钳制 | **不依赖**：510 个 `.anim` 里一个 >100 的都没有（"属性范围自动钳制"那句因此从 §1 删掉） |
| 怎么产生参数 | 参考资产使用Animator参数曲线；**不能据此归因为VRChat独有能力**。原生Unity同类绑定已实测成立 |
| ±1 的双向轴怎么做 | 写的是**另一个键**（`CheekPuff_Left -1` 写 `CheekSuckLeft`）→ 印证"双向轴 = 两个方向的键" |

## 9. "把重叠语义并进一棵树"通用到什么程度

实测有效（**当年那版眼睑 2D 子树；现在这棵树由控制器的作者摆**）：眼睑改成 2D 子树后，
`blink` 与 `squint` 的加和最多 ~110（原来是 200）—— 因为**权重和恒为 1**。
但通用性有**三条硬边界**：

| | 边界 | 说明 |
| --- | --- | --- |
| **① 维数** | **只有 2 维能用** | Unity 的混合树只有 1D / **2D**，没有 3D。两个会重叠的通道 → 2D 树 ✓；三个以上 → 树上表达不了 |
| **② 降维有损** | 压成两根轴是有损的 | `开合 = blink − wide` 让 `wide=0.5` 与 `blink=0.5` 落在同一个点。而且**压轴是参数算术，必须在树外面做** |
| **③ 没摆的角没有定义** | 靠"恰好夹住" | **2026-09-27 更正**：圈外的参数点是**投影到圈边、再用那条边的两个端点混合**（凸组合，**不外推**；实测三点表 (1,0.5)=125、(1.5,0.5)=100、(0.5,−0.5)=50、(0.5,1)=175 全部逐位吻合）。所以**缺角是安全的**，只是"圈"被切掉一块：那一侧的落点变成缺口边的两个邻居各半（实测 (1,1) → 151.5），不再是原来那个角。真正会**跳变**的是"孩子落在别的孩子构成的边/线上"（实测 (0,0.5)=166.67 而 (−0.5,0.5)=100）。详见 §10 |

不受边界②③影响的做法：**每个能到达的角都摆上姿势**。控制器的作者要做的，就是补一格 `闭+眯`
（格点 `A3X2Y2`）—— 那格的数值是一次**艺术决定**（"眨满时眯眼还剩多少"），摆进去就不再依赖任何未定义行为。

推广到 N 个重叠通道（真正的通用处方）：树上做不到，两条出路 ——
(a) 在外面算成一个组合参数再传进来（但那本身要先降维，见边界②）；
(b) 串联多棵 2D 树、中间**产生新参数** → 那就回到"树写不了参数"那座反馈桥（§4）。

**准确的表述**：通用的是**处方**（会重叠的语义并进同一棵树 + 为每个能到达的组合摆姿势）；
不通用的是**维数**（超过两根轴就得先降维，而降维有损、且必须在树外做）。

## 10. 2026-09-27 补测：2D 的边界行为、缺角行为、1D 子树（Unity 6000.3.15f1 · batchmode）

**起因**：往 2D 表喂**超出槽位范围**的值时，Unity 是把它**钳到边界**，还是**外推**？这条直接决定
"轴要不要在中间层归一化"。做法：一次性工程里四棵树挂在同一个 Direct 根下（每个子节点权重 = 一个恒 1 的参数，
互不干扰），**绑 `m_LocalPosition` / `m_LocalScale` 读原始混合值**（形态键读回来可能被 Renderer 钳，不能用）：

| 树 | 形状 |
| --- | --- |
| `Cartesian4` | 矩形四角 `(0,0)=0` `(1,0)=100` `(0,1)=200` `(1,1)=300` |
| `Triangle3` | **缺一角**：`(0,0)=0` `(1,0)=100` `(0,1)=200`（`(1,1)` 故意不摆） |
| `Grid9` | 3×3 网格，坐标 `−1/0/+1`，槽值 `= 100·i + j`（**形状与正式表一致**） |
| `Switch1D` | Simple1D（阈值 0/1），**两个孩子都是子树**（分别写 0 / 100） |

| 情形 | 实测 | 结论 |
| --- | --- | --- |

### 10.1 奇数阵缺一角（3×3 少一个角）：会不会"压回原点"？

这是**我们的形状**（每张表都是奇数阵，中心点有状态），值得单独测。做法：3×3 网格（坐标 `−1/0/+1`、槽值 `100i+j`）把 **(1,1) 那个角去掉**（8 个孩子），再把**中心那个孩子的值打成 999**
—— 于是"压回原点"会直接读成 999。

| 采样点 | 满 9 格 | 缺一角（8 格） | 缺一角 + 中心打 999 | 中心权重（反推） |
| --- | ---: | ---: | ---: | ---: |
| (0,0) 中心 | 101 | 101 | **999** | 1 |
| (0.3,0.3) | 138.88 | 124.31 | 607.85 | 0.55 |
| (0.5,0.5) | 151.5 | 134.67 | 434 | 0.34 |
| (0.7,0.7) | 164.13 | 139.85 | 347.08 | 0.24 |
| (0.9,0.9) | 185.17 | 146.91 | 228.55 | 0.09 |
| **(1,1) 缺的那个角** | 202 | **151.5** | **151.5** | **0** |
| (1.1,1.1) / (1.5,1.5) | 202 | 151.5 | 151.5 | 0 |
| (1,0.5) | 201.5 | 176.25 | 176.25 | 0 |
| (0.5,1) | 152 | 126.75 | 126.75 | 0 |
| (0.5,1.5) | 152（= y 钳到 1） | **102**（≠ (0.5,1) 的 126.75） | 102 | 0 |
| (1.5,0.5) | 201.5 | 201 | 201 | 0 |
| (−1,−1) / (1,−1) / (−1,1) | 0 / 200 / 2 | 同左 | 同左 | 0 |

**结论（三条）**：

1. **不会压回原点。** 中心孩子的权重从 0.55 沿对角线**平滑衰减到 0**，在缺角那一块**正好是 0**。
   缺角处的值 = **相邻两个边孩子各半**（(1,0)=201 与 (0,1)=102 → 151.5）—— 也就是说缺的那块
   不是"回中性"，而是**塌到那条缺失边上**（= 圈被切掉一角后的**新边**，与 §10 的统一规律一致）。
2. **内部平滑、单调、不越界**（124.31 → 151.5 一路递增，全部落在子节点值域内）——
   比"三点表"那种退化摆法好得多。**所以奇数阵少一个角，内部是可以接受的。**
3. ⚠️ **但缺角会让"圈"变小**：满 9 格时 `(0.5,1.5)` 钳到 `(0.5,1)`=126.75，缺角后是 **102** ——
   因为它被投影到**新边**的端点 `(0,1)` 上，而不是原来的矩形边界。
   ⇒ 要"圈外停在矩形边界那一格"，就得**摆满**；缺角时圈外会停在"缺口那条边"上（安全，但位置不同）。

### 10.2 Normalize Blend Values（那个复选框）

| 混合类型 | 复选框**关**（我们生成的 31 棵树都是这个） | 复选框**开** |
| --- | --- | --- |
| 1D / 2D | —— | **空操作**：同一棵树开/关，内部点、非对称点、超范围点读数**逐位相同** |
| **Direct**（两个孩子写同一个属性，权重 0.6 / 0.8） | **加法**：`100×0.6 + 200×0.8 = 220`；两个都写 100 时 `= 140` | **归一化**：权重被除以它们的和 ⇒ `0.4286×100 + 0.5714×200 = **157.14**` |

⚠️ **这一条对我们是个陷阱**：我们的区域 Direct **权重和本来就是 N**（`MouthRegion` 下 4 个孩子，每人权重 = `Ho/Drive/W/One` = 1）。
一旦有人在 Inspector 里把这个复选框勾上，4 个孩子会被除成 `0.25` ⇒ **整个区域变淡/姿势被摊薄**。
所以：**别勾它**（生成器写 `m_NormalizedBlendValues: 0`，那就是我们要的）。

（Unity 的 IssueTracker 有一条标题是「Direct blend tree "Normalize Blend Values" does not normalize」，
但在 **6000.3.15f1 上实测它是生效的**（157.14 就是归一化的结果）—— 以实测为准。）

**统一规律（把上面所有数字复盘了一遍，**逐位吻合**）**

> **只要"最外围孩子围成的圈"是完好的，任何参数点得到的姿势都在这个圈里面** ——
> 圈内按距离权重混合，圈外**把参数点投影到圈边上**再用那条边的两个端点线性混合。**永远不外推。**

| 点在哪 | 引擎的行为 | 实测（复盘验算） |
| --- | --- | --- |
| **圈内**（含边界） | 距离权重混合圈里所有孩子（值在圈内，但**不是分段线性**，见上表第二行） | (0.2,0.3)=129.93、(0.5,0.5)=151.5… |
| **圈外** | ① 把点**投影到圈的边界**（最近点）② 用**那条边的两个端点**线性混合 | 三点表：(1,0.5)=**125** = 投影到 (0.75,0.25) 后 `100×0.75+200×0.25`； (1.5,0.5)=**100** = 投影正好落在 (1,0)；(0.5,−0.5)=**50** = 投影到 (0.5,0) 即 `(0,0)`/`(1,0)` 各半；(0.5,1)=**175** = 投影 (0.25,0.75)。8 格缺角：(1,0.5)=**176.25** = `201×0.75+102×0.25`、(1,1.2)=**141.6**、(0.5,1.5)=**102**（投影落在端点 (0,1)）。矩形：x=−3 与 x=−1 同值、x=3 与 x=1 同值 |
| **圈退化**（某个孩子正好落在别的孩子构成的边/线上） | 那个孩子在**圈外算不到**（圈外只用边的两个端点）⇒ **圈内外跳变** | (0,0.5)=**166.67**（圈内，算上了那个点）而 (−0.5,0.5)=**100**（圈外，只用边端点） |

**四条可执行的结论**：

1. **圈 = 语义边界，轴怎么超都只在圈里走。** 这正是"安全钳回"的机制：**你要"张满"的样子摆在圈上，超出就停在圈上**。
   把点往里挪（0/.4/.75）之后同样成立（0.9 / 1.0 / 1.2 与 0.75 逐位相同）。
2. **圈内**别指望手算：非对称点与分段线性差最多 ~6%（引擎的距离权重公式没文档、五种候选都拟合不上）。
   要**精确**的死区 / 半格 / 量程，只有中间层的曲线能给你（那是自己算的）。
3. **两种圈会坏**：① 孩子落在别的孩子构成的边/线上 ⇒ 圈内外**跳变**（别这么摆）；
   ② **缺角** ⇒ 圈被切掉一块，圈外那一侧的落点变成"缺口那条边的两个邻居各半"（实测 (1,1) → 151.5）——
   **安全，但形状不再是你摆的那个角**（§10.1）。
4. §7 那条"2D 权重和没量过"**现在量过了：和恒为 1**（全程都是凸组合）。

> **更正（两版结论）**
> * 第一版只采网格线与对称中点，写成"内部**精确双线性**" —— 补采非对称点后**推翻**（是距离权重）。
> * 第二版说"缺角会出现**负权重**、不可预测" —— 那是我从"只有 3 个孩子 + 权重和为 1"**硬解出来的一个解**
>   （`(1.5,−0.5,0)`），**不是引擎的机制**。按上面"投影 + 边端点"复盘，所有数字都是凸组合、**没有负权重**；
>   §9 边界③ 的文字已同步更正。

## 11. 混合树上一共有哪些设置（别乱点的按钮）

序列化出来的树级字段只有 9 个（`BlendTree`，读自参考控制器与咱们那份资产）：

| 字段 | Inspector 上的位置 | 我们要的值 | 说明 |
| --- | --- | --- | --- |
| `m_BlendType` | **Blend Type** | `FreeformCartesian2D`（13 张表）/ `Simple1D`（5 个副本开关）/ `Direct`（根与 5 个区域） | 换类型等于换整棵树的语义，别在 Inspector 里随手改 |
| `m_BlendParameter` / `m_BlendParameterY` | **Blend Parameter**（X / Y） | 我们的轴参数 | 2D 才有 Y；写错名字 = 树永远停在一个点 |
| `m_UseAutomaticThresholds` + `m_MinThreshold` / `m_MaxThreshold` | **Automate Thresholds** + 图下方那两个数字（1D） | 现在是 `1` + 范围 `0…1` | ⚠️ **开着时 Unity 会忽略你填的阈值，在 `[min,max]` 上平均分配**。我们的开关树只有两个孩子 ⇒ 平均分就是 `0 / 1`，与我们要的一致；**要三个阈值就得先关掉它** |
| `m_NormalizedBlendValues` | **Normalize Blend Values** | **`0`，别动** | 1D/2D 空操作；**Direct 开了会把权重归一化**（我们的区域权重和是 4，会被除成 0.25）⇒ 见 §10.2 |
| `m_Childs[].m_Threshold` | 每行的 **Threshold**（1D） | 副本开关 = `0 / 1` | |
| `m_Childs[].m_Position` | 每行的 **Pos X / Pos Y**（2D） | 我们的采样坐标 | 见 §10 的三条结论 |
| `m_Childs[].m_TimeScale` / `m_CycleOffset` | 每行的时钟图标 / 偏移 | `1 / 0` | 姿势片段是静态的，改这两个只会让姿势**动起来**（我们不要） |
| `m_Childs[].m_DirectBlendParameter` | 每行的 **Direct Blend Parameter**（Direct 才有） | `Ho/Drive/W/One` 或区域门 | ⚠️ **Direct 的每个子节点都必须挂一个参数**，不挂就不参与混合 |
| `m_Childs[].m_Mirror` | 每行的 **Mirror** | `0` | 只对人形 locomotion 有意义；我们是形态键/骨骼姿势，勾了等于把姿势镜像，脸会歪 |

**Inspector 上的四个动作按钮**（不是字段，点了立刻改数据）：

| 按钮 | 干什么 | 我们能用吗 |
| --- | --- | --- |
| **Compute Positions**（2D） | 从每个孩子的**根运动**里取数据来算 Pos：`Velocity XZ`（Pos X = velocity.x、Pos Y = velocity.z）、`Speed And Angular Speed`（X = 角速度 rad/s、Y = 速度），或单轴版 `Speed` / `Velocity X/Y/Z` / `Angular Speed (Rad/Deg)`（只算 X 或只算 Y） | ❌ **绝对不要点**：我们的姿势片段**没有位移**（根运动速度 = 0）⇒ 一点下去**所有孩子的位置都会被算成 0**，整棵树塌成一格。它只服务于"走/跑/转向"那类用速度当参数的 locomotion 树 |
| **Compute Thresholds**（1D） | 同上，但改的是 1D 的阈值 | ❌ 同上（我们的阈值是语义开关 0/1） |
| **Automate Thresholds**（1D 复选框） | 在参数范围上平均分配阈值 | 🟡 现在是开的、结果正确（两孩子 ⇒ 0/1）；加第三个阈值前要关掉 |
| **Adjust Time Scale ▸ Homogeneous Speed** | 把每个孩子的 Time Scale 重新缩放成同一速度 | ❌ 与"静态姿势"无关 |
