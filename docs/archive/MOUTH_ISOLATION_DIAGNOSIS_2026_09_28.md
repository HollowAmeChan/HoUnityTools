### 下颌实测补记：闭嘴联合求解与分支跳变（2026-09-29）

用户反馈下颌测试已完成：张嘴时下颌下移表现尚可；闭嘴咀嚼虽然能读到，但表现像台阶切换，只有在紧闭嘴、下颌进入用户描述的“超过第一段关节”的用力状态后才突然触发满，正常使用很难触发。这里记录的是用户的动作描述，不据此推断解剖或设备内部机制。
用户进一步明确：**闭嘴时通过`jawOpen`与`mouthClose`联合计算。不能为了消掉台阶而擅自改成`jawOpen`单路。**

本次实际选择为`DIAG_MouthCore9_Jaw.controller + ho-iPhoneVTS.hoface.json`。磁盘点位如下，保留两份手调差异，没有互相覆盖：

| --- | ---: | ---: | ---: | ---: |
| 下巴合 | 0 | 0 | 0 | 0 |
| 下巴右 | −0.446 | 0.22 | −0.44 | 0.22 |
| 下巴张 | 0 | 0.75 | 0 | 0.75 |
| 下巴左 | 0.497 | 0.216 | 0.44 | 0.22 |

当前轴公式仍为：

```text
d = jawOpen - mouthClose
Jaw = clamp(if(d < 0, d, jawOpen), -1, 1)
```

**已从公式确认的问题：两个分支在`d=0`处不连续。** 固定`jawOpen=a>0`时，负侧趋近0，另一侧却直接取a。原备注中“闭嘴下颌下拉时`jawOpen≈0.28、mouthClose≈0.28`即可输出0.28”的说法不成立：只要`mouthClose`略大，实际仍走差值分支，然后被零平台抹掉。

以下是合成数值验算，**不是本次用户动作的逐帧录样**：

| jawOpen | mouthClose | 差值d | 旧公式输出 | 经过现有曲线、平滑之前 |
| ---: | ---: | ---: | ---: | ---: |
| 0.28 | 0.281 | −0.001 | −0.001 | 0 |
| 0.28 | 0.280 | 0 | 0.28 | 0.28 |
| 0.28 | 0.279 | 0.001 | 0.28 | 0.28 |

0.009秒平滑只能缓和时间上的突变，不能把这条不连续映射变成连续的动作关系。
另一个独立因素是Jaw曲线仍有`±0.05→0`的死区：如果日常轻咀嚼的联合求解结果落在其中，就会被吞掉。本次没有取得标注的同步原始轨迹，尚不能确定它在当前动作中占多大影响。
**“公式有跳变”已证实；“用户看到的瞬间满值完全由它造成”尚未证实。** 还需区分原始两路是否跳变、公式分支是否切换，以及最终轴值进入混合树后如何分配权重。

本轮处理边界：仅归档和验算。此前提出的`jawOpen`直通方案已根据用户纠正撤回，未写入；没有改主profile、曲线、控制器点位或当前选择，也没有生成该单路方案的对照配置。
接下来应保留两路输入，先取得同一段“静息→轻咀嚼→明显下颌运动→放松”的`jawOpen / mouthClose / 差值 / 最终Jaw`同步变化，再确定连续的闭嘴分支及死区。现有“记5秒”只保留各行min/avg/max，能辅助检查幅度，但不能用于证明各路跳变的先后顺序；历史分段均值也不能替代本轮轨迹。

### 动态录样模式（2026-09-29）

使用方式：

1. 播放并开始面捕驱动，展开“时序录制”，填写动作标签。
2. 采样间隔默认为`0.2秒`，另可选`0.05秒 / 0.02秒 / 每次求解`。这次定位下颌瞬间跳变建议选“每次求解”；0.2秒是每秒约5次，可能错过短暂的分支切换。
3. 点击“录时序5秒”，完成后自动保存；“停止并保存”保留不足5秒的已有样本。
4. Console及该Unity进程的日志会输出`[Ho 面捕时序]`与绝对文件路径；面板也可点“定位录制文件”。默认目录是角色工程的`Logs/HoFaceTraces/`，不进入Assets导入流程。

采样直接挂在会话完成求解的位置，**一次记录同时保存全部配置输入与输出，不跟随面板搜索过滤**。不会分别用输入栏/输出栏的两个异步定时器拼样本，也不会为记录重新执行公式。
每条JSONL样本包含实际单调时间、相对录制时间、求解用deltaTime、Unity帧号、接收状态及最近收包时间，并保存：

| 数据 | 用途 |
| --- | --- |
| `wires` | 当前合并后的设备线名、值及每根线最后收到的时间 |
| `inputs[].configured` | 配置输入行的结果 |
| `inputs[].effective` | 通道模式、输入曲线等处理后，输出表达式实际读到的值 |
| `outputs[].expression` | 本行公式结果；常量/无效表达式回退时记录默认值 |
| `outputs[].curve` | 本行响应曲线后、修饰符之前 |
| `outputs[].modified` | 平滑等修饰符后，本行写入输出表的值 |
| `outputs[].published` | 同名行覆盖及调试覆盖后，该名字最终发布的值 |
| `overrides` | 当时生效的手动覆盖，避免把手动输入误认成捕捉数据 |

同名输出行逐行保留`row`索引，不会把中间行丢掉。文件第一行包含版本、标签、采样设置和profile/settings快照；末行记录结束原因及实际样本数。非有限数会用`valid=false`标记，不能当作真实0；正常浮点值不按面板F4格式截断。

## 0.1 六点现场测试后的已确认结论（2026-09-28，历史记录）

**这是用户完成六点测试后确认的真实结论，作为当前嘴表的制作依据，不是待选方案。** 测试使用VTS大预设和隔离的Sad/Smile–Open主表。

1. **中性张嘴只有一段有效开口。** 下颌第一段张开正常，第一段的上限就应定义为“中性张满”。继续进入第二段需要下拉嘴角，会进入sad表现，因此不再为中性侧设计独立的第二段张嘴。
2. **第二段张嘴只存在于sad满的一侧。** sad侧需要保留两段开口：第一段sad张嘴、第二段sad大张；闭口是另一个端点。
3. **smile满时无法继续张到同样的大开口。** smile侧也只需要一段有效开口，其可达到的上限就是“smile张满”，不需要复制sad侧的大张档位。

| Form侧 | 应保留的开口语义 | 不再要求 |
| --- | --- | --- |
| sad | 闭口 → 第一段张嘴 → 第二段大张 | — |
| 中性 | 闭口 → 第一段张满 | 中性第二段大张 |
| smile | 闭口 → smile可达的张满 | smile第二段大张 |

**设计含义：Form与Open的可达范围有联合约束，嘴表不应被强行补成每列相同开度档位的方阵。**
按以上状态语义展开，是sad三态＋中性两态＋smile两态，共7个关键姿势；这是由已确认分段推导出的制作清单，**不是已经在资产里补好了7点**。
以后若仅为改善插值增加中间采样，它属于曲线/造型细化，不意味着重新引入“中性第二段”或“smile第二段”的动作语义。

## 1. 早先11点布局中定位的问题

早先调查的MouthCore有11个点，各点经一个恒1的Direct包装引用一个动画；每动画只写对应的一个形态键，Unity曲线值为100（用户界面的满值1）。
所以“一个点对应一个姿势”的理解与资产一致，本轮没有发现这里存在100倍量纲错误。

当时点位并不满足独立轴的闭口约束：

| 姿势 | Form | Open |
| --- | ---: | ---: |
| 苦闭 | −0.5 | 0 |
| 平闭 | −0.012 | 0.013 |
| 笑闭 | 0.482 | −0.017 |
| 大笑闭 | 0.907 | −0.024 |
| 笑半张 | 0.443 | 0.48 |
| 大笑半张 | 0.978 | 0.317 |
| 大笑满 | 0.926 | 0.596 |

同时，大预设Open输出曲线把−0.02…0.02压成0。**输入闭口的零线与模型闭口点不一致**；同一类表情在不同开度下的Form列也错位。

更关键的是：不能假定Freeform Cartesian 2D只在自己想象的网格单元里插值。把所有闭口点放到Y=0，只解决了一半问题；上方开嘴点如果没有同X的闭口锚点，闭口线上仍可能获得开嘴姿势权重。

用当前11个坐标、同样的FreeformCartesian2D、恒1 Direct包装和单键满值叶子，在独立工程重建权重探针。
测量的是各个“开嘴姿势”的权重总和；它不是唇缝毫米数，也不是实际角色的视觉验收。

| --- | ---: | --- |
| 原始11点 | **7.257%** | 输入毫无开口噪声时，树仍会混入开嘴姿势 |
| 仅把闭口点Y改成0 | **4.527%** | 只拉平闭口行不够 |

## 3. 早先诊断步骤：6点起步（现以§0现场结论为准）

**先继续用一张Freeform Cartesian 2D，暂不改大预设公式。**

```text
            苦         中性         大笑
开口端点    苦满       平满         大笑满
闭口端点    苦闭       平闭         大笑闭
```

准备的6点副本沿用现有闭口三列的Form值；三个开口端点分别纵向对齐这些列，保留各自原有Open端点。
它还不是强行归一化的−1/0/1 × 0/1标准矩形，没有新设演员的满幅阈值。

验收顺序：

1. **不用手机**：Open=0，扫Form的负侧、零附近、正侧与中间值，确认闭口。
2. 固定Form为苦/中性/笑，逐渐扫Open，观察嘴角、牙齿和唇轮廓是否自然。
3. 如果闭→开中间形状不好看，再换9点版加入半开行；如果只是某个局部不理想，就只补那个有用点。
4. 点位与动画通过后，用**原VTS大预设**驱动隔离主表，才评估Sad/Smile信号的零点、幅度、串扰和延迟。
5. 接回MouthJaw/MouthShift等子树，一次一项；之后再验收嘴情绪→眼睛联动；风格仲裁最后处理。

增加开嘴点时，应重新检查同一Form位置的闭口支撑；不要直接把每次录样的均值当作一组互不对齐的新坐标。
“数据能把点命中”和“整张表连续混合时符合闭口约束”是两个不同判据。

6点是用于定位与起步的候选，不是要求最终嘴只能有6种状态；半开及小笑姿势全部仍保留在原动画目录中。

## 4. Sad/Smile：先保留主线，必要时再逐项对照

设S=左右smile均值、F=左右frown均值、D=左右dimple均值，
T=`clamp(1.5 × (stretch均值 − 0.42×jawOpen − 0.05),0,1)`：

| 公式 | 含义 |
| --- | --- |
| 当前大预设 | `Form = S + 0.5D − max(F,T)` |
| VB原装公式映射到双极轴后 | `Form = S + 0.5D − F − 0.5×mouthPucker` |
| 诊断最小基线 | `Form = S − F` |

VB的Form不是纯粹的“情绪检测”：pucker会推负侧，dimple会推正侧；这些在对应模型中有造型目的。
我们希望嘴部的Sad/Smile继续影响眼睛，因此不能只为“像VB”便把发音/噘嘴特征重新混入这个共享情绪语义。

当前用户已经反馈大预设关闭风格后表现尚可，**本轮不据公式复杂就判它应该被替换**。
先消除插值问题；如果之后仍有难控制的情况，再看诊断输出里哪个项在变化。
T确实承担张口时frown弱化的补偿，简单删掉它可能损失张口的苦相，所以最小基线仅用于归因，不是发货方案。

另外，当前名为`vbparity`的旧对照把`Ho/Drive/Mouth/Open`设为`jawOpen`，而原装VB采用
`jawOpen − mouthClose − .2×roll + .2×funnel`。它只是一份临时模拟，不能称为完整VB等价复刻。
本轮新建的`VBFormula`诊断只对齐表达式，同时保留与其他诊断相同的输出曲线/平滑，明确不冒充VB全链路。

## 5. 阈值不必等于把轴全面台阶化

闭口边界正确后，仍可按实测闭嘴噪声设置一个连续曲线的零平台，并分别标定演员的舒适满幅。
这属于有明确意义的`闭口范围/中性范围/满幅`校准，不需要把说话开度全部量化成若干档。
如果要保证最终恰为0，也要考虑平滑位于零平台之后时产生的收敛尾巴；该处理仍属于中间层。
新的阈值需要当前演员的标注录样，不能根据历史统计里的猜测标签直接自动拍定。

Live2D也并非天然无噪声。其参数与keyform绑定、作者标定和模型结构决定实际表现；官方甚至特别提醒表情给嘴开度留下偏置会使嘴无法闭合。
