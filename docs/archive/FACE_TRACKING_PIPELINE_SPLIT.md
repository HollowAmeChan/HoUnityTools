# 面捕的层间分工：参数生产层 vs 驱动层

日期：2026-09-22。本文回答三个问题：**OSC 中间层是不是"参数生产层"**、**果冻眼该放哪**、**这套分工怎么同时喂给 VRC 和 Warudo**。

证据来源：本地解压的 5 个商业面捕包（见第 5 节），共 31 个控制器，全部逐个解析。解析脚本与报告在 `.research/`（gitignore）：
`inspect_ft_controllers.py`、`inspect_layer.py`、`ft-controllers-overview.txt`、`ft-detail-*.txt`、`lay-*.txt`。

## 1. 结论先说

**是。而且"控制器 + 混合树做动画、中间层做参数"这套分工，在这 31 个控制器里没有一个例外。**

真正的分界不是"层多还是层少"，而是**层按功能分段，还是按形态键逐条分段**：

| | 层的作用 | 数量 |
| --- | --- | --- |
| 参考实现 | **功能分段**：门控 / 平滑 / 二值化 / 果冻 / 修正 | FT 相关 **5~8 层** |
| 我们旧实现 | **逐键分段**：一个形态键一层 | 52 层 |

我们改成「1 层 + 一棵 Direct 树」之后，正好等于参考实现里的**驱动层**那一层。**缺的不是层数，是中间那几段功能层。**

## 2. 参考实现的标准骨架（以 kipfel 的 ARKit 模板为例，5 层）

| 层 | 名字 | 干什么 | 状态 |
| --- | --- | --- | --- |
| 0 | `FX - Face Tracking - ARKit Blendshapes` | **空状态机**，只是个命名空间 | 无 |
| 1 | `Tracking_State` | **门控**：眼/唇/表情/viseme 的开关，靠 `VRC Avatar Parameter Driver` 写 `State/*` | 全播 `_Do_Nothing`，WD=1 |
| 2 | `Face_Tracking_Blendshape_Driver` | **驱动**：**一棵 Direct 树，33 个子节点**。每个部位一个子节点，gate 用 `EyeTrackingActive` / `LipTrackingActive` | 1 个状态，WD=1 |
| 3 | `Face_Tracking_OSCmooth_Binary_Gen` | **参数生产（二值）**：Direct 树 22 子节点，每参数一个，输出 0/1 | 1 个状态，WD=1 |
| 4 | `Face_Tracking_OSCmooth_Smoothing_Gen` | **参数生产（平滑）**：2 个状态 `OSCmooth_Local` / `OSCmooth_Net`，各是一棵 **Direct 树 30 子节点**，每参数一个 | WD=1 |

三个关键细节：

1. **驱动层只做"参数 → 姿势"**，没有任何时间性逻辑。它就是一棵 Direct 树，Input 是 `OSCm/Proxy/FT/v2/*`。
2. **平滑层和驱动层在同一个控制器里，是两个图层**，不是外部程序。JS 里 `OSCm/BlendSet` 是它们的总闸（`_OSCmooth_*` 里每个子节点都挂这个 direct 参数）。
3. **参数是三元组**：`OSCm/Local/*`（原始）→ `OSCm/Smooth/*` → `OSCm/Proxy/*`（喂给驱动树）。`OSCm/Remote/*` 是网络侧另一套，用于远端平滑。

## 3. 果冻眼放哪：参考实现的两种做法

### 3.1 作为独立的"参数生产层"（Shinano v1.32）

Shinano 的控制器 8 层，FT 相关的排布：

```
[0] Eye Tracking State          ← 门控
[1] Lip Tracking State          ← 门控
[2] FacialTracking              ← 驱动（一棵大 Direct 树）
[3] JellyEye                    ← 果冻眼，独立一层
[4] QPro_Toggle
[5] AFK-FT Control
[6] _OSCmooth_Binary_Gen        ← 参数生产
[7] _OSCmooth_Smoothing_Gen     ← 参数生产
```

参数表里有 **`Blink_JellyEye`（Float）**，`JellyEye` 层的状态机是：

```
JellyIdle   （默认，WD=1）
Step 1      （WD=1）
Step 2      （WD=1）→ 播放 JellyEye.anim
```

也就是说：**果冻眼是"每帧推进、带历史"的一层**，和 OSCmooth 是同一类东西（produces a parameter / a pose over time），只是它自己一个层。

### 3.2 作为"修正层"（Mafuyu v1.04a）

Mafuyu 25 层里 FT 相关的是：

```
[19] EyeTrackingState
[20] FacialTrackingState
[21] FacialTracking
[22] MouthDefaultCorrection     ← 果冻/修正
[23] _OSCmooth_Binary_Gen
[24] _OSCmooth_Smoothing_Gen
```

`MouthDefaultCorrection` 的状态机是 `Idle`（默认）→ `MouthDefault`（播放 `MouthDefault.anim`）。说明书写得很清楚：

> 顔の基本表情シェイプキーが口元の動きに合わせて基本に戻れるように設定する補正用レイヤーがあります。
> （有一个修正层，让脸部基本表情形态键随着嘴部动作回到基准）

**这正是"嘴一动，基础表情键回默认"** —— 也就是我们设计文档里"基础动画和面捕抢同一个键"那个问题的工业解法：**用一层专门负责把基础表情拉回去**，而不是让面捕去猜。

### 3.3 所以你的判断是对的

> 「这是不是直接就是可以放果冻眼参数生产的层啊，然后混合树里面直接做果冻眼，这样做会比我们自己搓一个参数靠谱的多对吧」

**对。** 果冻/弹簧是个**时间滤波器**，它需要历史状态。放在 animator 里做的三个好处，正好是我们 C# 手搓的短板：

1. **时序天然正确** —— 它和姿势求值在同一次动画求值里，不存在"我算完了动画又覆盖掉"的竞态。
2. **可看可调** —— 在 Animator 窗口里能直接看到、能单独禁用、能调参数，不需要重新编译。
3. **可搬运** —— 同一层可以用同一套逻辑构建成 Warudo 蓝图节点（见第 4 节）。

代价是：**果冻的归属必须唯一**。既然参考实现把它做在控制器里，那我们 `HoBlinkConstraint` 里的果冻就应该**改成"只生产参数"，或者干脆退役**，不能两边都写眼睛键。这条要单独定。

## 4. VRC 与 Warudo 的对应：四段流水线

你描述的 Warudo 蓝图（裸参 → 参数平滑 → switch → 设到 SkinnedMeshRenderer）和 VRC 那边是**同一条流水线**，只是宿主不同：

| 阶段 | 语义 | VRC 里的形态 | Warudo 蓝图的形态 |
| --- | --- | --- | --- |
| ① 输入 | 裸参数（ARKit / UE / SRanipal） | `FT/v2/*`（206 个参数） | 裸参节点 |
| ② 参数生产 | 平滑 / 灵敏度 / 二值化 / 上下限 / **果冻** | `_OSCmooth_*_Gen` 图层 + `<Param> Root` 树 | 参数平滑节点 / 自定义节点 |
| ③ 门控 | 眼 / 唇 / 表情 / 远端 分组开关 | `Tracking_State`、`*TrackingState` 图层 | switch 切换节点 |
| ④ 输出 | 参数 → 姿势 → 形态键 | Direct 树 → 片段曲线 | 设到 SkinnedMeshRenderer |

**结论：中间层应该按这四个阶段设计，而不是绑定到某一种宿主。** 这样：

- 出 VRC：②③④ 编译成图层 + Direct 树（就是现在这些商业包的样子）。
- 出 Warudo 蓝图：②③④ 编译成节点 —— 你们很快要加的蓝图构建工具正好接得上。
- 出我们自己（Ho 渲管线 / 纯 Unity 调试）：②③④ 就是我们现在这套影子求值 + 生成器。

我们现在的实现只覆盖了 ①③④（输入、分组门控、Direct 树），**②完全空缺** —— 这就是"我们缺的不是层数，是中间那段"的具体所指。

## 6. 对我们下一步的直接影响

1. **补 ②「参数生产」这一段。** 最小可用版：把「平滑 + 灵敏度」做成可选的生成层，果冻单独一层。要不要对齐 OSCmooth 的 `Local/Smooth/Proxy` 三段命名，需要定（对齐好处是能在 VRC 侧直接复用别人的成品配置）。
2. **果冻的归属只能有一个。** 要么控制器侧生产、我们 `HoBlinkConstraint` 只读不写；要么反过来。两边都写必然打架。
3. **门控颗粒度对齐参考实现**：眼 / 唇 / 表情 三组，而不是我们现在的 5 组区域。参考实现是 `EyeTrackingActive` + `LipTrackingActive` 就分完了。
4. **中间层要按阶段抽象**，别写死成"生成图层"。因为 Warudo 蓝图那条路要用同一份中间表示。

## 7. 三条已定的决策

| 决策 | 内容 |
| --- | --- |
| **HoBlinkConstraint 退役** | 果冻眼改由控制器侧生产。`HoBlinkConstraint` **暂时保留不删**，但不再是眼睛键的写入者。原则上"连约束脚本都可以整体转向控制器图层"是允许的方向。 |
| **中间层命名对齐 OSCmooth** | 参数链用 `Local → Smooth → Proxy` 三段命名，生成层的命名也照它的风格。好处：能直接复用 VRC 生态里别人调好的配置与调参习惯。 |
| **果冻归属控制器侧** | 参考实现的两种做法都看过了（Shinano 的独立 `JellyEye` 层 / Mafuyu 的 `MouthDefaultCorrection` 修正层），选前者：独立层、每帧推进、带历史。 |

**补充定案（见 13.14 / 13.15）**：**旧果冻约束组件不适合搬进控制器资产**。原因是机制性的，不是偏好：

- 资产只能引用 Unity 对象，**引用不了一个挂在场景对象上的组件** —— 搬进去就会让控制器资产依赖我们的运行时脚本，Warudo 那边直接违背"不依赖进不了蓝图的东西"。
- 影子台里跑的是**控制器求值**，没有任何组件在那里执行；约束脚本的每帧回调进不去。

所以切开的位置是：**物理留在 C#（产参数），映射进资产（混合树）**。

**推论（要一起守的）**：既然果冻归控制器侧，**眼睛键的写入者就只能有一个**。`HoFaceOutputOwnership` 那套键级占用要扩展成"哪一段拥有哪个键"，否则果冻层和约束脚本会互相覆盖 —— 这正是参考实现里 `MouthDefaultCorrection` 存在的原因：基础表情的回退由**专门一层**负责，而不是让面捕去猜。

## 8. 傻瓜化：复杂度只能存在于生成物里

担心是对的，而且参考实现早就把这件事解决了。看它实际的安装面：

`Prefabs/Advance/Breakout/ARkit Blendshapes - Eye.prefab` **整个预制件只有一个组件** —— VRCFury 的 `FullController`，内容就两行引用：

```yaml
type: {class: FullController, ns: VF.Model.Feature, asm: VRCFury}
data:
  controllers:
  - controller: .../Breakout/FX - ARkit - Eye.controller     # 一个控制器
  prms:
  - parameters:  .../Breakout/Para - ARkit - Eye.asset        # 一份参数表
```

**层和树是构建期由 VRCFury 合并出来的，作者和用户都不碰。** 傻瓜化靠的是这五条：

| 手法 | 实际做法 |
| --- | --- |
| **按区域拆分安装** | Breakout 预制件：Eye / Eyebrow / Lip / Lip Extras / Tongue / Tongue Steps / Pupil Dilation，用哪个拖哪个 |
| **合并放到构建期** | VRCFury `FullController` 把控制器并进 FX 层，用户看不到合并后的 626 棵树 |
| **参数声明式** | `Para - *.asset` 就是一份 `VRCExpressionParameters` 列表，不是手工接线 |
| **平滑也是声明式的** | VRCFury 自带 `smoothedPrms` 字段；OSCmooth 是"配置 + 生成"。生成物带 `_Gen` 后缀，名字本身就在说"这是生成的，别手改" |
| **设备差异用变体** | `forPico4Pro` / `forQuestPro` / `GXR` / `default` 各一个预制件变体，换变体而不是改图层 |

安装说明也就一句话：「Unity 工具栏 → FT Patch → Start」。

### 对我们的三条硬要求

1. **用户的输入面不许随生成物一起变厚。** 面板上永远是那几个开关（连不连、驱不驱、哪几组、平滑强度、果冻开关），层数由配置推导出来。生成 5 层还是 30 层，用户都不用打开 Animator。
2. **生成物永不手改。** 生成层带前缀分段（`Ho/01 Raw`、`Ho/02 Smooth`、`Ho/03 Gate`、`Ho/04 Drive` 之类），文档和面板上都写死"要改就改配置重新生成"。参考实现用 `_Gen` 后缀表达同一件事。
3. **影子架构是挡住复杂度的那道墙。** 对角色真实模型而言，无论控制器里有多少层，永远只有"N 个形态键被面捕会话接管"这一件事可见。用户不需要理解内部结构就能知道自己在控制什么 —— 这一点是我们比参考实现更有优势的地方，别丢掉。

### Warudo 蓝图同理

蓝图也必须是**生成**的，而且要能折叠：中间表示按**四段**（①输入 ②参数生产 ③门控 ④输出）组织，生成蓝图时每段折成一个节点组/子流程。用户在蓝图里看到的是四个块，不是一个几百节点的网。

## 9. 中间层落地形态（命名对齐后）

按四段 + OSCmooth 命名，目标产物：

```
第 1 段  输入          ARKit/<键>            ← 已有（手机直连写入）
第 2 段  参数生产      OSCm/Local/<键>       ← 原始值中转（对齐 OSCmooth 的 Local）
                      OSCm/Smooth/<键>      ← 平滑后的值
                      OSCm/Proxy/<键>       ← 驱动树实际读的值
                      OSCm/BlendSet         ← 总闸
         （+ 果冻/修正：独立的 Ho/Jelly 段，产出自己的参数）
第 3 段  门控          EyeTrackingActive / LipTrackingActive   ← 收敛成参考实现的两组总闸
第 4 段  输出          ARKit Direct 树 → 形态键          ← 已有（上一轮刚改完）
```

对齐命名的一个具体好处：`OSCm/Proxy/FT/v2/<Shape>` 这套名字在 VRC 生态里是通行约定，我们的生成物能直接套用别人的调参经验，也能让别人看懂。

## 10. 生成物 vs 用户要改的东西

这是"傻瓜化"背后真正难的一处：**控制器是生成的，但用户又要能改它做复杂逻辑** —— 两者天然冲突（重新生成会吃掉用户的手改）。参考实现的解法是**把扩展点显式命名出来**：

| 出处 | 手法 |
| --- | --- |
| Jerry 的 ARKit 模板 | **状态名直接标可改性**：`FT Blendshape Driver (EDIT THIS)` / `FT Local Root (DO NOT EDIT)` / `FT Remote Root (DO NOT EDIT)` |
| Mafuyu v1.04a 说明书 | 让用户**改一个指定片段**：「MouthDefaultState 的动画文件里，加入你想在面部动作时回默认的形态键」 |

所以正确形态不是"生成一个不许碰的控制器"，而是**生成物里留出被命名的扩展点**。

### 两个产物，别混为一谈

「生成」和「只在运行时存在」是两件事。必须分开：

| 产物 | 在哪 | 谁改 | 作用 |
| --- | --- | --- | --- |
| **生成的面部控制器** | 落盘成 `.controller` 资产 | **用户可以改**（这就是"面向用户的最高级东西"） | 用户在这里加自己的混合树逻辑 |
| **预览副本** | 每次会话在内存里重建（`Compile`） | **谁都不改**，永远从上面那个 + 配置重建 | 带拥有权过滤，喂给影子台 |

**只在内存里生成的控制器是没法给用户改的** —— Animator 窗口打不开它，改不了结构，也存不下来。所以"运行时生成"只适用于第二个产物；第一个必须落盘。我们现在的实现其实已经是这个分工，只是没把它讲清楚。

### 由此定的四条

1. **生成物带命名分段，并显式标注可改性**。生成层/状态用 `Ho/... (生成·勿改)`，留给用户的扩展点用 `(EDIT THIS)`，与参考实现同一套表达。
2. **重新生成必须保留用户扩展点**。要么把用户那块引用进新生成物，要么生成到新文件并明确告诉用户"你改的那块还在原文件"。不能静默覆盖手改。这条要写在按钮上，不能只写在文档里。
3. **用户面对的最高级东西是混合树**，这一点确认成立 —— 参考实现 414~626 棵树就是靠手写树完成的耦合与二维空间。但我们的**接受范围仍然是有边界的**：只允许形态键曲线 + 标准状态/树，无 Behaviour、无事件、无对象曲线、无同步图层；超界明确报错，不静默丢弃。
4. **一个要知道的细节**：预览编译只替换片段、不动树结构，所以**用户加的树结构会保留**；但**曲线会按分组与通道选择被过滤** —— 用户手加的键能不能活下来，取决于它落在哪个分组、以及那个分组有没有开。这个行为要在面板上说清楚，否则"我明明加了这个键怎么没反应"会很难查。

### 10.1 层必须在**生成期**组装，运行期塞不进去

有一个很容易想当然的架构：「保留用户自己的控制器，运行期把生成的那些层塞进一个运行时创建的控制器里」。**这条路走不通**，而且我们现在也没这么做。

**我们现在运行时实际做的事**（`HoFaceAnimationAssets.Compile`）只有两步：

```csharp
result.controller = new AnimatorOverrideController(source);   // 只换片段
result.controller.ApplyOverrides(overrides);                 // 片段是过滤过曲线的副本
```

`AnimatorOverrideController` 的能力边界就是**替换片段**，没有加图层的 API。全仓 `Editor/FaceTracking` 里 `AddLayer` 一次都没出现过。

要在运行期合成，只能新建一个 `AnimatorController`、再把用户控制器的层/状态机/树搬过去。但 `AnimatorControllerLayer.stateMachine` 是**资产引用**，Unity 没有公开的深拷贝 API；靠 `EditorUtility.CopySerialized` 硬凑很脆（树里的片段引用、子状态机引用都要自己接），而且它是 editor-only 的 —— 和"运行时"这个说法本身就矛盾。

**所以正确的形态是：**

| 阶段 | 做什么 |
| --- | --- |
| **生成期**（按钮 / 配置变更时） | 把**全部层组装好**（生成的段 + 门控段 + 驱动段 + 用户扩展点段），落盘成一个真控制器资产 |
| **运行期**（每次会话） | 只做三件事：① 用 OverrideController 换片段并按拥有权过滤曲线 ② 建影子台 ③ 写参数、读数 |

「运行时创建的东西」确实存在 —— 就是那个 OverrideController 预览副本。但**它里面的层不是塞进去的，而是从源控制器整体继承来的**，它只是把片段换掉。这个区别很关键：**层从哪来、能不能改，取决于源资产，不取决于运行期。**

### 10.2 所以"用户可改的面"有两个，不是一个

| 可改面 | 内容 | 适合改什么 |
| --- | --- | --- |
| **① 组件配置**（面板） | 平滑强度、灵敏度、门控分组、果冻开关、通道模式、路径重映射 | 调参、开关、映射 —— 90% 的日常需求 |
| **② 生成物里的扩展点段** | 标了 `(EDIT THIS)` 的层/状态/片段 | 加耦合、二维空间、额外联动等**真正的逻辑** |

**生成段（`Ho/... (生成·勿改)`）禁止手改** —— 它会在重新生成时被覆盖。这就是为什么重新生成**必须保留扩展点段**，也是为什么这条规则要写在按钮上而不是只写在文档里。

### 10.3 改 UI 分两类：调参（即时）vs 改结构（要重新生成）

「改 UI 就直接改层」这句话要再分一层，否则会误以为每次拖个滑杆都要重新生成控制器：

| 类别 | 改的是什么 | 例子 | 生效方式 |
| --- | --- | --- | --- |
| **调参类** | **参数值**，或运行期的**过滤集合** | 平滑强度、灵敏度、通道模式（实时/手动/…）、门控开关、断流时长、路径重映射 | **即时**，不碰层。通道模式变化会让运行期重建预览副本（`Rebuild`），但层结构没变 |
| **结构类** | **层 / 状态 / 树的组成** | 加一个修正段、改平滑段算法、改门控分组集合、换驱动树的形状、建一棵自己的混合树 | **必须重新生成控制器 / 重跑工具** |

**参考实现就是这么分的**：平滑量在它那里是**参数**，不是写死的结构 —— `OSCm/Remote/EyeLidScaler`（默认 15）、`OSCm/Remote/EyeLidMod`（0.2）、`OSCm/Sensitivity/EyeLid`（0.8）、`OSCm/Local/FloatSmoothing` 都是带默认值的 Float 参数。也就是说 **OSCmooth 只把层生成一次，之后调平滑手感是改参数**，不用重新生成。

### 10.4 运行中改的是副本，不是资产

「运行中会修改里面的东西」——对，但要加定语：

| 运行期会改 | 运行期**不会**改 |
| --- | --- |
| 内存里的 OverrideController 预览副本（含过滤过曲线的片段副本） | 落盘的控制器资产 |
| 影子 Animator 的参数值 | 源片段的曲线 |
| 真实模型上被拥有的形态键 | 用户扩展点段 |

`Compile` 里的片段是 `Object.Instantiate` 出来的**副本**，过滤只作用在副本上；源 Clip 一个字节都不动。所以"运行中改副本、生成期改资产"这两条路径是**隔离**的，运行时出问题不会污染工程资产。

### 10.5 由此得出一条设计准则

**能做成参数的，就不要做成结构。** 因为参数改起来即时、可回退、能在运行中试；结构改起来要重新生成、要处理扩展点保留、还可能覆盖用户手改。

参考实现遵守这条（平滑量是参数）；我们也应该遵守：把「平滑强度 / 灵敏度 / 果冻刚度」这类**连续可调**的东西做成参数，只有**段的增删与算法选择**才是结构。

界面上也要把这两类**分开呈现**，否则「我改了怎么没生效」会反复出现 —— 这是纯 UI 问题，但用户只会记成"这工具不听话"。

### 10.6 组件契约：落盘全显式，运行时不落盘

前面用「参数 vs 结构」分类其实不够利落，会牵扯到"平滑强度算哪类"这种边界。**改成按「是否写盘」分类，判据就唯一了：**

> **凡是会落到控制器资产上的改动，只有点「应用 / 重新生成」才发生。组件上其它所有东西都是运行时覆盖，永久不写盘。**

于是组件可以被理解成两件事的组合，用户不需要记更多：

| 组件是什么 | 做什么 | 什么时候生效 |
| --- | --- | --- |
| **控制器的修改脚本** | 增删/改写控制器里的层、状态、树、片段、参数 | **只在点按钮时**，且写盘 |
| **运行时覆盖工具** | 通道模式、门控开关、手动值、断流时长、路径映射、LookAt 分工… | 立即，**永不写盘** |

这条契约直接消灭了「我改了怎么没生效」：**没有隐式落盘，所以不存在"改了但没生效"的中间态**；点了就是生效了，没点就是没生效，UI 上再显示「有 N 项未应用」即可。

#### 三个必须一起定的实现含义

1. **生成必须是「就地手术」而不是「重建文件」。** 既然组件是"控制器的修改脚本"，那它就应该**只改写自己那几段**、保留别的所有东西（尤其是 `(EDIT THIS)` 扩展点段和用户自己的层）。如果每次生成都新建一个文件、或者整个控制器重写一遍，就配不上这个说法，扩展点也保不住。
2. **要能认出"哪些层是自己的"。** 就地手术的前提。两条路：靠命名前缀（`Ho/...`）省事但用户一改名就失效；或者在资产里放一个隐藏的标记对象记录归属。建议**前缀 + 标记双保险**，并把"别改这些层的名字"写进生成段的名字里。
3. **参数默认值属于"写盘"那一侧。** 平滑强度这类东西的**默认值**烘在生成的控制器里（对齐 OSCmooth 的 `OSCm/Remote/EyeLidScaler = 15`），改默认值要点按钮；而**运行中调的是运行值**，不改默认、不写盘。这样既满足"全显式落盘"，调试手感又不至于每拖一次滑杆就要重新生成一次。

#### 一个要留意的代价

「全显式」会让**结构性改动**的循环变慢（改 → 点生成 → 重新开始驱动）。所以判断标准是：**能做成运行时可覆盖的，就别让它变成需要重新生成的东西。** 落到实践就是 —— 连续量（强度、灵敏度、刚度）一律做成参数 + 运行时覆盖；只有**段的增删与算法选择**才需要点按钮。

#### 顺带打开的一条路

这套契约之后，"组件 = 控制器加工工具"这个定位可以自然长大：以后可以在同一个地方提供**针对真实控制器资产的批处理**，例如批量改 Direct 子节点的参数名、给一组形态键曲线统一乘系数、把某个片段换成另一个、给一棵树补齐缺失的键。这些都是"组件 = 修改脚本"的直接延伸，而且因为要写盘，天然落在同一个按钮语义下。

## 11. 文件架构、挂载点与真实流程

### 11.1 四桶文件，各归各的

| 桶 | 位置 | 进版本库 | 内容 | 谁改 |
| --- | --- | --- | --- | --- |
| **本机设置** | `UserSettings/HoUnityTools/FaceTracking.asset` | ✗ | 手机 IP、上次连接状态 | 面板即时写（这台机器的事，不该同步给别人） |
| **组件配置** | 场景 / Prefab 上的组件 | ✓ | 输出分组、通道表、路径映射、未应用标记 | 用户改；**不写盘到控制器**，直到点按钮 |
| **我们产出的控制器** | `Assets/FaceTracking/Controllers/`（建议约定） | ✓ | 加工后的控制器（生成段 + `(EDIT THIS)` 段） | 生成期写；生成段勿手改 |
| **源控制器** | 用户原来放哪就哪 | ✓ | Jerry 模板 / 自己做的控制器 | **我们只读，从不改写** |

本机设置那一栏已经实现了（`ScriptableSingleton` + `FilePathAttribute.Location.ProjectFolder`），继续保持——**IP 是这台机器的事，不该跟着工程进版本库**。

### 11.2 源控制器只被读一次

这是"就地手术"能不能成立的关键：

```
第一次生成：  源控制器（只读）  +  组件配置  ──→  产出「我们的控制器」
之后每次应用：我们的控制器（就地手术，只重写 Ho/ 段，保留 EDIT THIS 段）
```

**源控制器从此不再参与。** 这样就解决了"就地手术会不会改到导入的 package 资产"——不会，因为我们只对自己产出的那一份动刀。用户想换源（升级模板版本）时，是显式地"重新从源生成"，那是一次新生成，不是应用。

### 11.3 片段内嵌还是独立文件

参考实现给了明确答案：

- **生成段**的片段**内嵌**在控制器里（`AddObjectToAsset`）—— 一个文件自包含、好进版本库。Jerry 的控制器里 412 棵树全是子资产。
- **扩展点片段独立成文件** —— Mafuyu 让用户改的 `MouthDefault.anim` 就是一个**独立 .anim 资产**，因为它就是给人手工编辑的。内嵌的子资产很难被用户单独打开、容易误改。

所以：`(EDIT THIS)` 相关的片段要独立落盘，名字写清楚，并在文档/面板里点名。

### 11.4 组件挂哪儿

| 挂法 | 说明 |
| --- | --- |
| **推荐：与 Animator 同物体**（角色根） | 绑定路径以它为根，不需要路径重映射，最省事 |
| 允许：角色下的工具子物体 | 必须显式指定 `targetAnimator`；路径仍以 **Animator 的 Transform** 为根，不能拿子物体当根 |
| **不要：挂到项目资产上** | 组件是场景级/角色级的东西，控制器是资产级的产物，两者不是一回事 |

### 11.5 真实流程

**① 首次接入（还没有控制器）**

```
角色挂上 HoFaceTrackingDebugger
  → 面板填手机 IP → 连接 → 参数表开始跳（此时还没有控制器，只有输入）
  → Inspector 点「生成面部控制器」→ 选目录（默认 Assets/FaceTracking/Controllers/）
  → 产出：门控段 + 参数生产段 + 驱动段 + 预留 (EDIT THIS) 段，并自动挂到组件上
  → 进 Play → 开始驱动 → 表情动了
```

**② 日常调试（不写盘）**

改通道模式 / 门控开关 / 平滑运行值 / 手动滑杆 → 立即生效。面板显示「无未应用改动」。

**③ 改结构（写盘，就地手术）**

开关果冻、改平滑算法、改门控分组集合 → 面板显示「**有 N 项未应用**」→ 点「应用到控制器」→ 只重写 `Ho/` 段，保留 `(EDIT THIS)` 段。若正在 Play，提示需要重新开始驱动。
（**建自己的混合树走另一个入口**：混合树小工具，它写的是用户命名的那一层，`应用改动` 不碰它。）

**④ 加自己的逻辑**

打开生成的控制器 → 找到 `Ho/09 (EDIT THIS)` 段 → 加树、加片段、加耦合 → 回组件改配置再应用 → **你那段还在**。

**⑤ 出别的后端**

同一份组件配置 → 不同后端生成：VRC = 图层 + 树；Warudo = 蓝图节点组；纯 Unity 调试 = 当前这套影子求值。

### 11.6 已定的三件事

1. **配置住在组件上**，不抽成独立 profile 资产 —— 用户要复用直接**复制粘贴组件**就行。
2. **初始化时每次都问路径** —— 反正只有第一次，之后都是原地修改，所以多问一次不算负担，而"目标写在哪"始终是用户显式决定的。
3. **应用改动不弹路径** —— 直接改组件已引用的那个控制器。

**仍待定一处**：两个角色的组件指向同一个控制器资产时，两份配置谁说了算？建议**检测到就明确警告**（"该控制器已被 X 的组件加工"），不做隐式仲裁。

## 12. 关键约束：曲线驱动参数是 VRChat 客户端能力，纯 Unity 用不了

第 1 节说 OSCmooth 的平滑层"在控制器里"，但**它靠的机制我们这边没有**：

- OSCmooth 的平滑子树把「上一帧的 `OSCm/Proxy/*`」和「这一帧的 `FT/v2/*`」按平滑系数混合，输出再写回 `OSCm/Proxy/*`。让动画输出回写参数，需要**曲线驱动 Animator 参数**。
- 证据一：VRChat SDK 的 DLL（`VRCSDK3A.dll`）里有 `VRC_AvatarParameterDriver` 这个 StateMachineBehaviour，但**没有任何 `Driven` 符号** —— 曲线驱动不是 SDK 实现的。
- 证据二（更有力）：**Av3Emulator 没有实现它**。Av3Emulator 是纯 Unity 里复刻 VRChat 动画行为的权威实现，它完整实现了 `VRC_AvatarParameterDriver` 的 Set/Add/Random/Copy 四种驱动（`LyumaAv3Runtime.cs` 第 792 行起），但全文找不到任何"曲线写参数"的实现 —— `driven` 只出现在 `legacySubAnimatorParameterDriverMode` 这个与曲线无关的开关上。如果 Unity 原生支持，或者模拟器需要它才能跑 OSCmooth 头像，这里不会缺。

**所以：OSCmooth 式的"层内平滑"在纯 Unity 下不成立**（既跑不了，多半也预览不出来）。

### 这决定了我们的中间层怎么落

设计成**对该差异免疫**：

| 阶段 | 我们（纯 Unity 影子） | VRC 后端 | Warudo |
| --- | --- | --- | --- |
| ② 参数生产 | **在 C# 里算**（`Tick` 里本来就在逐帧写参数） | 生成 OSCmooth 式图层（曲线驱动参数，客户端支持） | 蓝图里的参数平滑节点 |

**参数名仍然保留 `OSCm/Local → Smooth → Proxy` 三段**，这就是三段命名真正的技术理由（不是跟风）：

- 控制器本体永远只读 `OSCm/Proxy/<键>`；
- 我们的后端把 C# 算出的平滑值写进 `Proxy`；
- VRC 后端把平滑层插在 `Local` 和 `Proxy` 之间，**控制器本体一行都不用改**。

也就是说：**中间表示描述"有平滑这一段"，各后端自己决定把它 lower 成 C# 循环、图层、还是节点。**

### 12.1 它是刚需吗？要不要做成 enum？

**先看它的本质作用**：曲线驱动参数让**动画图有记忆**。没有它，图只能是"参数进 → 姿势出"的纯前馈；有了它，才能做逐帧状态计算和反馈回路。OSCmooth 的平滑就是这么实现的。

**分两个视角看刚需程度：**

| 视角 | 结论 |
| --- | --- |
| 对我们自己的**调试后端** | **额外能力，不是刚需。** C# 本来就在逐帧写每一个参数，有真正的状态和浮点运算，能力严格更强 |
| 对"产出一个**脱离我们的运行时、能在 VRChat 里独立跑**的控制器" | **刚需。** VRChat 里没有我们的 C#，动画图是唯一的计算基底 |

**复杂吗？不复杂。** 核心是一个"一步延迟的反馈桥"：动画求值后把曲线值读回来，下一帧写进参数。大约 50~100 行 + 一个哑组件 + 生成的曲线。唯一的前提是 Unity 只能把曲线绑到**组件属性**、绑不到 Animator 参数，所以要用一个哑组件当锚 —— 可行，只是"直接照抄 VRC 的控制器"还需要重写曲线绑定。

**会不会自己做？会，成本可控，触发条件明确：** ① 要出"能在 VRChat 独立跑"的控制器；② 要调试后端逐帧对齐 VRC 行为。**在撞上这两条之前不做。**

### 12.2 不要做成"算法切换"的 enum

这是本文最有把握的一条建议。做成 enum 会制造一个**危险的等价错觉**：用户会以为两套算法可互换、结果一致。但它们**不会逐帧相同**：

| | VRC 侧 | 我们侧 |
| --- | --- | --- |
| 平滑跑在哪 | 动画图里 | C# 里 |
| 延迟 | 一步（图求值的固有延迟） | 我们自选（可以是 0） |
| 受什么影响 | animator 更新率、曲线量化、图层求值顺序 | 浮点精度、我们的迭代顺序 |

结果**接近但不一样**。enum 会让人以为"切一下就是同一个东西"——那是在骗自己。

**正确的呈现：后端不是"运行时算法"，而是"导出目标"。**

- 面板上给一条**只读的能力声明**，说明每一段现在由谁负责，例如：
  `② 参数生产：本后端 = C# 计算（导出到 VRC 时会变成图层）`
- 用户想要 VRC 完全一致的行为时，那是**切后端预览**，不是切算法下拉。

**一条支持这个判断的旁证**：VRChat 生态两个主力编辑器模拟器 —— **Av3Emulator 和 Gesture Manager —— 都没有实现曲线驱动参数**。Av3Emulator 完整实现了 `VRC_AvatarParameterDriver` 的 Set/Add/Random/Copy（`LyumaAv3Runtime.cs:792` 起），但全文没有曲线写参数的实现；Gesture Manager 的 69 个 `.cs` 里也搜不到（`OSCm` 的命中全是 `OscModule`，网络 OSC，无关）。**连生态自己的预览工具都不复刻它**，用户早已接受"编辑器预览 ≠ 游戏内"。所以我们不复刻，是**和生态一致**，不是偷工减料。

## 13. 果冻眼：成熟做法依赖"模型预制形态键"，不是算出来的

挖了 Shinano（`FX_FT_added 2.controller`）的 `JellyEye` 层，结论和我原本的设想完全不同。

### 13.1 实际做法

| 部件 | 内容 |
| --- | --- |
| 图层 | `JellyEye`，weight=1，Override，无 AvatarMask |
| 状态机 | `JellyIdle`（默认）→ `Step 1` → `Step 2`（播放 `JellyEye.anim`）。**状态名就叫 Step，是步进播放** |
| 专用参数 | `Blink_JellyEye`（Float）。它**不是**眼睑值，是果冻自己的开关/强度 |
| 触发条件 | 转移条件是三个同时满足：`EyeLidLeft ≤ 0.1` **且** `EyeLidRight ≤ 0.1`（= 眼睛闭着）**且** `Blink_JellyEye ≥ 0.5` |
| 片段驱动什么 | **`blendShape.JellyEye 1` … `blendShape.JellyEye 5`** —— 模型里**预制好的 5 个专用形态键** |

**所以成熟做法 = 模型预制 N 个"果冻步"形态键 + 一个动画按步播出来 + 眨眼闭眼时触发。**
抖动不是运行时算的，是**美术摆好的姿势序列**。这也是它质量最好的原因，同时也意味着：

> **它需要美术在模型里做那组形态键。生成器造不出来。**

顺带一个对照：VRC 那边的 `Blink_JellyEye` 是**外部输入**参数（控制器里没有任何东西写它 —— 既不是曲线驱动，也不是 ParameterDriver），大概是菜单开关或外部 OSC。

### 13.2 这解释了我们为什么会有另一条路

`HoBlinkConstraint` 的果冻不需要模型预制：它**读一个键、过弹簧-阻尼、把抖动映射到别的键**。通用，但质量取决于映射。

于是"果冻眼"其实是**两种情况、两条路**，不是谁替代谁：

| | 靠什么 | 质量 | 前提 |
| --- | --- | --- | --- |
| **A. 步进播放（成熟做法）** | 模型预制 `JellyEye 1..N` + 步进动画 | 最好（美术摆的） | **模型得有那组键** |
| **B. 弹簧映射（HoBlink 那条）** | C# 弹簧读键→写别的键 | 通用 | 不需要美术资源 |

### 13.3 我们该怎么做（待定）

> **本节已被 13.8 / 13.14 / 13.15 取代，保留原文记录当初的判断。**
> 当时的方案是"扫模型上的果冻步键 → 生成一个 `Ho/10 Jelly` 步进层"，照抄 Shinano。
> 后来的结论是：步进动画是它在"没有脚本基底"下的绕法，我们不该抄；果冻的消费端是一棵
> **由用户自己选键的 2D 混合树**，而且它**不由初始化生成**，由混合树小工具按需建。

**A 我们做不了**：模型里没有 `JellyEye 1..5` 就没有东西可播。除非用户自己让美术加。

可行的组合是**检测 + 分支**：

1. 扫描模型上有没有一组按约定命名的"果冻步"键（例如 `JellyEye 1..N`，或我们自己的命名约定）。
2. 有 → 生成 `Ho/10 Jelly` 层：`Idle` → `Step 1..N`（步进播放，每个 Step 一个片段），
   转移条件用**已有的眼睑参数**（我们在写）+ 一个果冻开关参数。**这条完全对齐成熟做法。**
3. 没有 → 不生成果冻层，或者退到 B（C# 弹簧驱动已有键）。

**注意 2 里没有曲线驱动参数的问题**：转移条件读参数是原生能力，步进播放也是纯动画，
所以这条路在我们后端**可行**。

第一版建议只做 2（有专用键才生成），因为它是成熟做法的忠实移植，而且行为可预期；
B 那条（弹簧映射）本来就是 HoBlink 的活儿，而 HoBlink 已定退役，要不要搬进来得单独决定。

### 13.4 动画驱动够不够"物理感"？（结论：够，而且更可控）

疑问是合理的：**预制的固定动画，真能做出一根弹簧那种抖动吗？**

先把两件事分开：

| | 物理弹簧 | 作者的动画 |
| --- | --- | --- |
| 能表达"过冲 → 回弹 → 稳定"的**形状** | ✅ | ✅ 逐帧摆出来就是 |
| 能**随输入变化**（闭得快慢不同、幅度不同） | ✅ | ❌ 每次一样 |

所以真正的损失只有一个：**单调**。而"够不够物理感"这一问，答案反而偏向动画 —— 物理感的来源就是过冲、回弹、稳定这三样，**美术是针对这张脸的网格把过冲和回弹调对的**；弹簧参数是一套参数套所有模型，通常只能调到"差不多"。

**更关键的一点：眨眼的输入本身就是离散事件**（闭 / 开），不是连续信号。对离散事件固定响应完全够用 —— 物理每次算出来的也一样，那不如直接摆好看。这是这条做法能成立的根本原因。

单调的缓解手段是标准游戏做法：**做 2~3 个变体（轻 / 中 / 重）+ 按强度参数混合**。`HoBlinkConstraint` 当年算 `blinkSpeed` 想要的就是这个效果，用变体就能拿回来，而且比调物理参数确定。

### 13.5 那组"果冻步"键不一定需要美术 —— 一个降低门槛的做法

成熟做法在**"眼睛闭上"时触发**，这个前提很巧妙：**那时眼睑的追踪值本来就 ≈ 0**，所以 Override 播放不会和追踪信号打架。

顺着这条推下去，其实不必非要专用键：

| 方案 | 需要什么 | 效果 |
| --- | --- | --- |
| **A1. 专用果冻键**（成熟做法） | 美术在模型里做 `JellyEye 1..N` | 最好：整个眼周都能摆 |
| **A2. 在闭眼区间覆盖眼睑键** | **不需要美术资源** | 眼睑自身的摆动；仍是"过冲→回弹→稳定" |
| ~~B. 物理弹簧~~ | —— | 已定不要（HoBlink 退役） |

**A2 把"需要美术"这个前提解除了**，代价是摆动只能作用在眼睑键上（眼周其它部位无专用键可用）。

### 13.6 物理不是不要，是分工不同

`HoBlinkConstraint` 那个小弹簧确实没必要 —— 但**不等于物理没用**。按"驱动来源是离散还是连续"划分：

| 驱动来源 | 适合 | 为什么 |
| --- | --- | --- |
| **离散事件**（眨眼、表情切换） | **作者的动画** | 输入是二值的，固定响应就够，并且可控、可确定性解释 |
| **连续信号**（头动、身体动、扫视） | **物理（摆锤 / 弹簧）** | 输入连续、必须随输入变 —— 这才是摆锤的用武之地 |

这不是我们自己的发明，三边都一样：

- **Live2D**：[物理演算](https://docs.live2d.com/en/cubism-editor-manual/physics-operation/)是「输入参数 → 输出参数」带摆锤设置；而眨眼走[眨眼设置](https://docs.live2d.com/en/cubism-editor-manual/eye-blink-settings/) / [自动眨眼 SDK](http://docs.live2d.com/cubism-sdk-manual/autoeyeblink/)，**不是物理**。
- **VRC 商品**：果冻是步进动画（13.1），而头/身体交给 VRChat 自己的物理骨骼。
- **Warudo**：摆锤节点（我们仓库里也有 `HoPendulumConstraint`）。

**所以中间层该不该产生"摆锤物理参数"？该，而且就该由中间层自己实现摆锤。**

> **修正：本节原先写"这条通路在 Warudo 那边天然就是「摆锤节点 → 平滑节点」"是错的。**
> Warudo 的摆锤写得很死，**不能把摆锤搬进节点图**。所以"把物理当作外部来源接进中间层"这条路
> 在两个宿主上都走不通：VRC 侧需要曲线驱动参数（没有），Warudo 侧摆锤不可编排。
>
> 把物理"剥离出去"本来也是没必要的 —— **摆锤就是一维的东西，几行就能写**：
> 阻尼谐振子 `x'' = -ω²(x − target) − 2ζω·x'`，每帧积分，加个子步保稳定。
> 而且它是确定性的，正好能被自动化用例验证（阶跃响应必须过冲、必须收敛）。

中间层的位置因此是：**自己实现这一维物理，产出"带物理的参数"**。

### 13.8 收敛后的果冻设计：物理产参数，混合树消费参数

```
眼睑信号（连续的一维量）
  → 中间层的 1-D 物理（阻尼弹簧 / 摆锤，两个轴两个频率）
    → 产出带物理的参数  Ho/JellyX · Ho/JellyY（连续、会过冲、会回弹、有符号）
      → 果冻混合树（2D FreeformCartesian，混合树小工具建，见 13.15）
         子节点 = 用户自己选的形态键 × 自己摆的位置
        → 驱动模型上的果冻眼形态键
```

**为什么"树"而不是"片段"**：树是**参数的函数**，没有时间轴 —— 参数过冲，姿势就过冲；参数回弹，
姿势就回弹。片段是把时间烤死的，物理算出来的轨迹没法塞进片段里（13.13）。

**为什么"树"而不是"脚本直接写键"**（我原先的提议，被否掉）：

| | 映射住在哪 | 用户能改吗 | 依赖 |
| --- | --- | --- | --- |
| 脚本直接写键 | 组件的字段里 | 只能改数字，看不见结果 | 绑死我们的 C# |
| **混合树** | **控制器资产里** | **能，且是"用户面对的最高级东西"** | 只依赖两个 Float |

而且"一族形状 × 一个二维参数"本来就是混合树的标准用法 —— 这是它被发明出来的场景，
不是绕路。

| 做法 | 形状（好看） | 随输入变化（有物理感） |
| --- | --- | --- |
| 纯作者动画（Shinano，步进状态机） | ✅ 美术摆的 | ❌ 每次一样 |
| 纯物理写键（旧 HoBlink） | ❌ 只能"差不多" | ✅ |
| **物理产参数 + 混合树消费** | ✅ | ✅ |

**这也是为什么用户说"驱动动画的参数需要是一个带物理的东西"是对的**：参数负责"每次都不一样"，
树的形状负责"每次都好看"。

**目标键已经有了**：用户的头模型上已经做了一批果冻眼形态键，所以走 **A1（专用键）**，
小工具（13.15）负责把它们编排成一棵混合树 —— 不再需要 A2 那条退路。

> **后续修正（见 13.11）**：不固定键名。UI 改成输入**网格列表**、由用户手动选键。
> 另外"几个动画"的答案也在这里更新了 —— 参考实现只有 1 个，我们是 2 个，理由见下。

### 13.11 几个动画？参考实现是 1 个，我们应该是 2 个

把四个商业包全扫了一遍，结果有点意外：

| 包 | 名字带 Jelly 的资产 |
| --- | --- |
| Shinano v1.32 | **1 个**（`JellyEye.anim`） |
| Mafuyu / Manuka / kipfel | **0 个** |

**果冻不是这些商品的标配，只有 Shinano 一家做了。** 而它的做法是：

- **1 个片段**，通过**步进状态机**播放（`JellyIdle → Step 1 → Step 2`），**不是混合树混合**。
- 那个 `Blink_JellyEye` 参数**还有第二个职责：当抑制开关**。它在别人家的树上把会让画面破的
  表情压掉 —— `MouthStretch Limit`（Y 轴 = `Blink_JellyEye`，果冻一开就换成 `_EmptyAnimation`）、
  `Jaw Open`（`Blink_JellyEye` 到 0.8 就切走）。也就是说**果冻开的时候嘴部拉伸和下颌要收住**，
  否则脸会崩。

**我们应该是 2 个，而且这是"物理产参数"这套设计的必然结果：**

```
Ho/Jelly 是 0..1 的连续量（物理给的）
  → 一棵 1D 树在它上面插值
    → 两个端点：Jelly 0（中性） / Jelly 1（果冻全开）
```

**为什么 2 个就够、不需要 4 个**：抖动的**时间形状**（过冲、回弹、稳定）已经由物理提供了，
**动画只需要提供姿势的两个端点**。参数来回振荡，两个端点之间就被动地来回插值 —— 抖动是这么
来的。做 4 个反而是在拿动画重复物理已经做过的事。

对照参考实现：它只有 1 个片段、靠步进状态机给出"固定的时间形状"；我们把时间形状交给物理，
所以需要的是"两个姿势端点"，而不是"一段序列"。**同样的视觉效果，我们是参数化 + 可调，它是写死的一段。**

**要一并照搬的还有那个抑制职责**：果冻开启时，`mouthStretch*` / `jawOpen` 这类会互相破相的键
要收住。这一步在生成物里体现为果冻树上的一层限制（对应它的 `MouthStretch Limit`）。

### 13.12 参考实现的抖动是"画"出来的 —— 以及"两个"到底指哪个轴

把 `JellyEye.anim` 的曲线值拉出来看，结论修正了 13.11 的一部分推断：

> **每条曲线自己就是一整段约 2 秒的衰减振荡**（`0 → 10 → 85 → 0 → 65 → 5 → 25 → 0 …`，
> 振幅递减），36 个关键帧；`JellyEye 1..5` 是 5 条这样的曲线。

**所以抖动是直接画在片段里的时间序列，它根本不需要物理。** 这就是它用步进状态机的原因：
触发即播一段已经画好的抖动。

这带来一个清晰的分工对比：

| | 时间形状（过冲/回弹） | 姿势 | 美术工作量 |
| --- | --- | --- | --- |
| **参考实现** | **画在片段里**（36 帧 × 5 曲线） | 同一段片段 | 大：要手绘衰减曲线 |
| **我们的做法** | **物理给**（`Ho/Jelly`） | 片段只给端点/方向姿势 | 小：只要摆姿势 |

**"两个"指的是哪个轴** —— 这是两个不同的设计，别混：

| | 轴 | 内容 |
| --- | --- | --- |
| 我先前说的 | **强度** | `Jelly 0`（中性） ↔ `Jelly 1`（全开），一棵 1D 树插值 |
| **用户提的** | **方向** | 竖向抖动 / 横向抖动，两个方向各自一个弹簧 |

**方向轴更灵动，而且可行**：两个弹簧给不同频率 → 两个参数 `Ho/JellyX` / `Ho/JellyY`；
方向姿势按位置摆在参数空间里（四角 / 四方向 + 原点），由一棵 **2D FreeformCartesian 树**
把 `(X, Y)` 映射成姿势。因为两个参数频率不同，`(X, Y)` 在参数空间里走出的路径是一条
Lissajous 曲线 —— 读起来像有机运动，而不是一根直线来回。

> **早期这里写的是"用 Direct 树相加"，不成立**：Direct 树对同一个属性的多路写入不是相加
> （见 13.15 第 3 条）。而且"空 ↔ 单向峰值"两条 1D 曲线各自写一半，本身就凑不出二维空间 ——
> 一棵 2D 树才是这件事的正确工具。

每个方向写**全部**键（没摆权重的写 0），参数为 0 时靠原点子节点归零；
静止姿势由原点子节点（写 0）保证，不靠模型默认值 —— 那样会跟别的写入者打架。

代价：美术要出**两个方向的峰值姿势**（用户已经有那批果冻键，手工选键即可）。
收益：从"1 个方向、每次一样"变成"两个方向叠加、随输入走 Lissajous"。

### 13.13 先纠正一处：「动画不会倒着走」只对"播片段"成立，对混合树不成立

用户担心：物理参数是来回振荡的，而**动画不会倒着走**，所以"真物理参不适合动画驱动"。

**这句话对一半，而那一半恰好不是我们说的那个方案：**

| 消费方式 | 参数来回振荡时会怎样 |
| --- | --- |
| **播一段片段**（时间轴） | ❌ 确实不会倒着走 —— 时间轴只有一个方向 |
| **混合树**（参数的函数） | ✅ **可逆**：参数回到 0，姿势就回到 0；参数过冲，姿势就过冲 |

**混合树不是"播一段动画"，它是"参数 → 姿势"的映射**，没有时间轴。所以 `Ho/JellyX/Y`
驱动一棵 Direct/2D 树（每条方向从"空"到"峰值"插值）时，参数来回振荡 → 姿势来回振荡，
**这正是我们要的抖动**，不存在"倒着走"的问题。

也就是说：**"物理参 → 混合树"这条路是通的**，前面 13.8/13.12 的设计没有被这个理由否掉。

### 13.14 定案：物理产参数 → **混合树**消费 → 用户自己的键

先记一段被否掉的提议，免得半年后重新提一遍：

> **被否掉的提议**：消费端改成"直接写键" —— 组件里配 `网格 + 形态键 + 方向权重`，会话每帧写。
> 理由是"这属于运行时覆盖那一类，不落盘，符合契约"。
>
> **为什么否掉**：映射关系（哪张脸的哪个键、往哪个方向摆多少）是**形状数据**，不是调参。
> 塞进组件字段里等于把它藏进一个看不见结果的地方；而它恰好就是混合树的标准用法。
> "不写盘"省下的是**生成资产的麻烦**，代价是用户永远看不到、改不动那片映射 —— 不划算。

**最终分工**：

| | 谁负责 | 落在哪 |
| --- | --- | --- |
| 物理（过冲 / 回弹 / 两轴不同频） | 我们的 C#（会话） | 组件配置 + 每帧写两个 Float |
| 映射（键 × 方向 × 权重） | **混合树** | 控制器资产里，用户可看可改 |
| 建树 + 建片段 | **混合树小工具**（13.15） | 点按钮才写盘 |

**参数空间 [-1, 1]**：`0` = 静止，`+` = 挤压（过冲会顶到 1），`−` = 回弹。有符号是必需的 ——
眼睑是一段脉冲输入，弹簧必然回弹到 0 以下；夹到 `0..1` 会把整个回弹削掉（这条已经在会话里修掉）。
形状键权重本身仍然 ≥ 0：树在子节点权重上归一化，负的只是**参数**，不是键值。

### 13.9 原则：不依赖宿主自身的、进不了蓝图的东西

用户定的原则（比 13.6 我那个定位更强）：

> **进 Warudo 时不依赖 Warudo 自身的东西 —— 尤其是进不了蓝图的那些。**

它的实际含义：整条管线需要的每一段，都必须能在**每个宿主的"最低公共表达"**里写出来：

| 宿主 | 能表达什么 | 不能表达什么 |
| --- | --- | --- |
| Unity 调试后端（我们的） | 全部（C# 随便算） | —— |
| **Warudo 蓝图** | **节点 + 每帧 + 有状态**的参数运算（**已经有"参数平滑节点"**） | Warudo 自己的摆锤（写死的，进不了蓝图） |
| VRC | 图层 + 树 + 转移条件 | 曲线驱动参数（已推迟，见 14 节） |

这条原则直接**堵死了"把物理交给外部来源"**这条路：

- Warudo 的摆锤**不可编排** → 用不了；
- 所以那一维物理**必须是我们自己的算法**，只是按宿主 lower 成不同形态（Unity = C#；Warudo = 蓝图节点）。

**好消息**：Warudo 已经有"参数平滑节点"，说明蓝图**能表达「每帧 + 有状态」的参数运算** ——
而平滑是一阶、弹簧是二阶，是同一类东西。所以一维弹簧在蓝图里**大概率可表达**。

**但这一条现在验不了**：仓库里目前只有角色 mod 的构建工具，**蓝图 mod 的工具还没做**，
所以 Warudo 侧既没有节点基建、也没有可对照的产物。要真正确认，得等蓝图工具落地，
或者去查 Warudo 的节点清单（本机装了 Warudo，但不在本仓库范围内）。

**因此实施上的纪律**：在做第 1 步（一维物理）时，**把状态显式化、把单步积分抽成独立函数**，
不要把它埋进 Unity 的事件回调里。这样它才是一份可以被搬运的**算法**，而不是一段绑死在这个
宿主上的代码 —— 和"四段流水线"对中间表示的要求是同一条纪律。

### 13.10 决定：Warudo 只当"面部参数入口"，不用蓝图

用户：**不信 Warudo 蓝图了，只愿意使用它的面部参数入口。**

这条**消掉了 13.9 里那个未验证的假设**（蓝图能不能表达弹簧）—— 不需要了。而且它是可行的：

> **仓库里本来就有在 Warudo 里跑的 C# 组件。** `HoWarudoRuntimeHub` 是一个 MonoBehaviour
> （带运行时 IMGUI 窗口），`IHoWarudoRuntimeModule` 是它的模块接口。Warudo mod 本身就是
> Unity 程序集，所以我们的中间层（**含那一维物理**）在 Warudo 侧也是**我们自己的 C#**。

于是物理只需要一种实现：

| 宿主 | 中间层跑在哪 | 物理跑在哪 |
| --- | --- | --- |
| Unity 调试后端 | 我们的会话（影子台） | C# |
| **Warudo** | **我们的 C# 组件 + 打进 mod 的 Animator/Controller** | **C#** |
| VRC | 已推迟（14 节） | —— |

**副作用**：13.9 那条"必须写成宿主无关的算法"**不再必需**。把单步积分抽成独立函数仍然值得，
但理由从"为了搬到别的宿主"变成"为了可测"—— 一个纯函数式的 `Step(ref state, target, dt, …)`
能被自动化用例直接喂阶跃、直接断言过冲与收敛，这比在事件回调里跑一遍动画去观察可靠得多。

### 13.7 果冻动画生成小工具（**已砍掉**）

> **这一节作废**，被 13.15 的混合树小工具取代。保留原文只为记录"为什么当初会想这么做"：
> 当时假设消费端是**步进动画**（照抄 Shinano），于是需要按参数生成一串片段。
> 改成混合树之后，"生成动画"这件事整个消失了 —— 树只需要每个方向**一张静态姿势的片段**，

当时的设想（作废）：按参数生成步进的果冻片段，参数化步数、每步幅度、衰减率、总时长、目标键。

### 13.15 落点：混合树小工具（**已搁置**）

> **搁置（决策，不是待办）。** 用户：**"我们做的太着急了"** —— 工具该长什么样，取决于
> "混合树在编辑器里到底怎么工作、它被设计出来是给谁用的"，而这个前提**还没看**。
> 所以工具**先不做**：代码留着（`HoFaceBlendTreeWindow` / `HoFaceBlendTreeTool`，用例在跑），
> 但不再往下加功能；等把混合树的交互与设计意图看明白，再回来定它的形态。
>
> **别把它当成"差一点就完成"的功能继续推**：它现在有三版反复（去掉折叠→改回来→搬网格列表），
> 每一版都是在没有那个前提的情况下猜的。这正是"太急"的表现。

原设计意图（保留，未作废）：

**一个通用的"快速建混合树"小工具**，果冻只是它的第一个用法。

| | |
| --- | --- |
| 输入 | 目标控制器 + 图层名 + 参数对（X / Y） + **网格列表** + 手动选键 |
| 每个方向 | 一个位置 `(x, y)` + 每个键的权重（0–100） |
| 产物 | 每个方向一张静态片段（写满那些键）+ 一棵 2D FreeformCartesian 树 + 一个图层 + 参数 |
| 预览 | 两个滑条直接推参数，播放中就能看到键被混成什么样 |

**三个必须做对的地方**（都会做成工具的默认行为）：

1. **原点子节点。** 2D 混合树对权重做归一化 —— 只放 `(±1, 0) / (0, ±1)` 四个子节点，
   参数在 `(0, 0)` 时得到的是四个姿势的平均值，**静止时脸上就挂着一个固定的形变**。
   必须在 `(0, 0)` 放一个写零的子节点，静止才是精确的静止。
2. **参数对先建好。** 缺就建（Float），类型不对就报错，不静默。
3. **键冲突要提示。** 同一个键如果已经被 `Ho/00 Drive` 那棵树驱动，两棵子树就都在写它 ——
   结果一定是**互相掺和**，不是相加。具体掺法（按权重平均还是后者覆盖前者）**我们没实测**，
   但这已经足够支持"别这么用"：果冻应该驱动**自己的**键（Shinano 用的就是一个专用的 `JellyEye`）。

### 13.16 顺带暴露出来的一个真 bug：输出过滤不能按"名字是不是 ARKit"来

影子台**只把 `Compile` 认可的键抄回真模型**。原来这一步的条件是"这个名字是 52 个 ARKit 键之一
+ 有通道映射 + 该区已开"。用户的果冻键（`JellyEye`）一条都不满足 —— 于是：

> **果冻层在影子里算得好好的，脸上一动不动。**

改法：**门控只管 ARKit 键，非 ARKit 键直接放行。**

| | 该由谁回答 |
| --- | --- |
| "我们**写哪些参数**" | 输入门控（区开关 / 通道映射 / 有没有实时数据） |
| "控制器**能动哪些键**" | 控制器自己（那是用户资产里的映射） |

两者本来是两个问题，塞进同一个 `if` 就会产生上面这种"看着在跑、其实没到"的故障 ——
而且它不报错、不警告，只是没效果。用例里加了一条正面断言把它钉住。

**副作用（可接受）**：用户往这个控制器里塞的别的形态键曲线也会被一起抄回去。
这本来就是"这份控制器拥有它动过的脸键"的正确语义；代价是如果往面捕控制器里塞身体动画，
身体网格会被拉进影子台 —— 那属于超出契约的用法。

## 15. 「初始化」与「应用」：两个动作，语义必须分开

命名承载语义。**「生成」听起来可重复、无害**，于是用户会以为可以随便点；但这一步产出的是一个**完整文件**，而之后所有手工改动都在这个文件里 —— 点错一次就全没了。所以：

> **它叫「初始化控制器」，而且只应该在开始时点（或明确决定推倒重来）。**

| 按钮 | 什么时候点 | 语义 | 破坏性 |
| --- | --- | --- | --- |
| **初始化控制器** | **只在开始时**，或明确决定重来 | 从「源控制器 + 配置」产出**一个完整文件** | **破坏性**：覆盖目标文件，里面的手工修改全丢 |
| **应用改动 (N)** | 之后每一次改结构 | 就地手术，只重写 `Ho/` 段 | 非破坏性（保留 `(EDIT THIS)` 段） |

按钮形态应该跟着状态变，让危险性自己说话：

- 组件上**没有**控制器 → 主按钮「**初始化控制器**」。
- 组件上**已有**控制器 → 主按钮变成「应用改动 (N)」，而「重新初始化…」降级为次要按钮 + 警告样式。**没有未应用改动时，应用按钮禁用并显示「已是最新」。**

### 15.1 现状有三处要改（核对代码发现的）

1. **现在拒绝覆盖** —— `HoFaceAnimationAssets.Generate` 里写着「目标资产已存在，请选择新路径」。这跟"让用户知道自己会覆盖一个完整文件"正好相反：用户改不了源、只能文件越生越多，旧的手工修改被搁浅。应改成**允许覆盖，但用确认对话框把代价说清楚**，并默认提供「另存为新文件」这条安全出路。
2. **现在会静默重置组件配置** —— `Generate` 里有 `rig.channels = HoFaceTrackingChannels.CreateDefaults()`。这正是新契约禁止的隐式修改：初始化不该动组件配置。真要补默认通道，应该**只补齐缺失的、不覆盖已有的**。
3. **名字**要从「生成 ARKit 控制器」改成「初始化控制器」，并按上面的规则变成状态相关的按钮。

### 15.2 初始化对话框必须说清三件事

1. **目标路径** —— 完整、可见、可复制。不要只说文件名。
2. **会失去什么** —— 文件已存在时，尽量算出具体代价（例如「该文件里有 3 个非 `Ho/` 层、12 个手工状态」），而不是笼统的"将被覆盖"。
3. **安全出路** —— 默认给「另存为新文件」，让"我想重来但不想丢旧的"有地方去。

### 15.3 一个可选但值得做的加固：生成指纹

在控制器里存一个隐藏标记，记录"上次生成时的配置摘要 + 生成段内容摘要"。有了它，两个需求一次满足：

- **手改检测**：应用/重新初始化前比对生成段，不一致就警告「生成段被手工改过，应用会覆盖它」。
- **未应用计数**：配置摘要与当前组件配置比对，直接得出「有 N 项未应用」，不用额外维护一份状态。

第一版可以不做；但一旦用户开始手工改树（这正是这套设计的目的），没有它就只能靠"名字里写了勿改"这种君子协定。

## 16. 下一步：区域划分与开关（先把设计前提钉住）

用户定的方向：**我们的 ARKit 驱动层现在是"裸的直出"**（52 个键平铺在一棵 Direct 树里），
商品资产是**分区域 + 带开关**的。我们只有一个输入（iFacialMocap 的 ARKit），不需要它们那套
多输入适配，但**区域划分和开关要做**。

### 16.1 参考实现确认过的形状

驱动层 = 一棵 Direct 根树，根的子节点是**区域子树**，每个区域子树挂一个**区域参数当权重**，
叶子才是形态键片段（`direct=ARKit/<键>`）。区域参数是 **Float（默认 0）**，不是 Bool：

```
└ Direct 根
  └ 眼睑   direct = EyeTrackingActive     ← 区域权重
      └ 叶子片段 direct = FT/v2/EyeLidLeft
  └ 嘴唇   direct = LipTrackingActive
  ...
```

已知的区域门控参数：`EyeTrackingActive`、`LipTrackingActive`（另有 `State/TrackingActive` Bool、
`RemoteModeActive`）。**这条正好把我们现在的做法否掉了**：我们切区域是靠 C#
在编译时剔除片段（`Compile` 的 outputFilter），也就是"开关一拨就重编译"——那是**结构**，
而别人是**参数**。按我们自己的规矩（能做成参数的就不要做成结构），这一处要改。

### 16.2 「双眼同眨」：他们的开关叫 `EyeSync`

用户描述的模型侧事实：**有些模型的左右眨眼键都是"双眼眨"键**（美术为了避免两只眼睛闭合程度
不一致就这么做了）。于是左右两个通道一起触发时，同一个形变被写两遍 → **过眨眼**。
需求是：非 wink 情况下把两侧强行并成一个值。

在参考工程里找到了对应的开关（`adjerry91.vrcft.templates-7.0.3 / FX - Face Tracking - Shared.controller`）：

| 参数 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `FT/EyeSync` | Float | **0** | 0 = 左右独立（允许 wink）；**1 = 强制同眨**。1D 树，Min 0 / Max 1，非自动阈值 → 是**交叉淡入**，不是 Bool |
| `FT/EyeSyncMix` | Float | **0.5** | 同眨分支内部的**合成配比** |

作用范围是**两处**：`EyeSync EyeLids`（眼睑）与 `EyeSync In/Out`（眼球横向）。
**眼球纵向 `EyeY` 没有被包进去** —— 这一点值得照抄，因为它说明作者只对"左右会打架"的那两条轴做了同步。

### 16.3 但它的实现方式我们不能抄

把 `EyeSync ON` 那几棵子树拆开看（`.research/inspect_eyesync.py` + `eyesync-report.txt`）：

- 结构是**嵌套 Direct 树**套了好几层，子节点上残留着一批用不上的 `thr=`（说明它早期是 1D 树，
  后来改成了 Direct，阈值没清）；
- 更关键：`FTv2EyeLidLeft1Proxy.anim` 这类"片段"**根本不写形态键** —— 它们的曲线绑在
  `attribute: OSCm/Proxy/FT/v2/EyeLidLeft`（空路径）上，是**曲线驱动参数**（VRChat 客户端特性），
  另有一条绑在组件属性上的锚（`path: 0` / `attribute: <hash>`）供 Unity 侧跑。

也就是说：**`EyeSync` 的机器是"参数空间里的反馈回路"**，它必须绕这一圈，因为 VRChat 没有脚本基底。
**我们有 C#**，同一件事就是几行算术（合并左右两个值），不需要那套嵌套 Direct 树，
也不需要那个我们本来就推迟了的曲线驱动参数桥（见 14 节）。

**要沿用他们的语义（名字 / 默认值 / 0..1 交叉淡入 / 作用在眼睑与眼球横向），不要沿用他们的结构。**

### 16.4 待定（要用户拍板才能动手）

1. **区域粒度**：用我们已有的五个（嘴 / 眉 / 颊鼻 / 眼睑 / 眼球），还是照参考实现更细
   （它有独立的舌、下颌段）？
2. **区域参数命名**：`Ho/Gate/...` 自己的命名空间，还是直接用生态名
   （`EyeTrackingActive` / `LipTrackingActive`）？VRC 后端已推迟，所以现在用生态名没有直接收益。
3. **双眼键的两种模型**：
   - **左右分开**（每个键管自己那只眼）→ 分别驱动，允许 wink；
   - **单键双眼**（一个键，或左右键都是"双眼"键）→ 合成一个值。
   第二种里"到底是只驱动一个键、还是两个键都驱动但都减半"，取决于美术怎么摆的，
   这一条要问清 —— 写错就是过眨眼，而它**不报错**。

### 16.5 Shinano 的层结构：开关是独立层，但实现是 VRC 专有行为

用户指出的两点，核对 `FX_FT_added 2.controller`（`.research/inspect_layers.py`）都成立：

```
[0] Eye Tracking State    状态: InStation / Eye Tracking Off / AFK / Idle / Eye Tracking On
[1] Lip Tracking State    状态: Lip Tracking On / Lip Tracking Off / AFK / InStation / Idle
[2] FacialTracking        一个状态，动作 = Face Tracking Root（那棵巨型树）
[3] JellyEye              JellyIdle / Step 1 / Step 2
[4] QPro_Toggle · [5] AFK-FT Control
[6] _OSCmooth_Binary_Gen（Binary_Root） · [7] _OSCmooth_Smoothing_Gen（OSCm_Local / OSCm_Remote）
```

**区域开关确实是独立的动画层**（[0] [1]），面捕层 [2] 与果冻层 [3] 也是分开的。

**但那两层开关的"动作"是空的** —— 真正干活的是挂在状态上的 **StateMachineBehaviour**，
按序列化字段认出来是 VRChat SDK 专有的两个：

| 字段签名 | 是什么 | 干什么 |
| --- | --- | --- |
| `trackingHead` … `trackingEyes` / `trackingMouth` / `debugString` | `VRCAnimatorTrackingControl` | 按部位关掉追踪 |
| `parameters[{type,name,value,localOnly,…}]` / `localOnly` / `debugString` | `VRCAvatarParameterDriver` | 驱动 `EyeTrackingActive` / `LipTrackingActive` |

所以：**开关层的"形状"值得抄**（每个区域一个二状态小开关 + AFK / InStation 守卫；
区域参数由开关层产出），**但实现抄不了** —— 这两个行为在纯 Unity 里不存在，
而且我们的 `Compile` 现在明确**拒绝** StateMachineBehaviour（`ValidateMachine`）。
在我们这边，区域参数由 C# 生产，开关层的职责并进会话。

**顺带一条设计含义**：用户说 Shinano 的树"极其复杂我其实不太敢动"。这句话本身就是信息 ——
我们的前提里写着"用户面对的最高级东西是混合树"，但如果连看过大量控制器的人都不敢碰它的树，
那"让用户进树加逻辑"的门槛比我原来估的高。生成的树要**刻意保持浅**（Direct 根 + 一层区域子树 + 叶子），
用户的编辑面留在组件上；`(EDIT THIS)` 是逃生口，不是主路。

## 17. 两棵大树拆开看：他们到底在拆什么

材料：`.research/bigtree-jerry.txt`（`FT Blendshape Driver`，22 个子节点）与
`.research/bigtree-shinano.txt`（`Face Tracking Root`），生成脚本 `.research/inspect_bigtree.py`。

### 17.1 形状

**Jerry（ARKit 模板）：平铺 + 隐式归组**

```
[Direct] FT Blendshape Driver           ← 根，22 个子节点，全部平铺
  ├ Right Eye Lid Blend      gate=EyeTrackingActive   内部 FreeformCartesian2D(开合 × 眯眼) 5 姿势
  ├ Left  Eye Lid Blend      gate=EyeTrackingActive   同上
  ├ Eye Look Right/Left Blend gate=EyeTrackingActive  SimpleDirectional2D(EyeRightX × EyeY) 5 姿势
  ├ Brow Inner/Outer/Down …  gate=EyeTrackingActive   ← 眉归**眼**区
  ├ Nose Sneer / Cheek Puff  gate=LipTrackingActive   ← 颊鼻归**唇**区
  ├ Mouth … (十余个)          gate=LipTrackingActive
  └ Face Tracking Emulation  gate=FaceTrackingEmulation
       ├ Face Tracking Limits  1D(FaceTrackingLimits) → No Limits / Limits
       └ Brow Angry / Brow Wide / Cheek Squint … Emulation   ← 用别的参数"模拟"模型没有的表情
```

**区域不是物理子树** —— 是把共用同一个 gate 参数的语义单元摆在一起，隐式归组。

> 拆树时顺手校正了一处：Unity 序列化里的 `m_BlendType` 是
> `0 = Simple1D / 1 = SimpleDirectional2D / 2 = FreeformDirectional2D / 3 = FreeformCartesian2D / 4 = Direct`
> （早期报告把 0/1 标反过）。两家实际只用了 0 / 1 / 3 / 4 这四种，`FreeformDirectional2D` 一次都没出现。

**Shinano（8 层控制器里的 `FacialTracking` 层）：逐层收窄**

```
[Direct] Face Tracking Root              ← 根**只有 2 个子节点**
  ├ EyeTracking Active   gate=EyeTrackingActive   1D(EyeTracking_GestureControl)
  │    └ Eye BlendSet        gate=GestureLeftWeight   ← 模式适配层（手势）
  │        ├ Eye Look Left/Right Blend   SimpleDirectional2D(X × Y)，9 个姿势含四个斜向
  │        ├ Eye Lid LR Sync             1D(Eye Lid LR Sync) → {LR BlendSet | Sync BlendSet}
  │        ├ Brow Pinch BlendSet / KemoEar（兽耳挂在这里）
  │    └ _EmptyAnimation  thr=1                              ← 清空 / 回退
  └ LipTracking Active   gate=LipTrackingActive   1D(LipTracking_GestureControl)
       └ LipTracking BlendSet  gate=GestureLeftWeight
           ├ Mouth,Jaw Limit → Mouth X Limit → _EmptyAnimation        ┐
           ├ JawOpenLimit_LU → JawOpenLimit_LL → JawOpen 0.anim       │ 抑制链
           ├ LipFunnel Limit 1 → Limit 2 → _EmptyAnimation            │
           ├ LipSuckUpper → LipSuckLower Limit                        ┘
           ├ Mouth Sad Smile Left/Right、Nose Sneer、Cheek Puff、Ear Sad
           └ MouthDefaultCorrection  (Direct, 9 个子节点)  ← 基础表情回退
```

**同一件事，两种写法。** Jerry 平铺（好读、好改、但区域关系是隐式的）；
Shinano 逐层收窄（根只分两大区，每层只回答一个问题，但深度上去了、也就没人敢动）。

### 17.2 抽出来的六个设计模式

| # | 模式 | 他们怎么做 | 我们 |
| --- | --- | --- | --- |
| 1 | **区域门控** | 共用 gate 参数：`EyeTrackingActive` / `LipTrackingActive`（Float 默认 0） | **要抄**（把 C# 编译期剔除改成参数） |
| 2 | **两级参数** | 外部开关 `EyeTrackingActive` → 平滑代理 `FT/EyeTrackingActive` | 要抄"外部/内部两段"这个区分 |

| 4 | **左右同步** | 三种落地：独立小树 `Eye Lid LR Sync`（Shinano）／双向参数 `Mouth X Blend`（`-1..1` 一棵 1D 树，Jerry）／`EyeSync`+`EyeSyncMix`（Jerry，眼睑+眼球横向） | 要抄（见 16.2） |

### 17.3 一条我们现有分组是错的

Jerry 里**眉挂 `EyeTrackingActive`**（`Brow Inner Up` / `Brow Outer Up` / `Brow Down` 全是），
**颊鼻挂 `LipTrackingActive`**。也就是说语义分区是：

```
Ho/00 Drive (Direct)
  ├ 眼睑   gate = EyeTrackingActive        ← 区域门控（参数，不是编译期剔除）
  │   ├ 左眼睑 2D（开合 × 眯眼）
  │   ├ 右眼睑 2D（开合 × 眯眼）
  │   └ 左右同步（EyeSync：分开 / 同眨）
  ├ 眼球   gate = EyeTrackingActive
  │   ├ 左眼 SimpleDirectional2D（X × Y）
  │   ├ 右眼 SimpleDirectional2D（X × Y）
  │   └ 左右同步（只作用横向 In/Out —— 照抄他们的作用范围）
  ├ 眉     gate = EyeTrackingActive        ← 眉归眼
  ├ 嘴     gate = LipTrackingActive
  │   ├ 各语义单元（1D / 2D）
  │   ├ 抑制链（例如 jawOpen 大时收住唇形）
  │   └ 回退（嘴部参数接近 0 时撑基础表情）
  ├ 颊鼻   gate = LipTrackingActive        ← 颊鼻归唇
  └ (可选) 附加部件挂载点（兽耳等）
```

**每一层只回答一个问题**：第一层"哪个区域算数"，第二层"这件事是几维的"，
第三层才是具体的键。这正好是用户说的"按语义拆开之后，用户才能精确做设计"。

### 17.5 为什么拆开之后才有自动化工具的可能

- 现在是"一棵 Direct 根 + 52 片叶子"，**没有任何中间结构可以被工具指认**：
  想"把眼睑整体改成 2D"或"给嘴加一条抑制"，工具找不到落脚点，只能重建整棵树。
- 拆成语义单元之后，每个单元都是**一个有名、有参数、有维度的子树**，
  于是"批量改维度""给某个单元加抑制""把某个单元复制到另一个角色"都变成了**对节点的操作**。
- 也就是说：**先有语义结构，工具才有可操作的对象**。这是"先拆树、再做工具"的顺序理由 ——
  反过来做（先做通用混合树工具）就会像 13.15 那样，工具长得像什么全靠猜。

### 17.6 一个会改变设计的区别：「关掉区域」和「压回中性」不是同一件事

拆他们的树时发现 `MouthDefaultCorrection`（Shinano）和 `Face Tracking Limits`（Jerry）都长在
**gate 旁边**，而且都是"参数接近 0 时把基础表情撑回来"。顺着这条想下去，会撞到我们自己的一个区别：

| | 含义 | 结果 | 我们怎么实现 |
| --- | --- | --- | --- |
| **关掉区域** | 这一段驱动**不算数** | 那些键回到**基础动画**（角色的表情还在） | 释放键的占用（现在就是这样：编译期过滤 → 不在 `owned` 里 → 不抄） |
| **压回中性** | 这一段**还在驱动**，只是值为 0 | 那些键被写成 **0** —— 基础动画的表情被抹掉 | 树的权重 / 参数为 0 就是这样 |

**关键点：Write Defaults 开着时，权重 0 写的是"默认值"（影子上的 0），不是"交还给基础动画"。**
所以**不能拿树的 gate 权重去实现区域开关** —— 那会把脸压成没有表情，而不是让基础表情回来。

他们那边之所以必须做 `MouthDefaultCorrection`，正是因为**他们的 gate 只能压回中性**：
面捕层本身就是脸的主人，压回中性就没人撑基础表情了，只好再写一层"参数为 0 时把基础表情
补回来"的树。

**我们的影子架构在这件事上是有优势的**：释放占用就等于交还，基础表情自动回来
（"面捕没拥有的键在构造上就不可能被影响"）。所以：

1. **区域开关 = 释放占用**，语义是"交还"，不该做成树的权重。
   —— 注意这**不是**写盘的结构变更：`Rebuild()` 只是重编译影子上的临时 OverrideController，
   磁盘上的控制器一个字节都不动。所以"改成参数"这条对区域开关**不成立**，
   16.1 里"我们把区域做成了结构"那个判断要按这一条修正。
2. **回退（Correction）仍然要做**，但它是另一件事：**在我们拥有的键上**，参数接近 0 时
   不要把基础表情压掉。这才是 `MouthDefaultCorrection` / `Limits` 在我们这边的对应物。

> **实测（`HO_WDZERO`，探针台不经过我们的会话，直接问 Unity）：**
>
> | 提问 | 结果 |
> | --- | --- |
> | 被状态里的片段**以权重 0** 写着的属性 | **保持 33，没被碰** —— 权重 0 ≠ 写 0 |
> | 不在状态任何片段里的属性（对照） | 保持 33 |
> | 同一个属性，参数给 0.6（启动时预置 33） | **73.2 = 0.6×100 + 0.4×33** |
>
> 第三条是意外收获，也是最有价值的一条：**WD 开的余项 `(1-Σw)` 混的是"Animator 启动时捕获的值"，
> 不是硬 0。** 之前探针台量到"精确 60"只是因为那边启动值恰好是 0
> （早先那条"Direct 树 + WD Off 会发散"的判别性实验也顺着这条一起解释通了）。
>
> **由此修正上面那段（我原来写反了）**：
>
> 1. **权重 0 只是"不施加"，不会把属性拉回 0。** 但在我们的影子里这**仍然不等于交还** ——
>    影子代理的值原样被抄回真实模型，所以区域关掉若只把权重压到 0，抄回去的就是影子上的旧值。
>    **区域开关仍然必须是"释放占用"**，这一条不变，理由换了。
> 2. **回退（Correction）不用手写一棵树了**：只要**把影子代理预置成基础姿势**，
>    部分权重就会自然朝它混过去（余项机制白送）。这正是 `MouthDefaultCorrection` 想要的效果。
> 3. 这条同时给出一个**新的设计杠杆**：影子台"预置基础姿势"还是"从 0 开始"，会改变**每一个
>    部分权重**的含义 —— 预置之后 `w=0.8` 的含义是"八成面捕 + 两成基础表情"，不预置就是"八成面捕 + 两成 0"。
>    这是个要用户拍板的设计选择（见 18.6），不是实现细节。

```
ARKit/eyeBlinkLeft ┐
ARKit/eyeWideLeft  ├→  开合 = blink − wide   ∈[-1,1]   →  眼睑左 2D 树
ARKit/eyeSquintLeft┘→  眯眼 = squint         ∈[0,1]
```

这是好事，不是负担：**恰恰是"参数生产"这一段的含义**（第 4 节四段流水线的第②段）。
而且它把"这件事是几维的"这个决定**从树里搬到了 C# 里** —— 用户改维度时不用动树。

### 18.5 抑制链：放 C#，不放树

参考实现把抑制做成树里的 `* Limit` 节点链（`JawOpenLimit`、`MouthStretch Limit`……），
**原因是他们的参数生产做不了条件判断**（只有曲线驱动参数和三段命名那套工具）。

我们的抑制是"参数 → 参数"的函数，按"能做成参数的就不要做成结构"应该落在**参数生产**段：

| 抑制 | 条件 | 收住谁 |
| --- | --- | --- |
| 张嘴时唇形失效 | `jawOpen` 高 | `唇形`（funnel/pucker）、`唇压`、`唇拉伸` |
| 伸舌时嘴部收住 | `tongueOut` 高 | `嘴·唇闭合`、`唇形` |
| 闭嘴时下颌收住 | `mouthClose` 高 | `下颌·开合` |

好处是**树保持浅**（用户只需要面对"单元 + 姿势"），而且抑制可以被纯函数用例直接验收。

### 18.6 回退：靠"影子台预置基础姿势"，而不是再写一棵树

见 17.6 的实测：把影子代理预置成基础姿势，部分权重就会自然朝它混过去。
所以"参数接近 0 时撑基础表情"**不需要一棵 Correction 树**。

但这带来一个**要用户拍板的设计选择**：

| | `w = 0.8` 的含义 | 代价 |
| --- | --- | --- |
| **影子从 0 开始**（现状） | 八成面捕 + 两成 0 | 面捕一压，基础表情就没了 |
| **影子预置基础姿势** | 八成面捕 + 两成基础表情 | 面捕永远压不满；基础表情会"漏"进面捕结果 |

现状是前者，改后者会影响已有断言（例如基础动画写 15、参数 0.8 时，结果从 80 变 83）。
这一条我不擅自改，等用户定。

### 18.7 施工顺序（先结构、后工具）

1. 把上面两张表落成**生成器的输出**（区域子树 + 单元树 + 姿势片段 + 单元参数），
   姿势片段先按"同名 ARKit 键写 100"自动填 —— 这样功能上等价于现在的直通，但结构已经在了。
2. 单元参数在会话里算（18.4），抑制在会话里算（18.5）。
3. 维度、姿势、抑制都成了**可指认的对象**之后，再谈工具（13.15 那个被搁置的），
   以及"给某个单元加一条抑制""把某个单元复制到另一个角色"这类批处理。

## 19. 定案（用户与外部讨论后）：混合树手做、果冻独立、主力转向参数中间层

这一条**撤销/改写了前面几节**，先读这里，再回看 13.14 / 13.15 / 18.7 时要知道它们已被取代。

### 19.1 三句话

1. **混合树由用户手动做。** 用户搞明白混合树之后认为"也没啥"——它本来就是"参数 → 姿势"的函数，
   手摆姿势是最直观的。**我们只提供最基本的设施。**
2. **果冻回到独立组件。** 不再由控制器消费。
3. **主力转向"参数处理中间层"**：平滑、门控、ramp 增益、模式开关等等。

### 19.2 果冻为什么必须是独立组件（用户的论证，比我的更干净）

> 混合树**不能输出带物理的参数**，而且混合树**是状态机里的东西**（状态 → 树）。
>
> 所以：**物理参数的生产跟状态机没关系**（它需要逐帧历史，而状态机是"参数进、姿势出"）；
> 同时它**是纯值消费**（值 → 姿势，无状态），所以**消费场景也不需要待在状态机里**。
>
> 两头都不需要状态机 ⇒ **果冻眼本身就该是一个独立组件。**

这比 13.14 里我绕的那一圈（"VRC 没有脚本基底所以用树，我们有 C# 所以用键"）更本质：
它不依赖"我们有没有 C#"这个偶然条件，而是从**混合树的表达能力**直接推出来的。
换句话说：**果冻进不了控制器，不是因为我们不方便，而是因为它本来就不属于那里。**

### 19.3 由此确定的分工

| | 归谁 | 落在哪 |
| --- | --- | --- |
| 原始输入 | 我们的 C# | iFacialMocap UDP → 52 通道 |
| **参数中间层**（平滑 / 门控 / ramp 增益 / 模式开关 / 轴合并） | **我们的 C#（主力）** | 组件配置 + 会话 |
| **姿势映射**（参数 → 姿势） | **用户手动** | 控制器里的混合树 |
| **果冻**（物理 + 写键） | **独立组件** | 自己的组件，读键 → 弹簧 → 写键 |

### 19.4 被撤销的部分

| 先前结论 | 现状 |
| --- | --- |
| 13.14「果冻由控制器侧的混合树消费」 | **撤销** → 独立组件（19.2） |
| 13.15「通用混合树小工具」 | **撤销** → 它的两个"本质"部件改成生成器的基础件（19.5）。UI 窗口作废 |
| 18.7「先拆树、再谈工具」 | **改写** → 生成器只出**底子**（区域 + 单元 + 空姿势），姿势由用户手摆 |
| `Ho/JellyX` / `Ho/JellyY` 两个生成参数 | **撤销** → 生成器不再产出它们 |

### 19.5 生成器该出的"最基本设施"

用户点名的两件，都是**机械到不值得手点**的东西：

1. **N×N 的 2D 混合树**：给定两条轴上的 N 个位置 + 每个格子的姿势，机械地生成 N² 个片段并摆好坐标。
   眼睑的「开合 × 眯眼」、唇形的「嘟 × 圆」都是这个形状。
2. **把两个 `0~1` 参数合并成一根 `-1~1` 的单轴**，并配一棵三姿势的 1D 树（`-1 / 0 / +1`）。
   这是"双向轴"的标准写法（参考实现里的 `Mouth X Blend`、`SmileSadLeft/Right`）。

**注意第 2 条的两半**：那颗**1D 树**是生成器的活（摆三个坐标 + 三个片段），
而那个 `-1~1` 的**参数值**是参数中间层的活（`正向 − 反向`）——**混合树自己算不出新参数**
（这正是 19.2 的前提）。所以两者要一起交付，否则半截。

落点：`Runtime/FaceTracking/HoFaceAxis.cs`（纯函数，值）+ `Editor/FaceTracking/HoFaceBlendTreeKit.cs`（树与片段）。

## 20. 果冻的落点：`HoSpringConstraint`（弹簧驱动）

### 20.1 命名

| 候选 | 结论 |
| --- | --- |
| **`HoSpringConstraint` / 「弹簧驱动」** | **采用。** 描述的是发动机本身（阻尼弹簧），而"果冻"只是它的第一个预设 |
| 「物理驱动」 | 有歧义：仓库里已有 `HoPendulumConstraint`（液面摆锤）也是"物理"，两个名字会撞 |
| 「果冻约束」 | 用户自己给了退路："没有复用意义的话可以继续叫果冻约束"。但**它有复用意义**（见 20.4） |

### 20.2 模型：**一个组件 = 一根弹簧**

```
HoSpringConstraint
  meshes[]      读和写都在这几张网格上
  keyNames[]    读哪些键，取**最大**（双眼键模型一个键、左右键模型两个键，都能直接用）
  frequency     跟随（Hz）
  damping       回弹（阻尼比）
  gain          输入增益
  targets[]     HoSpringTarget
                  HoShapeKeyTarget  ← 复用眨眼/注视那套输出（增益/ramp/范围/钳制/合并）
                  reversed          ← 吃哪半周
```

**用户定的："多条规则完全可以用户多挂一个组件。"** 于是把原先那层 `Sources` 整个删掉，
并且一路推到底 —— 连"一个组件里放两个自由度"也不要：**果冻眼就是两个组件**（横向 6Hz、纵向 8.5Hz）。

这不是为了省代码，是为了**结构扁平**：组件里只剩两层列表（读哪些键、写哪些键），
没有"规则套自由度套目标"那种三级嵌套。挂组件是 Unity 用户最熟的动作，
而三级折叠的 Inspector 是谁都不想碰的 —— 默认 Inspector 的截图就是证据。

**`reversed` 是这个组件唯一的"新概念"**，而它恰好是果冻的一半：弹簧会过冲到 1 以上、回弹到 0
以下，正向目标吃挤压、反向目标吃回弹。若不做这个区分，回弹会被钳在 0 上，**看不见**。
（驱动映射抽成了纯函数 `HoSpringConstraint.Driver(value, reversed)`，所以这条可以直接断言。）

### 20.3 输入走"读已经落下来的键"（用户拍的 A）

它跟面捕**完全解耦**：不持有会话、不问 ARKit 通道，读的就是网格上那一帧的值。
谁写进去的都行（面捕、基础动画、别的约束），谁先谁后只由执行顺序决定。
另一个好处是**读的和写的可以是同一批键**而不打架 —— 写之前先 `Snapshot()`，
读的时候走"外部基准"（切断自反馈）。

### 20.4 为什么要复用 `HoShapeKeyWriter`

它已经解决了这一整类组件的脏活：跨网格键解析、ramp 预设、增益/偏移、输出范围与钳制、
叠加/覆盖、饱和合并、**恢复原值**、以及**占用表检查**（`HoFaceOutputOwnership` ——
面捕正占着的键它不会去抢）。新组件自己只加了"弹簧"这一层。复用的另一面就是 20.1 里那个结论：
**这不是果冻专用件**，任何"读几个键 → 过弹簧 → 写几个键"都能用它。

### 20.5 预设：第一个是果冻眼

`HoSpringPresets.JellyEye(meshes)`：搭结构（两个自由度，f = 6 / 8.5，ζ = 0.25）+ 给驱动键。
驱动键按 `HoBlinkKeyTable` 的"眼睑闭合"语义找（VRM `Blink`、MMD `まばたき`、VRChat `vrc.blink`……），
**再补 ARKit 的 `eyeBlinkLeft` / `eyeBlinkRight`** —— 面捕落下来的值落在模型自己的键上，
但整套 ARKit 命名的模型也很常见，而那张表是按 VRM/MMD 规范命名的、不含 ARKit。

两个频率不同是关键：`ζ = 0.25` 只给"会过冲"，**两轴不同频**才让参数走成 Lissajous，
读起来才像有机运动而不是一根直线来回（这条在第 1 步的物理用例里已经钉住）。

### 20.6 还没做

1. **播放模式的专项验收**：组件自己的逐帧链路已经在编辑期验过了（`Step()` 抽成公开方法就是为了
   这个：喂 90 帧，读一个已落下的键 → 弹簧 → 写自己的键，峰值 100）。还没验的是它与面捕
   **同时**跑时的表现（执行顺序、同批键的占用表交互）。

面板 `Editor/Constraints/HoSpringConstraintEditor.cs` 已经按仓库的版面规矩做出来了，只有两层列表：
网格 → 输入键 → 弹簧（跟随/回弹/增益 + 当前值横条）→ 目标（每行只放 **键名 / 正反向 / 增益 / 强度**，
`HoShapeKeyTarget` 剩下的 ramp 与输出范围收在行末的「更多」里，一层、且次要），底部是
「＋ 果冻眼（两个组件）」「＋ 再来一根（复制网格和输入）」。

**面板上还欠一条警告**：目标键如果正被面捕占着（`HoFaceOutputOwnership`），写会被跳过 ——
这是对的（不许抢），但**不报错**，用户只会看到"没效果"。要在目标行上直接标出来。

## 21. 「眨眼 + 眯眼」叠加：业界实际怎么处理（已核实）

现象：ARKit 的 `eyeBlink` 与 `eyeSquint` 在模型上闭的是**同一块**，裸输入里两者同时非 0，
于是同一个形变被写了两遍 → **过眨眼**。这一节是把三条实际做法查清楚之后的结果 ——
**结论：我原先"在参数层用乘法把眯眼压下去"的想法，不是他们的做法。**

### 21.1 模板侧（Jerry）：把会重叠的语义放进同一棵 2D 树，而且**姿势自带闭眼量**

把五个眼睑姿势片段摊开看（`.research/dump_clips.py`，实测）：

| 姿势片段 | eyeBlinkRight | eyeSquintRight | eyeWideRight |
| --- | --- | --- | --- |
| `Eye_Lid_Blink_Right` | **100** | 0 | 0 |
| `Eye_Lid_Neutral_Right` | 0 | 0 | 0 |
| `Eye_Lid_Wide_Right` | 0 | 0 | **100** |
| **`Eye_Lid_Squint_Right`** | **90** | **100** | 0 |
| `Eye_Open_Squint_Right` | 0 | **100** | 0 |

三点关键：

1. **每个姿势写的都是同样那三个键**（blink / squint / wide），只是值不同 ——
   所以它们是**同一棵 FreeformCartesian2D(开合 × 眯眼) 树**的五个格子。
2. **"眯眼"这个姿势里自己带了 blink 90**。作者把"眯眼时眼睛有多闭"直接摆进姿势里，
   于是"blink 高 + squint 高"落在 2D 空间里一个**已经被摆好的点**，不是两个形变相加。
3. **树是插值、权重和恒为 1**，所以合成结果**永远不会超过最强的那个姿势**；
   而我们的裸树是"两个独立子节点各自权重 0..1"，两者相加自然就翻倍。

**这就是"为什么眼睑是 2D 而嘴是 1D"**：不是好看，是必须 —— 会互相叠加的语义只能进同一棵树。

### 21.2 UE 家族：模型上直接放一个**组合校正键**

同一套模板的 Unified Expressions 一族里，闭眼+眯眼有专门的键：
`EyeClosedSquintCorrectiveRight`（以及 `EyeSquintRight` / `EyeWideRight` / `EyeClosedRight`）。
姿势片段直接把它写进去 —— 组合本身就是模型作者交付的一部分。

### 21.3 VRCFT 侧：有后处理修正器，但**没有**对眼睑做 blink×squint 抑制

`VRCFaceTracking.Core/Params/Data/Mutation/Correctors.cs`（本地源码实测）：

| 修正 | 默认 | 做法 |
| --- | --- | --- |
| `mouthClosedFix` | **开** | `MouthClosed = Math.Min(MouthClosed, JawOpen)` —— **夹断式** |
| `lipSuckFix` | **开** | `LipSuckLowerLeft *= (1 - MouthLowerDownLeft)` —— **乘法式**（和我想的那个式子同形，但用在唇吸上） |
| `eyeLidBlend` | **关（0）** | 把**对侧眼**的值混进来：`v*(1-b*0.5) + 对方*(b*0.5)`；作用于 `Openness` / `EyeWide` / `EyeSquint` 的左右 |
| `eyeLookSymmetrize` | **关** | 只把**纵向** gaze 取平均（横向的收敛是 TODO） |

也就是说，**VRCFT 对眼睑的处理是"不做抑制"**：它把眼睑开合做成**一只眼一个 `Openness` 参数**，
眯眼是**另一个 shape**，两者怎么合**交给模型/模板**——也就是 21.1 的姿势，或者 21.2 的校正键。

### 21.4 结论与我们的取舍

| 方案 | 出处 | 评价 |
| --- | --- | --- |
| **眼睑做成 2D 树（开合 × 眯眼），姿势里带上闭眼量** | 模板（21.1） | **正解，已采用** |
| 模型上放组合校正键 | UE 家族（21.2） | 取决于模型有没有；有就用 |
| 参数层乘法抑制 `squint *= 1 − blink` | 我原先的想法 | **已删除**，见下 |

**定案（用户）：自己造的东西删掉，尽量按成熟做法来。**
所以那层参数侧补偿**整个删了**（`HoFaceSuppression` 连同它的组件字段、面板行、4 条用例），
改成 21.1 那条：**眼睑做成 2D 子树，姿势表照 Jerry 实测摆**。

### 21.5 落地：驱动层现在的样子

```
Ho/00 Drive (Direct)
  ├ 眼睑左  FreeformCartesian2D(Ho/LidLeft.X, Ho/LidLeft.Y)   权重 = Ho/Gate/Eye
  │     睁大(-1,0)=wide100 / 中性(0,0)=空 / 闭(1,0)=blink100
  │     眯(0,1)=**blink90 + squint100** / 睁大+眯(-1,1)=wide100+squint100
  ├ 眼睑右  同上
  ├ 眼        (Direct, 权重 = Ho/Gate/Eye)  ← 眼球 8 + 眉 5，仍然是"一键一叶子"直通
  └ 唇        (Direct, 权重 = Ho/Gate/Lip)  ← 嘴 22 + 颊 3 + 鼻 2 + 舌 1
```

- **眼睑的两棵 2D 树直接用区域门控当权重**，不额外引"恒为 1"的参数 ——
  跟参考实现一样靠**共用门控**隐式归组（它的 `Always 1` 是给别的场合用的）。
- **轴参数由会话生产**：`开合 = blink − wide`（-1 睁大 / +1 闭）、`眯眼 = squint`。
  这就是"参数算术在外面"——树算不出新参数，只能消费它。参考实现同理
  （VRCFT 在外面产 `Openness`，模板里的 2D 树只管姿势）。
- 已经废弃的六个直通片段（`eyeBlink*` / `eyeWide*` / `eyeSquint*`）**会被清掉**，
  反复应用不堆子资产。

**§18.5 那条"抑制放 C#、不放树"要收窄**（而且我在这里先写错过一次，见第 22 节）：
能靠**姿势**表达的重叠（眼睑）放树；`min`/`max`/除法这类**非多项式**的运算才在外面 ——
VRCFT 的 `mouthClosedFix`（`min`）正是这种；而 `lipSuckFix`（乘法）**其实树里能做**。

## 22. 混合树的表达力：能算什么、不能算什么（纠正我先前的说法）

用户追问：「合成两个值变成一个值，混合树真的做不到吗？预先分配一个控制器图层参数，
它不就能输出了吗，下游再读。」—— 要分**两层**回答，而且**我先前有一句是错的**。

### 22.1 「写进参数」这层：纯 Unity 确实做不到

混合树的输出是**对象上的属性值**（Transform、形态键、材质、组件字段），
它**写不了 Animator 参数** —— `EditorCurveBinding` 能绑到的"属性"里不含 Animator 参数。

- **能做到的是**曲线绑**组件字段**（拿一个哑组件当锚）。参考实现的
  `FTv2EyeLid*1Proxy.anim` 就是这么干的：曲线绑在 `attribute: OSCm/Proxy/FT/v2/EyeLidLeft` 上，
  另有一条绑组件属性的锚。
- **VRChat 能"曲线驱动参数"**，是客户端**额外实现**了这个特性（求值后把那种值写回参数）。
  Unity 没有。这正是我们推迟的"反馈桥"（§14.3）。
- 真要在 Unity 里做，就是"曲线写哑组件 → C# 每帧读 → `SetFloat` 写回参数"，**代价是一帧延迟**，
  而且能表达的值不会超过 22.2 那个上界。

**对我们没有收益**：下游（会话、真模型）本来就在 C# 里。绕一圈（树 → 组件字段 → C# → 参数）
只多一层间接和一帧延迟，算出来的东西还受同一个上界限制。

### 22.2 「算一个值」这层：树比我说过的能算得多（**我说错的地方**）

Direct 树对**每个属性**的结果是：

    输出 = Σᵢ (Πⱼ 门控ᵢⱼ) · 值ᵢ  +  (1 − Σw) · 默认值      然后按属性范围钳制

也就是一台**以参数为变量的多项式机器 + 钳制**。所以这些**都能表达**：

| 想要的 | 树里怎么做 | 备注 |
| --- | --- | --- |
| 加权和 `Σ wᵢ·Cᵢ` | 多个子节点写同一个属性 | 普通混合 |
| **乘积 `a·b`** | 嵌套 Direct：外层门控 a，里层再门控 b | 参考实现的门控层级 |
| **`(a+b)/2`（取平均）** | 两个子节点写同一属性、系数 0.5 | **参考实现的 `EyeSyncMix = 0.5` 就是这个** |
| `1 − a` | 同一属性上两个子节点写 1 与 0，权重为 a | —— |
| 幂 `a²` | 同一个门控套两层 | —— |
| 上下限 | 属性自身的范围（0~100）就是钳制 | 果冻超调靠它 |

**做不到的**：`min`、`max`、除法、以及任何需要"记忆"的东西（弹簧、平滑、带回差的阈值）。

### 22.3 结论：那条线按"是不是多项式"划，不按"是不是参数算术"划

> **能写成"参数的多项式组合"的 → 进树**（加权和 / 加权平均 / 乘积 / 幂 / 反向）；
> **只有 `min`/`max`/除法/需要记忆的 → 在外面算完再传进去。**

于是逐条落位：

| 处理 | 树能做吗 | 落位 |
| --- | --- | --- |
| 眼睑 blink × squint 叠加 | ✅ 2D 姿势 | **树**（已做） |
| VRCFT `mouthClosedFix`（`min`） | ❌ | 外面 |
| VRCFT `lipSuckFix`（乘法） | ✅ | 它放在外面，是因为那是与模型无关的 tracker 通用后处理 |
| **我们的双眼同步（取平均）** | ✅（`EyeSyncMix = 0.5` 那个加权和就是） | **留在 C#** —— 但理由**不是"树做不到"**（我先前这么说过，是错的），而是：VRCFT 也在 C# 做（`Correctors.BlendOpposingParams`），而我们的下游本来就是 C#，三行代码比生成一棵"OFF/ON 两版映射"的树简单 |
| 平滑 / 死区 / 弹簧 | ❌ 需要记忆 | 外面（会话 / 独立组件） |



**另外两条顺手核实的**（跟双眼同步有关）：

- VRCFT 的 `eyeLidBlend` **默认关**，而且它融合的是 `Openness` / `EyeWide` / `EyeSquint` 的左右，
  **不含眼球横向**；横向由另一个开关 `eyeLookSymmetrize` 处理，且它只做纵向、横向标着 TODO。
  （Jerry 的模板里另有 `EyeSync In/Out`，所以"横向要不要同步"在生态里是**模板层**的选择。）
- 我们现在的实现把眼球横向的跨对同步做进了同一个开关里 —— 比 VRCFT 多、比 Jerry 一致。
  保留，但要知道它不是 VRCFT 的行为。


### 20.7 面板这一版：汉化 + 默认值 + 果冻预设入口

**默认值那个坑值得单独记一笔。** 默认 Inspector 的截图里，新加的目标是
**权重 0 / 增益 0 / 偏移 0 / 输出上限 0 / 钳制 关**——全是 0，也就是这一路什么都写不出来。
根因是 Unity 的 **`SerializedProperty.InsertArrayElementAtIndex` 不跑字段初始化**：
插入的嵌套对象是"零值实例"，`weight = 1.0f`、`outputMax = 100.0f` 这些初始化器全都不执行
（枚举倒是全落在 0 上，所以看起来像"叠配/直通/双眼"，更迷惑 —— 只有数字是 0）。

改法：**加元素走真对象**（`component.Targets.Add(new HoSpringTarget(...))` + `Undo.RecordObject`
+ `serializedObject.Update()`），构造器会跑，默认值就是对的。
（同目录别的编辑器插的是 `List<HoShapeKeyTarget>` 本身、且列表通常非空——非空时 Unity 会
**复制上一个元素**，所以他们只清身份字段就够了。我们这里是"嵌套类 + 可能空列表"，两个坑叠一起。）

**输出上限的默认值改成 90**（`HoSpringTarget.DefaultOutputMax`）。理由：果冻的全部意义在超调，
钳在 100 就看不见它。这一条只影响弹簧这一侧，`CreateRuntime` 多了一个可选参数，别的调用方不变。

**汉化**：`HoShapeKeyRampPreset` 是唯一一个没加 `[InspectorName]` 的枚举（下拉里显示
Direct / SoftFollow / Amplify…），补齐成 直通 / 柔跟 / 放大 / 缓入 / 慢放 / 阶梯 / 自定义；
面板里我写的英文小标题 `ramp` 也换成「成形」。其余枚举（叠加/覆盖、夹断/软饱和/按比例分配、
双眼/左/右、全部/指定）本来就有中文名。

**果冻预设有了两处入口**：面板顶部的主按钮「果冻眼 ×2」，以及
`GameObject/HoUnityTools/果冻眼（弹簧驱动 ×2）` 菜单。两者都会在网格列表空着时
**从 Animator 根往下自动收网格**，并给每根弹簧放好两行待填目标（挤压 / 回弹）。
不然"点了预设"和"什么都没配"长得一样。

**版面**：全部用 `Card()` 分组（预设 / 网格 / 输入键 / 弹簧 / 目标 / 缺失），
弹簧那一组加了三条横条（输入、弹簧值并带 1.0 的 ghost 线标出超调区、目标输出），
标题行只放一个状态胶囊 + 实时值。仍然**没有任何折叠分区** —— 只有目标行末尾那个「更多」
（成形 / 输出范围 / 混合方式）是一层，且是次要的。
