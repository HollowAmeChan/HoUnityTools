# 面捕中间层处理

日期：2026-09-23。这份只讲**中间层**：它在哪、每一段做什么、按什么顺序、以及**为什么其中有些必须留在树外面**。
工作流见 [面捕工作流](FACE_TRACKING_WORKFLOW.md)；能力边界见 [混合树的能力边界](BLEND_TREE_LIMITS.md)。

## 1. 它是什么

**参数进、参数出。** 中间层只搬运和加工**值**，从不碰姿势 —— 姿势是混合树的事。
它跑在 C# 里（会话），因为**它要的三样东西混合树都没有**：

| 它需要 | 树有吗 |
| --- | --- |
| **时间 / 历史**（平滑、弹簧） | ❌ 树是参数的纯函数，没有状态 |
| **非多项式运算**（`min` / `max` / 除法） | ❌ 树只会"加权和 + 门控相乘" |
| **产生一个新参数** | ❌ 树只能写对象属性，写不了 Animator 参数 |

反过来说：**凡是能写成"参数的多项式组合"、或者能靠"姿势"表达的，都该进树**（判据见 §4）。

## 2. 处理清单

| 顺序 | 处理 | 做什么 | 在哪配 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | **通道映射** | ARKit 通道 → 形态键 / 参数名 | 「输入参数」 | 键名解析只看网格上真实存在的键 |
| 2 | **模式** | 实时 / 手动 / 保持 / 中性 / **交还** | 「输入参数」每行 | 「交还」= 不碰这个键，让给基础动画（走占用表释放） |
| 3 | **增益 + 中性值** | 每路乘系数、断流落回哪个值 | 「输入参数」每行 | |
| 4 | **死区**（4 组） | 低于阈值按 0，以上重新铺满 | 「参数生产」 | **只作用在实时输入**，手动滑杆不吃 |
| 5 | **平滑**（4 组） | 指数平滑，每组一个时间常数 | 「参数生产」 | 默认 0（透传）—— 手机侧自带处理，叠一层会加延迟 |
| 6 | **双眼同步**（可选） | 把左右眼合成一个值再写回两侧 | 「参数生产」 | 治"两眼闭合程度不一致"。**开着就不能 wink** |
| 6 | **单键双眼**（可选） | 只驱动一侧，另一侧写 0 | 「参数生产」 | 只适用于**左右键各自都能闭双眼**的模型 |
| 7 | **区域门控** | 眼 / 唇 / 凝视 → 写成 `Ho/Drive/Gate/*` 参数 | 「控制器输出参数设置」 | 门控是**参数**，可以被任何东西驱动（用户自己的层、以后的菜单） |
| 8 | **轴生产** | 眼睑 2D 树的两根轴：`开合 = blink − wide`、`眯眼 = squint` | 「参数生产」（隐式，不可关） | 见 §3，这是**必须**在外面的参数算术 |
| 9 | **写参数** | 52 个 `ARKit/*` + 门控 + 轴 + 调试预览覆盖 | —— | 影子台 `SetFloat` |

**不属于中间层但同一族**：果冻/弹簧 → 独立组件（`HoSpringConstraint`，读落下来的键 → 弹簧 → 写键）。
它**不借道 Animator 参数**（`Ho/JellyX|Y` 那两个参数已撤销，生成器也删了）。理由见
[层间分工（已归档）](archive/FACE_TRACKING_PIPELINE_SPLIT.md) 19.2：混合树出不了物理参数，
生产者与消费者就都不属于状态机。

## 3. 顺序（为什么是这个顺序）

```
原始 52 通道
  → 增益 / 死区            （只对实时输入整形）
  → 分组平滑               （有时间常数，必须在这里）
  → 双眼同步 / 单键双眼     （跨眼的合并，用平滑后的值）
  → 区域门控 + 眼睑轴生产   （轴 = 参数算术；门控 = 交给树的参数）
  → 写出去
```

两条纪律：

- **轴必须在写参数之前算完**（树只消费，不生产）。
- **单眼内的修正要在跨眼合并之前**：合并会把一侧清零，之后就没东西可修正了。
  （现在没有单眼修正这一项 —— 曾经有过一个"眯眼抑制"，因为自造而删掉了，见 §5。）

## 4. 判据：这件事该放中间层，还是放树里

> **能写成"参数的多项式组合"的 → 进树**（加权和 / 加权平均 / 乘积 / 反向 / 幂 / 门控开关 / 两版映射交叉淡入）；
> **`min` / `max` / 除法 / 需要记忆的 → 中间层**；**参数 → 姿势的映射 → 树**。

一个实用的问法：**我要的是"值"还是"姿势"？** 要值给别人用 → 中间层（或反馈桥，见能力边界 §4）；
要姿势 → 树。

## 5. 隐式处理：哪些是"看不见的"，怎么处理

中间层里有几件事用了机制、但在 UI 上看不到 —— 记在这里，免得下次又被当成"没做"或"玄学"：

| 隐式处理 | 为什么看不见 | 现在怎么办 |
| --- | --- | --- |
| **眼睑合并**：`blink / wide / squint` 三个键被写进**同一棵 2D 树**的姿势里 | 它发生在**树**里，而树是控制器作品（作者编的），面板上没有对应项 | 见下面「已决定不做开关」 |
| **眨满时眯眼被权衡掉**：两键加和从 200 降到 ~110 | 树的性质（权重和恒 1），没有对应代码 | 同上；要精确控制就补 `A3X2Y2` 那格姿势（§6） |
| **`wide` 与 `blink` 压成一根轴**，两者不可区分 | `开合 = blink − wide` 是会话里算的，面板上没有一行 | 可以显示；它是**有损**降维（`wide=0.5` 与 `blink=0.5` 同值），但两根轴已经是树的上限（没有 3D 树） |
| **区域门控写的是 `Ho/Drive/Gate/*`** | 参数在控制器里，面板上是三个勾 | 摘要里有「眼 · 唇 · 凝视」 |

**眼睑合并暂时不做开关；但"隐式"已经消掉了** —— 面板「控制器输出参数设置」里有一行**只读的「控制器结构」**，
从**资产**读出来报给你（"N 层 · M 个状态 · K 个片段 · 写 J 个形态键"，以及模型上没有的那些键）。
**从资产读而不是从配置推断**：它显示的永远是事实。
不做开关的理由：开关要么让树里同时放两条路（`独立直通版` + `2D 合并版` 靠门控切），
要么是结构开关（去改那份控制器作品再重新初始化）—— 两条都让眼睑这块的面积翻倍，
而它服务的需求（真有模型要 blink/squint 独立驱动）**我们还没遇到**。

## 6. 欠账（三条已于 2026-09-23 还清）

1. ~~**`闭+眯` 那格姿势没摆**~~ → **已补**（格点 `A3X2Y2`，片段名 `LidL__BlinkWide__Squint__A3X2Y2`）：`blink 100 + squint 0`，
   两键加和正好 100，"眨满时眯眼还剩多少"从此是**作者的决定**而不是引擎的边界行为。
   （用例断言这一格是 100 / 0。）
2. ~~**面板不报告结构**~~ → **已加**：「控制器输出参数设置」里一行只读的「控制器结构」，从资产读（§5）。
3. ~~**两个眼睑开关还是两个布尔**~~ → **已收成一个三选一**：`左右独立 / 强制同眨 / 单键双眼`。
   底层仍是原来那两个布尔字段（序列化兼容），只是呈现成互斥的三档 ——
   那个到不了的组合（同步关 + 单键开）从此不可能被选出来。

它是"有损降维"，用户看不到自己丢了什么。下一步可以把它并进「控制器结构」那一行。
