# 动态参数（Hub）的坑：五天里改了五次设计

正本：[动态参数（语义输出）](../FACE_TRACKING_DYNAMIC_PARAMETERS.md)（现在的形状）、
[控制器输出范围与实测能力](../ANIMATOR_OUTPUT_PIPELINE_DESIGN.md)（我们到底写哪些东西）。
这份只留**被删掉的形状、它们为什么留不住**，以及现场真咬过我们的两个坑。

判据是"当时真的发生了、而且下次还会发生"：**下面每一版都真的写进过代码**，
所以"想再把某个中间版本捡回来"的念头出现时，先看这里的理由还成不成立。

## 0. 时间线：别把中间那几版当现状

| 时间 | 当时的形状 | 为什么没留下来 |
| --- | --- | --- |
| 2026-09-25 | 词表放 **ScriptableObject 资产**（`HoFaceSemanticAsset`），值放 `float[] values` + `string[] names`（两个平行数组按下标对齐） | 资产那半边**从来没有过消费者**（§3）；平行数组只为"曲线写下标"和"纯按下标写"服务，两条都删了 |
| 2026-09-26 上午 | 写手 = **动画曲线写 `values.<i>`** | 绑定是静态字符串，作者必须先知道下标（§1） |
| 2026-09-26 下午 | 写手 = **控制器状态上的 `StateMachineBehaviour`**（`Add Behaviour` + `{slot, expression}`） | 中间层本来就算得出那些值 ⇒ 两份真相；且它是"只在 bundle 里跑、编辑器里看不见"的写者（§2） |
| 2026-09-26 晚 | 写手整个删掉 ⇒ **中间层算完直接写 Hub** | —— 这一版就是现在 |
| 2026-09-27 | 「把手」（`HoFaceSemanticConnector`）也删掉；两个平行数组**收成一个键值对列表** `List<HoFaceSemanticSlot>` | Connector 的三条理由全没了（§4）；平行数组的下标不变量没有存在意义了（§3 末） |

⚠️ 这五次里**每一次都是"看起来更统一、实际少一个失败模式"**，所以现在这份形状的特征是：
**一个组件、一条键值对列表、一个写入口（中间层）**。少一样都别改回去。

## 1. 用动画曲线写 `values.<i>`（09-26 上午废弃）

症状：一切都能跑，但作者**必须先知道下标**，而且**顺序一变就静默写错槽**。

| 曲线写数组元素 | 现在（中间层按名字写） |
| --- | --- |
| 绑定是静态字符串 ⇒ 作者必须知道下标 | 按名字，不用知道下标 |
| Animation 窗口里数组元素是 `Element 0..N`（**没有名字**） | 名字就是输出行的 `parameter` |
| 顺序一变 ⇒ 旧曲线**静默写错槽** | 顺序无所谓（谁先写谁在前） |
| 长度要在打包前猜对（越界写静默无效） | 槽由写的人当场开，**没有长度** |

**它当年还只是推断、不是实测**：能力表里测过的是脚本 `float`/`bool`/`int`、`Vector`/`Color` 分量、
开关、材质、对象引用，**没有"数组元素"这一行**；而数组元素的 SerializedProperty 路径通常是
`values.Array.data[i]`，与注释里写的 `values.<i>` 是两个不同的字符串。
那条路**已经不在代码里**了（`Tests~` 里原来那两组探针也一起删了），
所以"到底哪个字符串能写"这个问题现在没有答案 —— **要走回去就得重新测**。

## 2. 控制器状态上的「语义写手」（同一天下午废弃）

它解决的是曲线那条路的下标问题：`Add Behaviour` → 填 `{slot, expression}`，
变量是这个控制器的 Animator 参数，`OnStateEnter` / `OnStateUpdate` 按名字写进**影子** Hub，
再由会话 / 节点中转到角色 Hub。**为什么连它也删了**：

* 那些值**中间层本来就算得出来**（它就是写参数的那个人）—— 让控制器再算一遍 = **两份真相**；
* 它是一个**只在 bundle 里跑、编辑器里看不见**的写者：出问题时"面板里对、Warudo 里不对"
  这类最难查的现象就多一个来源；
* 它带来的每一件麻烦（影子 Hub、中继、`ValidateMachine` 的"只放过某一个"例外、
  "bundle 能不能解析到这个类型"这条没验的依赖、`P/A` 探针）都只为它服务；
* 想读姿态（它唯一有理由做的事）**现在也没做**：姿态本来就能采，
  真要"按姿态再产出一个参数"，正确的位置是**中间层再来一遍**。

**结论**：**我们**的写者只有一个（中间层），而且它**不在控制器里**；出口只有一个（Hub）——
但 Hub 自己是谁都能写的，只是 **clip 写不了它**。

## 3. 槽表 / 词表资产：第二份真相（09-25 删资产、09-26 删表）

删掉 `HoFaceSemanticAsset` 的理由**是实测的**：

* 资产那半边**从来没有过消费者**：`IndexOf / KeyAt / NeutralAt / BuildKeySnapshot / FillNeutral`
  的外部调用点 **0 个**；`HoFaceSemanticHub.GetFloat(string) / SetFloat(string) / ResetToNeutral()`
  的外部调用点也是 **0 个**；`AlignToAsset()` 只有写动态参数节点那一处。
* 资产存在的**公开理由也不成立**："bundle 里放不了组件类型 ⇒ 名字必须放在双方都能引用的东西上"
  —— 可 bundle 里那份 Hub **本来就没有资产**，控制器从头到尾**按下标**读。
* 用户定：**不做跨角色共享词表**（N 个角色 = N 份拷贝，这是有意的，不是缺陷）。

那之后词表挪到了 Connector 上（一张 `key`/`note` 表），**同一天又删了**：

* 名字**本来就由写的人在运行期声明**（谁写谁开一格），长在 Hub 上 —— 表里再写一遍就是**第二份真相**；
* 有了表，节点就要拿它**寻址**（名字 → 下标），于是那个组件变成"注册表"，**不再像个接口**
  （用户原话："connector 现在变得不像一个连接器了，他本来的职责应该是把动态参数挂出去用的"）；
* 用户定的用法是：**"名字都不用列，先跑一遍运行看里面有啥，或者约定好名字用"**。

⚠️ **代价要认**：表同时还兼着"**名字对不上**"的校验点。删掉之后，配置里把 `MouthX` 敲成 `Mouthx`，
那条值会**安静地**落到另一个槽（`Mouthx`），而读 `MouthX` 的人只会拿到 0。
发现它的办法只有两条：**跑一遍看 Hub 里的名字**（或面板的「参数输出」栏），或者看节点/会话状态里那行
**新声明**（新开出来的名字会点名）。

⚠️ **中性值从来不在表里**：中性 = `0`，是**静态规则**（想清就 `hub.Zero()`）。
`0.5` 那种"中立位"是 VBridger 私有的约定，我们**不采用**（[HO 参数规范](../PARAMETER_HO.md) §2）。

**平行数组是怎么收掉的**：`float[] values` + `string[] names` 按下标对齐，只为两件事服务 ——
① 动画曲线能绑到 `values.Array.data[i]`；② 老式"纯按下标写"那条路。两条都删了以后，
"两个数组必须等长、下标必须对齐"成了**纯粹的下标漂移风险**，
所以改成 `List<HoFaceSemanticSlot>`：一格一个 `(key, value)`，**没有平行不变量可以破坏**。

## 4. 「把手」（Connector）为什么站不住（09-27 删）

它当年存在的三条理由，在槽表删掉之后**全都不成立了**：

| 当年的理由 | 现在 |
| --- | --- |
| "接口不能有状态（bundle 里的代理 Hub 得跟着造一份假的）" | 早就没有代理 Hub 了（写手删掉之后影子上不再跑 Hub） |
| "消费方只需要一个引用" | 直接引用 Hub 同样是一个引用，而且少一次跳转 |
| "名字的定义权留在写的人手上" | 这件事现在由 **Hub 自己的 `SetFloat`**（谁写谁开格）承担 |

于是它只剩"再指一次 Hub"，还多两个失败模式（**忘挂**、**没填引用**）。**删掉，Hub 自己就是那个入口。**

## 5. 现场挖出来的两个坑（09-26）

### 5.1 `ValidateMachine` 一票否决 ⇒ 会话**起不来**

症状：**脸不动、Hub 空**，而报错只是一条容易被略过的红框。
原因：`HoFaceAnimationAssets.ValidateMachine` 原来"控制器里**任何** `StateMachineBehaviour`
都一票否决"，而当时写手就挂在控制器基座层上 —— 校验先把控制器判死，会话自然不启动。
怎么办：写手删掉之后，这条**回到"任何 Behaviour 都拒绝"**，不再需要例外。
⚠️ 附带一条操作教训：**改完代码一定要让 Unity 重编译** ——
现场第一次报"毫无变化"，就是因为修复还没进编译。

### 5.2 面板看不到中间层的输出值 ⇒ 分不清两种失败

症状：不知道是"配置没算出值"还是"算出来了但写不进去"。
原因：当时面板只有「参数输入」那一栏的裸线名，**中间层的求值结果不可见**。
怎么办：现在「参数输出」栏逐行摊开，并把**参数不在控制器里**的行单独标出。
判据：`N 行 · 非零 M · 不在控制器里 K`。

## 6. 老链路的那次现场实测（现在要重跑）

**✅ 当时实测通的是"写手"那条链（现已删除）**：土豆角色 + `PTP_CTR_Face_ARKit` + `ho-iPhoneVTS`，
控制器基座层默认状态上挂写手（10 条语义），会话每帧 `shadow.Update(0f)` ⇒ 影子 Hub 按名字开槽
⇒ 中继写到**角色那片 Hub**。证据有两条：

* 面板「参数输出」栏逐行显示中间层的求值结果；
* 角色 `面捕动态参数` 的 Hub 里 10 个槽**都带着名字与实时值**
  （`jawOpen=0.032 · mouthRound=0.559 · LidLeft=0.242 …`）。

⚠️ **那次跑的是"写手 → 影子 Hub → 中继"三段，现在只剩"中间层 → 角色 Hub"一段**，
所以**现在的形状要重新跑一遍现场**（Hub 里有名字与实时值 = 通过）。
机器化的回归门是 `Tests~/FaceTrackingValidation.cs` 的 `stage 18`：会话算完一帧后断言角色 Hub 上
**槽数 = 输出行数**、且 `ARKit/jawOpen` ≈ 0.6（`HO_HUB_PUBLISH` 那一行是它的读数）。

**⚠️ 还剩没验的**：**Warudo 侧的连线与面板**（节点 → 角色 Hub 真的写进去了没有）。
Unity 侧的现场与批处理用例都测不到 Warudo 的节点行为 —— 那是跨仓验证项
（[仓库与提交](REPO_AND_GIT.md) §7）。

## 7. 输出范围：从"七种属性 + 一组适配器"收到"只写姿态 + Hub"（09-26 ~ 27）

症状（当时的设计长这样）：2026-09-25 的实测列出了 Unity **能**被曲线驱动的七种东西
（脚本 float/bool/int、Vector/Color 分量、部件与 Renderer 开关、材质 float/color、材质对象替换），
于是规划了一整套"求值帧 `properties[]` + 批量应用节点 + 注册组件适配器 + 合成 MPB + 对象引用切换"。
**那套从来没有落地**，而且每加一种目标类型，都要多一套"写进去还得能读回来"的适配器。

原因（用户定）：**组件值全部走 Hub。** 控制器只写三种东西 —— 形态键动画、骨骼动画、**Hub 槽**；
材质属性、对象引用**从我们的范围里去掉**，组件**不再是写入目标，而是 Hub 的读者**。
判据：写任意组件字段的能力上限取决于**我们能不能把值读回来**，
而读回来要么反射（UMod 禁 `System.Reflection`）、要么得有一个能被动画的已知类型 —— 成本远高于收益。

怎么办：

* 别再加"应用 XX 组件 / 应用材质 / 应用部件状态"这类 node（原来那几行规划都删了）；
* 要放开某一类之前，先看[控制器输出范围](../ANIMATOR_OUTPUT_PIPELINE_DESIGN.md) §2 的能力表 ——
  **那些实测仍然有效，不用重测**；
* ⚠️ Hub 的槽是 **float**：非 float 语义（开关 / 档位 / 向量 / 颜色 / 引用）经过 Hub 时
  要自己定编码（0/1 当真假、三个槽当一个向量），这是收窄的代价。

## 8. "曲线写 Animator 参数是 VRChat 专属"——这条结论是**错的**

症状（当时）：旧文档把"用动画曲线驱动 Animator 的 float 参数"当成 VRChat 专属能力，
于是设计里绕开了它。原因：**没有实测就写进了文档**。
怎么办：2026-09-25 用普通 `.anim` + `AnimatorController`、绑定
`path="" / type=Animator / propertyName="Derived"` 直接验证 —— **两个 Unity 版本都通过**。
判据留档：`Tests~` 之外的一次性实验在 `.research/controller-capabilities/`，
摘要表见[控制器输出范围](../ANIMATOR_OUTPUT_PIPELINE_DESIGN.md) §2。
**教训**：这类"引擎能力"的结论只认实测，看到"某某专属"的说法先去量一次。
