# 混合树的坑（都实测过）

用例在 `Tests~/FaceTrackingValidation.cs`，探针阶段的日志行是 `HO_WDON` / `HO_WDOFF` / `HO_WDZERO` / `HO_MATRIX`。
能力模型与判据见 [混合树的能力边界](../BLEND_TREE_LIMITS.md)。

## 1. 「Direct 树 + 写默认值关闭」会发散

症状：同一个 Direct 树，WD 关掉之后值**逐帧往上爬**，几帧就跑飞。

| 条件 | jawOpen（参数 0.6） |
| --- | --- |
| Direct + WD 开 | **60.0**（精确 = 参数 × 100） |
| Direct + WD 关（场景里没有别的写入者） | 0 |
| Direct + WD 关（基础动画也在写同一个键） | **98.98 → 246.28 → 1059.33** |

原因：Direct 树里权重和不足 1 的那部分 `(1 − Σw)` 会与"当前值"混合；**WD 关时这个"当前值"永不复位**。
`98.976` 精确等于递推 `out ← 0.6×100 + 0.4×out` 的第五项 —— 机制是被这条算式验证的，不是猜的。

怎么办：`Compile` 直接拒绝这个组合（不留给运气）；模板里所有状态保持 WD 开。
"必须 WD Off"是早期接管 Animator 时代的过期约束，影子台是隔离的、没有别的写入者，WD On 无害。

## 2. Direct 树**不**归一化

症状：先入为主地以为"多个通道同时给会互相削弱"，于是给每个键开一个 Override 图层（52 键 ≈ 52 层）。

实测：`jawOpen=0.6` + `mouthSmileLeft=0.8` 同时给 → **精确 60 / 80**。
同一个属性被两个子节点写时：`0.6 + 0.8` → **140**（不是 70 的平均，也不在树里钳到 100）。

怎么办：一层一棵 Direct 树就够了；但**同一个键不要被两条直通叶子写**（会相加），
会重叠的语义要用"选一格"的姿势树（[能力边界](../BLEND_TREE_LIMITS.md) §6）。

## 3. 嵌套 Direct 门控是**相乘**的

`0.6`（外层门控）× `0.8`（内层门控）→ **48**。
树本身支持"这块算不算数 × 这只眼算不算数"，不必自己先乘好。
（曾经我们有一整套 `Ho/Drive/Gate/*` 区域门控参数，**已删** —— 哪些键算数现在由使用者自己的树决定。）

⚠️ **但"把门控乘在树里"是我们现在的边界：门控只做一层**（2026-09-26 用户定）。
理由在动态参数那条链上：**树内部算出来的量没有出口** —— Hub 是一片"脚本写的工作台"（谁都能按名字写），
但**动画 clip 写不了它**（曲线写 `values.<i>` 那条路已删），我们也不再提供跑在控制器里的写者。
一层门控时"有效门控 = 那个参数"（Hub 里就是真值，下游不用重算）；嵌套时"有效门控 = 各层相乘"，
只活在树里（真要就得自己写个组件去读参数、算完写 Hub）。
想要"两个开关的与"，请在**中间层**乘好、作为**一行输出**喂进树。
完整论述（含现在这份控制器的形状）见 [控制器结构](../FACE_TRACKING_CONTROLLER_STRUCTURE.md) §3.3。

## 4. WD 开时，"默认值"混的是 **Animator 启动时的值**

同一个属性被权重 0.6 的子节点写、启动时是 33：结果是 `0.6×100 + 0.4×33 = 73.2`，**不是 60**。
早先探针台量到"精确 60"只是因为那边的启动值是 0 —— 差点据此写错回退方案。

两个推论：
- 想用"部分权重混回基础表情"，**基础值必须在 Animator 挂上控制器之前就摆好**。
- 权重为 0 的子节点**不写 0**，它根本不碰那个属性；状态里没有任何片段动画的属性也一样不被碰（实测保持 33）。

## 5. 树**产不出参数**

混合树只能"读参数、出姿势"。任何"两个键合成一根轴"（`开合 = eyeBlink − eyeWide`）都必须在外面算好再喂进来 ——
这就是为什么轴的生产算**中间层**（配置文件里那一行表达式）、不算树。曾经的 `HoFaceAxis` 辅助类已删，
它的活现在就是配置里的一行字。

## 6. 2D 表：**超范围是钳制**，但**缺一角就不可预测**（2026-09-27 实测）

**症状**：想靠"轴超出 1 也没关系，树会自己夹住"来省掉中间层的归一化；或者稀疏采样时留一个空格子，
以为只是"那一格没有姿势、会插值过去"。

**实测**（数字与做法见[能力边界](../BLEND_TREE_LIMITS.md) §10）：

| 摆法 | 轴超出范围时 |
| --- | --- |
| **完整的圈**（矩形网格 3×3 / 2×2 / 3×1 都摆满） | 参数点被**投影到圈边**、再用那条边的两个端点线性混合 ⇒ 落点**永远在圈上**（x=−3 与 x=−1 同值，x=3 与 x=1 同值）；**把整列/整行/单角往里挪之后，照样落在位移后的圈上** |
| **缺一个角** | 圈被切掉一块 ⇒ 圈外那一侧落在**缺口那条新边**的两个邻居中间（实测 (1,1)=151.5 = 201/102 各半）；**安全，但不再是原来那个角** |
| **孩子落在别的孩子构成的边/线上**（退化摆法） | 那个孩子在**圈外算不到** ⇒ **圈内外跳变**（实测 (0,0.5)=166.67 而 (−0.5,0.5)=100）⇒ 别这么摆 |
| 内部（非对称点） | ⚠️ **不是分段线性**：实测与手算差最多 ~6%（(0.2,0.3) 得 129.93 而手算 121.3）。Unity 的 2D 混合是**距离权重**，手册不给公式、五种候选公式也都拟合不上 ⇒ **坐标只是标签，格内的插值形状不能手算**（网格线上是精确的） |

**为什么这是个坑**：钳制太"温和"，于是很容易得出"那就让轴随便超"的结论。三个代价：

1. **分辨率白扔**：轴实测只到 0.75，而槽位摆到 1 ⇒ 后 1/4 的插值空间永远用不到（等于把采样点往后挪一截）。
2. **树与 Hub 不一致**：钳制只发生在树内部 —— Hub / 面板里读到的轴值仍是超出的原值。
   "Hub 里还在涨、姿势却卡住不动"这种不一致，在下游消费者那里最难查。
3. **圈的形状决定"停在哪儿"**：摆满矩形 ⇒ 出界停在矩形边界那一格；**缺角 ⇒ 停在缺口那条新边上**
   （实测 (1,1) = 201/102 各半，不是原来那个角）。两者都安全，但**姿势不一样**，所以摆法要按"你想让它停在哪"来定。
4. **两个别点的东西**：`Compute Positions`（按根运动算 Pos，我们的片段没有位移 ⇒ 一点全塌到 (0,0)）与
   `Normalize Blend Values`（1D/2D 空操作，但 **Direct 上会把权重归一化** ⇒ 我们的区域权重和是 4，勾上摊薄成 0.25）。
   清单见[能力边界](../BLEND_TREE_LIMITS.md) §11。

**机制一句话**（复盘全部数字逐位吻合）：**圈内按距离权重混合；圈外先把参数点投影到圈边、再用那条边的两个端点混合**
⇒ 不管理解成"钳制"还是"投影"，**输出永远在"最外围孩子围成的圈"里面，永不外推**（§10 统一规律）。

**怎么办**：量程 / 死区 / 稳定**都在中间层解决**（响应曲线 + 修饰符），树里只负责"这个轴值长什么姿势"；
槽位坐标只在"这个姿势该出现在刻度 0.4 还是 0.5"时才动（那是合法的第二条路，但插值形状由引擎定、Hub 里仍是原始值）。
三层分工见[控制器：进度与轴口](../VTS_HQ_CONTROLLER.md) §2.3.1 / §3.3。
